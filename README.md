## 这是什么

一句话：**懂业务的人和懂代码的人，大概率是两拨人 —— 而且各自都没时间跨过去。**

这套东西记录的是：怎么由**一个人**把两层能力**一起**灌注给一个 AI，  
再让它**可移植地**去服务这两拨人。

| 层      | 是什么                                                                  | 能复制吗        |
| ------ | -------------------------------------------------------------------- | ----------- |
| **表面** | **六个小工具** —— 让自动化 / AI 协作 / 多人协作不「静默出错」                              | ✅ 直接拿去用     |
| **中间** | **方法论** —— 换一个场景该怎么办                                                 | ✅ 换个领域也能套   |
| **主线** | ★ [**0 号 AI**](docs/zero-agent.md) —— 怎么从 0 带出一个同时懂业务与工程的 AI，再克隆出去   | ⚠ **稀缺在这里** |
| **终局** | [人机共同进化](docs/human-agent-coevolution.md) —— 人和 AI 一起，做"谁都还没描述清楚的东西" | 设想          |

> 这就是为什么仓库里既有**能跑的代码**，又有一堆"**不像代码**"的东西 ——  
> 它们本来就是同一件事的不同层面。

## 怎么从 0？

问题很自然：**既然要一个「双懂」的人，这种人去哪找？**

先把它拆开 —— 这样的人需要**多大**的能力？需要**什么形状**的能力？

我的答案有点反直觉〔作者说：因为"双懂"听起来像 CEO 级，实际需要的却是视角组合，不是职位〕：

> **不需要「很大」，需要的是「很少见的一种组合」；  
> 不需要「什么都会」，只需要三样。**

### 一、为什么「懂业务」是硬需求

最直接的理由是**红线**〔作者说：他在业务里最先想到的就是"什么事不能做"，因为越界的代价不可逆〕：  
只有懂业务的人，才能判断 AI **什么时候正在越过业务边界**，并且在**越界之前**把规矩立好。

> 事后再补救，等你的**往往不是一个问题，而是一串问题** ——  
> 因为 AI 已经把错的做法执行了很多遍。

但我想补一条同样硬的：**验收标准**〔AI 说：只防越界，这个人就只是个守门人；而命题需要的是出题人〕。

|               | 频率     | 后果     |
| ------------- | ------ | ------ |
| **红线**（不能碰什么） | 低频     | **致命** |
| **验收**（什么才算对） | **高频** | 决定成败   |

AI 能做出很多东西，但只有懂业务的人能回答「**这是不是我们要的**」。

**第三条更根本**〔作者说：他从"模型自带经验"里看出真源要分域，才发现业务那一半只能由人提供〕：
**业务上的「对」，只有人能定义。**

| 域 | 真源是什么（谁说了算） | 为什么它能裁决 |
|---|---|---|
| **代码 / 工程** | ★ **「能不能跑」**（编译 / 测试 / 运行时）—— **不是模型** | 它不依赖任何人的权威 —— **它是个实验** |
| **业务 / 价值** | ★ **人的诉求** | 因为业务对不对取决于**人的诉求** —— 不是统计出来的，是**有人要它这样** |

模型在这两域里都是**参照系** —— 代码域里的参照质量远高于任何个人，
但**它不是真源**：真源得能裁决，而模型"适合生成假设，不适合做终审"。

⇒ 这一条把前两条也解释掉了：**没有懂业务的人，红线没人划、验收没人定**；
而 AI 再强，在业务域也只能**参照**，不能**裁决**。

⇒ **懂业务 = 既知道「不能碰什么」，也知道「什么才算对」——
而且这两件事，只有他能说了算。**  
〔对撞出：作者给了"红线"与"真源分域"，AI 补了"验收"，三条各自成立、合起来才完整〕

### 二、为什么「架构」在这条路上更依赖验证

这一点我想说得更准一些。

**不是「架构本质上是天赋」**，而是〔AI 拧准：原说法见下，这是第二次拧准〕：

> **在这个人的处境下，架构判断的失误率更高 —— 所以它比常人更依赖外部验证。**

> 作者原来的说法是：「架构首先是**天赋性**的东西，其次才是经验性的」  
> 〔作者说：他描述的是自己的实际处境，不是一条普遍规律〕。  
> 第一次拧准把它改成了「在这个处境下，只有天赋能撑起架构」。
> 但那个版本**仍然把能力缺口叫成了天赋** —— 而给一个缺口换个好听的名字，
> 并不等于把它变成优势。所以**第二次连"天赋"一起去掉**，只留下它的实际后果。

理由是一条链：

1. 他必须懂业务 ⇒ 精力被业务占掉一大块；
2. 一个人的成长是有限的 ⇒ 他的**代码经验必然受限**；
3. 而架构判断的可靠度，本来**主要来自大量代码经验的归纳**（见过得多，才知道哪条路容易塌）；
4. 经验那条被削弱 ⇒ **他不能靠"我见得多，所以我知道"来下判断** ——  
   只能**先做一小块出来，看它跑不跑得通**。

换个处境（比如写了十年代码的人），架构判断的把握可以更高、需要的验证更少。  
**这是成本差异，不是高下之分。**

**那这种处境下，判断力长什么样？** 一个可观察的定义：

> **在看不清全貌的时候，能提出一个「值得试一下」的方向，然后动手去试。**  
> 〔作者说：经验那条路被削弱之后，他实际就是靠"试了才知道"往前走的〕

关键词是「**在看不清全貌的时候**」—— 能看清全貌的，那叫规划，不叫判断。

★ 但必须补一句，否则这节会被读成"凭感觉也行"：
**「值得试」不等于「是对的」。** 这条路走得通，不是因为直觉准，
而是因为**试的成本被压得很低**（能快速验证、能安全地改、错了就回滚）——
**是验证兜住了判断的误差。** 这跟"凭感觉拍板"是两回事。

### 三、真正的核心特质：**会提问**

**AI 不缺答案，缺的是「值得回答的问题」。**

还记得早期搜索引擎最怕什么吗 —— **「我也不知道我要找什么」**。  
结果就是牛头不对马嘴。很多人把这段经验顺延下来，认定「AI 不过是更强的搜索引擎」。  
于是现在分成两种**都不健康**的用法：

| 分支          | 表现               | 结果               |
| ----------- | ---------------- | ---------------- |
| **当超强搜索引擎** | 只让 AI 写代码，人忙着抠细节 | 变成 **AI 反问他**    |
| **完全躺平**    | 什么都交给 AI         | 双方大部分时间**对不上频道** |

两者都缺同一样东西：**人对 AI 的反问**。

健康的形态是**双向反问**，缺一不可：

- **人反问 AI**：你凭什么这么说？如果 X 变了会怎样？你怎么知道它是对的？
- **AI 反问人**：你要的到底是哪个结果？在什么前提下？

#### 什么样的提问才算「好」

一个实用的判据 —— **好的提问会逼出「可证伪的期待」**  
〔AI 说：因为"能不能被验证"是提问质量唯一的硬指标，其余都是感觉〕：

| ✗ 弱的提问     | ✓ 强的提问                |
| ---------- | --------------------- |
| 「你觉得该怎么做？」 | 「我认为应该是 X，**你去验证**」   |
| 「这个能优化吗？」  | 「**改完之后我该看到什么变化**？」   |
| 「有没有问题？」   | 「**如果输入翻倍**，它会在哪里先断？」 |

差别在于：**弱提问拿到答案就停了；强提问会换来下一个更具体的问题。**

这也解释了一件事 —— 为什么「提问能力」直接决定 0 号 AI 的**成长质量**  
〔作者说：他关心的从来不是"活有没有干完"，而是"AI 有没有在长"〕：

- 提问若**解决后能沉淀**（变成一条检查器 / 准则 / 技能）⇒ 它在**长**；
- 提问若只是「帮我把这个做掉」⇒ 它只是在**干活**，没有在长。

> 一句话：**能被固化的提问，才是在培养 AI；不能被固化的提问，只是在使用 AI。**  
> 〔AI 说：把上面那段收成一条能直接拿来判的尺子〕

#### ★ 但真正挡住人的，不是「不会」，是「不敢」

这一条来自真实使用反馈 —— 大家最怕的**不是"我想不出来"，而是"我说不清楚"**  
〔作者说：这是同事用下来的反馈，不是推演出来的〕。

> 担心自己表述有偏差 ⇒ 担心 AI 理解歪了 ⇒ 做不到预想的结果。

于是行为变形：要么**拼命把话说精确**（等于自己把问题全想完了），  
要么**干脆不用**。这正是前文第三个分支的成因。

**方向是错的**，因为：

| 人们误以为            | 实际是             |
| ---------------- | --------------- |
| 「精确」靠**一次说清楚**达到 | 「精确」靠**来回澄清**收敛 |
| 说错会被记下来          | 说错只是**下一轮的输入**  |
| 该先想好再开口          | 开口本身就是**想的工具**  |

而最要命的是：**它掐住的正好是输入端** —— 这套体系里**人唯一不可替代的那一环**。  
（AI 能补执行、能补代码，补不了"你到底想要什么"。）

**四条解法 —— 都是降低「说错」的成本**  
〔对撞出：问题由作者从反馈里提出来，四条解法是 AI 顺着"降低说错成本"这个方向展开的〕：

| 做法                            | 效果                   |
| ----------------------------- | -------------------- |
| **让它先复述**：「动手前先说"我理解的是……对吗？"」 | 把偏差**提前暴露**，而不是藏在结果里 |
| **允许含糊**：「我大概想要 X，但我不确定」      | 含糊是**合法输入**，不是失职     |
| **让它指出你的含糊**：「我哪里说得不清楚？」      | 把"揣摩"变成"提问"          |
| ★ **先做小的、可验证的一步**             | **用"看结果"替代"说清楚"**    |

> 最后一条最关键：**原型比语言更擅长对齐意图。**  
> 如果一个人说不清楚，那就**先给他看一个小的** —— 他看完了，往往就说得清了。

#### 它同时闭合了「天马行空 × 执行力」这个分工

> 分工（人出天马行空、AI 出执行力）由**作者**提出〔作者说：他用一句话点明了双方各自不可替代的那一半〕；  
> 「**说不清 → 先给小产物 → 就说得清了**」这个闭环由 **AI** 接上〔AI 说：接上它，这个分工才算闭合，否则只是一句口号〕。

```
   人的天马行空          先做一个小产物          看见了，就说清了          放大
  （本来就说不清）  →    （AI 执行）        →   （对齐意图）        →   （AI 执行）
        ↑                                                                  │
        └──────────────────  看得越多，想法越具体  ────────────────────────┘
```

**「说不清」不是缺陷** —— 说得清就不叫天马行空了。

所以系统必须**接受含糊输入**；否则它天然筛掉的，正是**最有价值的那部分输入**。

### 四、所以到底去哪找

- **不需要「很多」** —— 0 号 AI 只需要**一个**；
- **也不需要「很高」** —— 需要的是那个**组合**。它不要求职位，只要求**视角**；  
  一个离业务很近的小团队负责人，可能比一个离业务很远的技术专家更合适。
- 但要诚实：**如果一个人都找不到，这个命题就不成立。**  
  这是它的**前提**，不是它的结论。

→ 完整的机制（0 号 AI 怎么产生、怎么克隆、服务谁）见 [**0 号 AI**](docs/zero-agent.md)。

## 主线：一条成长路径

> **0 号 AI 不可能从单机长成参天大树。**  
> 〔作者说：因为单机阶段的一切假设都是猜的，只有真实业务能证伪它们〕
>
> 下面这个顺序**不是设计出来的，是被真实环境逼出来的** —— 每一步都有它的代价。  
> 〔AI 说：这是回头整理时发现的规律，不是事前画好的路线图〕

### ① 起步 · 怎么开始带

| 主题              | 要点                                 |
| --------------- | ---------------------------------- |
| **强弱提问**        | 强提问逼出「可证伪的期待」；**能被固化的提问，才是在培养 AI** |
| **自迭代中的护栏**     | 让它自查、找漏洞 —— 但每个护栏必须**能证明它会红**      |
| **在约束中走完一条业务流** | 先给**边界清晰**的完整流程，而不是零碎片段（片段学不到系统）   |
| **在失败里成长**      | 撞坑 → **复盘根因** → 固化成机制（不是「下次注意」）    |

→ [怎么从 0 带出一个懂业务的 agent](docs/raising-an-agent.md)

### ② 冲击 · 流入真实业务

> **单机阶段的一切假设都是猜的** —— 并发、权限、人的不确定性。

只有雏形**在真实业务与使用中碰壁**，才知道：

- **系统设计**哪里有问题（原本以为不会打架的地方，在打架）；
- **业务理解**哪里有问题（原本以为理解对了，其实没有）。

⇒ **碰壁不是失败，是唯一的校准方式。**  
〔作者说：没被现实顶回来的那一刻，你根本不知道哪个假设是错的〕

→ [集群开发的三块基建](docs/distribution-and-approval.md)

### ③ 漂移 · 版本与高频迭代

> **漂移是不可避免的。** 高频迭代 = 高频漂移 —— 不存在「迭代快、还不漂」的方案。

| 漂移形态          | 防法            |
| ------------- | ------------- |
| 判据散落两处，改一处漏一处 | **单一真源**      |
| 文档与代码对不上      | **提交前自检**     |
| 改了行为，别人却不知道   | **行为等价性验证**   |
| 旧版本累积、越滚越乱    | **只增不删 + 留档** |

→ [漂移：为什么"改得快"就必然"漂得快"](docs/drift.md)（四种形态 + 四种防法）

### ④ 效率 · 业务技能成型之后

技能成型 ⇒ 任务变多 ⇒ **并发**变成主要矛盾。但粗暴互斥会把吞吐拖死：

| 问题             | 解             |
| -------------- | ------------- |
| 不相干的任务互相排队     | 锁**按资源分片**    |
| 「进程活着」被当成「在干活」 | **持有方心跳**     |
| 重跑导致重复副作用      | **幂等 + 断点续跑** |

→ [`reslock`](zeroagent/reslock.py) · [`checkpoint`](zeroagent/checkpoint.py) · [编排层](docs/orchestration.md)

### ⑤ 认知漂移 · AI 的「实现」 vs 人的「意图」

最隐蔽的一类，也最该防。

> AI 理解一个功能，是在**实现层**（代码怎么写）；  
> 人理解一个功能，是在**意图层**（为什么要有它、它服务于什么）。
>
> **两者会在交流中漂移** —— 双方都以为对齐了，其实没有。  
> 〔作者说：因为两边根本不在同一个坐标系，一个看"怎么写"，一个看"为什么要有"〕

这和前面「不敢说」那节是**同一个病根的两面**  
〔对撞出：两条线索接上之后才发现，断的都是"意图传递"这一环〕：  
**意图的传递是脆弱的。**

**防法三件套**：

| 环节       | 做法                                    |
| -------- | ------------------------------------- |
| **怎么发现** | ★ **红绿验证** —— 把「我以为你懂了」变成一个**能变红的用例** |
| **怎么解决** | 回到**单一真源** —— 意图只能有一处定义               |
| **怎么验证** | **独立复核** + **逆向验证**（真的变了吗）            |

> 「红绿验证」和前面「原型比语言更擅长对齐意图」是同一招：  
> **不要用语言对齐，用一个会变色的东西对齐。**

→ [认知漂移](docs/cognitive-drift.md)（含「真源要分域」）· [与 AI 协作的工程护栏](docs/ai-collaboration.md)

## 先说一个词：fail-closed

下面这9 个工具，全都建立在同一个原则上 —— 先把这个词说清。

**fail-closed = 拿不准的时候，默认「不放行」。**

| 出了岔子的场景 | fail-open（默认放行） | **fail-closed（默认拦下）** |
|---|---|---|
| 检查器自己挂了 | 当作「通过」 | 当作「**不通过**」 |
| 读不出配置 | 用默认值继续跑 | **停下**，报错 |
| 判断不了 | 蒙一个 | 明确报「**判不了**」 |

一句话：**「我不知道」绝不允许被当成「没问题」。**

它的反面，就是本仓库要治的病 —— **静默失败**：

> **没报错，但结果是错的。**
> 崩溃会喊，它不会；等你发现的时候，往往已经晚了。

所以这9 个工具的一致取向是：**宁可不跑、宁可多跑、宁可停下，
也不要给出一个看起来正常的错结果。**

## 9 个工具

> ★ **别把它们当成 9 个互不相干的检查器** —— 它们是一条流水线的九个工位。
> **怎么串、什么时候叫谁** ⇒ [这 9 个工具是怎么串起来的](docs/toolchain.md)。


每个工具堵一种**静默失败** —— 也就是前面说的「**没报错，但结果是错的**」。

| 工具                                             | 防的是哪种静默失败                   |
| ---------------------------------------------- | --------------------------- |
| [`redact`](zeroagent/redact.py)               | 脱敏**漏了一处** —— 报告看着干净，其实真值还在 |
| [`checkgate`](zeroagent/checkgate.py)         | 自检**没跑**却报「通过」 —— 假绿        |
| [`reslock`](zeroagent/reslock.py)             | 任务**早干完了，锁还占着** —— 假占用      |
| [`contextbudget`](zeroagent/contextbudget.py) | 笔记**超限被截断** —— 尾部的规则悄悄失效    |
| [`approvalgate`](zeroagent/approvalgate.py)   | 危险操作**被静默放行** —— 审批被绕过      |
| [`checkpoint`](zeroagent/checkpoint.py)       | **重跑**导致重复副作用 / 跳步时用了过时输入   |
| [`feedback`](zeroagent/feedback.py)           | **两个实例对同一件事判断不一致，却没人发现** —— 克隆了代码、没克隆判断 |
| [`doccheck`](zeroagent/doccheck.py)           | 文档**引用断了却没人喊** —— 死链、坏锚点、**写死的数字过期** |
| [`clonecheck`](zeroagent/clonecheck.py)       | 「**空白机器还能不能做对**」只活在文档里 —— 判据从没被执行 |

> 每个都**自带自测**，且自测里包含「**注入一个坏场景 ⇒ 它确实报红**」。  
> 一个永远通过的检查器，比没有更糟 —— 它给你虚假的安全感。

### `redact` — 脱敏 + 残留自检

只做替换的工具**没法告诉你它漏了**。所以这里把两步绑死：

```
替换 ──► 独立再扫一遍 ──► 有残留就抛错、不产出
```

精确词典（不靠正则猜）· **长值优先**（防短值吃掉长值）· 词典外的值用上下文规则兜底。

### `checkgate` — 检查器注册表 + 运行闸门

把「有哪几项检查 / 失败算阻塞还是警告 / 显示什么文案」收口到**一个 JSON**，  
加一项检查只改一处。四条 fail-closed：

注册表读不出 ⇒ **阻塞** · 没声明 level ⇒ **阻塞** · **超时 ⇒ 阻塞** · 脚本缺失 ⇒ 明说「没检查」

> 第 3 条是关键：**「判不了」不允许冒充「通过」。**

### `reslock` — 按资源分片的文件锁

不相干的资源**不互相排队**（分片）；任务干完了但进程还留着时，  
靠**持有方心跳**让等待方接管（防假占用）。

> ★ 踩过的坑：Windows 上 `os.kill(pid, 0)` 会**真的把进程杀掉**（Python 文档：非 `CTRL_*` 信号一律  
> `TerminateProcess`）⇒ 走 `OpenProcess + GetExitCodeProcess`。

### `contextbudget` — 上下文预算守卫

笔记 / 记忆 / 指令文件超限后会被**按字符静默截断**，尾部的约束悄悄消失、不报错。  
本工具量水位并预警：`ok / near / over`（接近线默认 90%），**只读不写**。

### `approvalgate` — 审批闸门

有副作用的操作必须有人批，且**不能自己批自己**：

只有 `approved` 放行 · **申请人 == 审批人 ⇒ 拒绝 + 记审计** · 同人同内容**幂等** · 全程留痕

### `checkpoint` — 幂等 + 断点续跑

任务中断后重跑，**要么重复副作用、要么跳错步** —— 两种错都不报错。  
这里用「**key + 输入指纹**」判断"这步做过没有"：输入一变就视为未完成；  
进度文件坏掉 ⇒ **全部重跑**（宁可多跑，绝不跳错）。

## 它是怎么被写出来的

这份 README **不是**「我写完给 AI 润色」，**也不是**「AI 写完我挂名」。  
它是**来回对撞**出来的 —— 下面把账摆开。

### 一、观点归属（节选）


| 观点 | 归属 | 他／它为什么要这么说 |
|---|---|---|
| 懂业务的第一理由是**红线** | 〔作者〕 | 他在业务里最先撞见的是"越界"，而那个代价不可逆 |
| **验收标准**同样是硬需求 | 〔AI 补〕 | 只防越界，这个人就只是个守门人；命题需要的是出题人 |
| **业务上的「对」只有人能定义**（真源要分域） | 〔作者〕 | 他从"模型自带经验"里看到了这条边界在哪 |
| 「提问能力」直接决定 AI 的成长质量 | 〔作者〕 | 他要的不是"活干完"，是"AI 有没有在长" |
| 「强弱提问」的判据 = 能否逼出「可证伪的期待」 | 〔AI〕 | 因为"能不能被验证"是提问质量唯一的硬指标 |
| **架构是天赋**这条命题 | 〔作者〕（后经两次拧准，见上文） | 他描述的是自己的处境：精力被业务占掉，经验那条路走不通 |
| 把它拧准为「**在这条路径下**」 | 〔AI 拧准〕 | 否则会被读成本质断言，误伤"靠经验走到架构"的那批人 |
| 「**不敢说**」是输入端的结构性问题 | 〔作者〕 | 这是同事用下来的真实反馈，不是推演 |
| 「**天马行空 × 执行力**」这个分工 | 〔作者〕 | 他用一句话点明了双方各自不可替代的那一半 |
| 「说不清 → 小产物 → 就说得清了」这个闭环 | 〔AI 接上〕 | 接上它，那个分工才算闭合，否则只是一句口号 |
| 五阶段成长路径的**大纲** | 〔作者〕 | 因为那是他自己一步一步走过来的顺序 |
| 「**碰壁不是失败，是唯一的校准方式**」 | 〔作者〕 | 单机阶段的假设全是猜的，只有现实能证伪 |
| ⑤**认知漂移**：「实现层」vs「意图层」 | 〔作者〕 | 他观察到 AI coding 与实际业务意图会在交流中分岔 |

### 二、★ 三个「对撞」产物 —— 谁都没单独想到

| 结论 | 怎么来的 |
|---|---|
| **懂业务 = 既知道不能碰什么，也知道什么才算对** | 作者给「红线」与「真源分域」，AI 补「验收」 ⇒ 三条合起来才完整 |
| **「红绿验证」= 「原型 > 语言」** | 作者给「认知漂移」，AI 接上「不敢说」 ⇒ 发现解法是**同一招** |
| **⑤ 与「不敢说」是同一个病根的两面** | 同上 —— 两条线索接上，才知道是一个病 |

> 这三条**不是分工，是对撞**：拆开看，谁都没想到完整的那个结论。

### 三、★ 互相否掉过的 —— 这才是双向验证的硬证据

| 谁否谁 | 内容 | 为什么否 |
|---|---|---|
| 〔作者〕否〔AI〕 | AI 加的「30 秒速览」表 | 机械表格**会盖掉主题**，让人读不到论证 |
| 〔作者〕否〔AI〕 | AI 把「快速开始」放开头 | 那是**另一套内容的残留**，打断了从话题到论证的推进 |
| 〔AI〕否〔作者〕 | 「架构是**天赋性**的东西」 | 会把**路径问题说成生死问题**，误伤经验派 |
| 〔AI〕否〔作者〕 | 「**CEO 级**」的类比 | 分量过重会把自己吓住 —— 实际既不需要"很多"也不需要"很高" |
| 〔作者〕自认 | 「我表达的**太过急切**」 | 并认可「靠经验走到架构」也是一条路 |

### 四、这张表说明了什么

- **不是分工，是对撞** —— 三处〔对撞〕**谁都没单独想到**；
- **否决是双向的** —— 作者否了 AI 两次，AI 也否了作者两次；**「AI 服从人」不成立**；
- ⇒ 这正是[人机共同进化](docs/human-agent-coevolution.md) 说的「**双向成长**」：
  如果只有单向，上面这些里**一条都不会发生**。

## 从哪来

这些工具与经验，来自一套**生产级自动化系统**（已泛化，无业务细节）：

- 面向**多个外部 Web 平台**的数据采集与合规自动化；
- 数十个租户、几十个自动化任务、多台机器、**无人值守**定时运行；
- 四层结构「调度 → 执行 → 守卫 → 数据」，守卫层负责并发、脱敏、发布前自检；
- 能力**分发给多名使用者**，带审批闸门与分级权限。

| 指标 | 值 |
|---|---|
| 发布前一致性检查器 | 14 项（注册表驱动，加一项只改一处） |
| 自动化脚本 / 复用单元 | 80+ / 30+ |
| 批处理性能 | 150 个目标：**352s → 69s**（约 5×） |
| 静默失败 | 六类各有守卫 + 回归用例 |

> ⚠ **上面这些数字，在本仓库里复现不了** —— 它们来自主系统的内部统计（主系统代码不公开）。
> **本仓库能独立验证的只有四项**，而且跑一遍就知道真假：
> **9 个模块 · 42 项单测 · 108 项自测 · 9 个可跑示例**（见 [快速开始](#快速开始)）。
>
> 挑明这条界线的理由很简单：**一个作品集里，可复现的数字和不可复现的数字，分量不一样。**

> ★ **主系统代码不公开**：含客户数据与商业流程，合规上不可外发。
> 本仓库只放**与业务无关**的通用部分；
> 完整的逐日工作记录另有脱敏存档，**面试时可提供**。
