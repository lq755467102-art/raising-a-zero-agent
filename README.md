# failclosed-toolkit

> 一个人 + 一个 agent，从零做出一套无人值守的系统；  
> 顺手把「怎么让系统不出静默错」沉淀成了工具与方法论。

`零依赖` · `纯标准库` · `Python 3.8+` · `34 项单测 + 67 项自测`

---

## 这是什么

一句话：**懂业务的人和懂代码的人，大概率是两拨人 —— 而且各自都没时间跨过去。**

这套东西记录的是：怎么由**一个人**把两层能力**一起**灌注给一个 AI，  
再让它**可移植地**去服务这两拨人。

| 层      | 是什么                                                                  | 能复制吗        |
| ------ | -------------------------------------------------------------------- | ----------- |
| **表面** | **六个小工具** —— 让自动化 / AI 协作 / 多人协作不「静默出错」                              | ✅ 直接拿去用     |
| **中间** | **方法论** —— 换一个场景该怎么办                                                 | ✅ 换个领域也能套   |
| **主线** | ★ [**0 号 AI**](docs/zero-agent.md) —— 怎么从 0 带出一个同时懂业务与工程的 AI，再克隆出去   | ⚠ **稀缺在这里** |
| **终局** | [人机共同进化](docs/human-agent-coevolution.md) —— 人和 AI 一起，做"谁都还没描述清楚的东西" | 设想          |

> 这就是为什么仓库里既有**能跑的代码**，又有一堆"**不像代码**"的东西 ——  
> 它们本来就是同一件事的不同层面。

## 怎么从 0？

问题很自然：**既然要一个「双懂」的人，这种人去哪找？**

先把它拆开 —— 这样的人需要**多大**的能力？需要**什么形状**的能力？

我的答案有点反直觉：

> **不需要「很大」，需要的是「很少见的一种组合」；
> 不需要「什么都会」，只需要三样。**

### 一、为什么「懂业务」是硬需求

最直接的理由是**红线**：只有懂业务的人，才能判断 AI **什么时候正在越过业务边界**，
并且在**越界之前**把规矩立好。

> 事后再补救，等你的**往往不是一个问题，而是一串问题** ——
> 因为 AI 已经把错的做法执行了很多遍。

但我想补一条同样硬的：**验收标准**。

| | 频率 | 后果 |
|---|---|---|
| **红线**（不能碰什么） | 低频 | **致命** |
| **验收**（什么才算对） | **高频** | 决定成败 |

AI 能做出很多东西，但只有懂业务的人能回答「**这是不是我们要的**」。

⇒ **懂业务 = 既知道「不能碰什么」，也知道「什么才算对」。**

### 二、为什么「架构」在这条路上更像天赋

这一点我想说得更准一些。

**不是「架构本质上是天赋」**，而是：

> **在这个人的处境下，只有天赋能撑起架构。**

理由是一条链：

1. 他必须懂业务 ⇒ 精力被业务占掉一大块；
2. 一个人的成长是有限的 ⇒ 他的**代码经验必然受限**；
3. 而架构能力本来有**两条来源** —— **从大量代码经验里归纳**（慢、可复制），
   和**从对问题的敏感里直觉得到**（快、但不可教）；
4. 经验那条被堵住 ⇒ 他**只能**走直觉那条。

换个处境（比如写了十年代码的人），架构完全可以靠经验积累出来。
**这两条是不同路径，不是高下之分。**

**那这个天赋长什么样？** 一个可观察的定义：

> **在看不清全貌的时候，敏锐地感觉到「什么对这套系统有用」，然后动手去试。**

关键词是「**在看不清全貌的时候**」—— 能看清全貌的，那叫规划，不叫天赋。

### 三、真正的核心特质：**会提问**

**AI 不缺答案，缺的是「值得回答的问题」。**

还记得早期搜索引擎最怕什么吗 —— **「我也不知道我要找什么」**。
结果就是牛头不对马嘴。很多人把这段经验顺延下来，认定「AI 不过是更强的搜索引擎」。
于是现在分成两种**都不健康**的用法：

| 分支 | 表现 | 结果 |
|---|---|---|
| **当超强搜索引擎** | 只让 AI 写代码，人忙着抠细节 | 变成 **AI 反问他** |
| **完全躺平** | 什么都交给 AI | 双方大部分时间**对不上频道** |

两者都缺同一样东西：**人对 AI 的反问**。

健康的形态是**双向反问**，缺一不可：

- **人反问 AI**：你凭什么这么说？如果 X 变了会怎样？你怎么知道它是对的？
- **AI 反问人**：你要的到底是哪个结果？在什么前提下？

#### 什么样的提问才算「好」

一个实用的判据 —— **好的提问会逼出「可证伪的期待」**：

| ✗ 弱的提问 | ✓ 强的提问 |
|---|---|
| 「你觉得该怎么做？」 | 「我认为应该是 X，**你去验证**」 |
| 「这个能优化吗？」 | 「**改完之后我该看到什么变化**？」 |
| 「有没有问题？」 | 「**如果输入翻倍**，它会在哪里先断？」 |

差别在于：**弱提问拿到答案就停了；强提问会换来下一个更具体的问题。**

这也解释了一件事 —— 为什么「提问能力」直接决定 0 号 AI 的**成长质量**：

- 提问若**解决后能沉淀**（变成一条检查器 / 准则 / 技能）⇒ 它在**长**；
- 提问若只是「帮我把这个做掉」⇒ 它只是在**干活**，没有在长。

> 一句话：**能被固化的提问，才是在培养 AI；不能被固化的提问，只是在使用 AI。**

### 四、所以到底去哪找

- **不需要「很多」** —— 0 号 AI 只需要**一个**；
- **也不需要「很高」** —— 需要的是那个**组合**。它不要求职位，只要求**视角**；
  一个离业务很近的小团队负责人，可能比一个离业务很远的技术专家更合适。
- 但要诚实：**如果一个人都找不到，这个命题就不成立。**
  这是它的**前提**，不是它的结论。

→ 完整的机制（0 号 AI 怎么产生、怎么克隆、服务谁）见 [**0 号 AI**](docs/zero-agent.md)。

## 六个工具

前提：**静默失败 = 没报错，但结果是错的。** 它比崩溃难缠得多 —— 崩溃会喊，它不会。

| 工具                                             | 防的是哪种静默失败                   |
| ---------------------------------------------- | --------------------------- |
| [`redact`](failclosed/redact.py)               | 脱敏**漏了一处** —— 报告看着干净，其实真值还在 |
| [`checkgate`](failclosed/checkgate.py)         | 自检**没跑**却报「通过」 —— 假绿        |
| [`reslock`](failclosed/reslock.py)             | 任务**早干完了，锁还占着** —— 假占用      |
| [`contextbudget`](failclosed/contextbudget.py) | 笔记**超限被截断** —— 尾部的规则悄悄失效    |
| [`approvalgate`](failclosed/approvalgate.py)   | 危险操作**被静默放行** —— 审批被绕过      |
| [`checkpoint`](failclosed/checkpoint.py)       | **重跑**导致重复副作用 / 跳步时用了过时输入   |

> 每个都**自带自测**，且自测里包含「**注入一个坏场景 ⇒ 它确实报红**」。  
> 一个永远通过的检查器，比没有更糟 —— 它给你虚假的安全感。

### `redact` — 脱敏 + 残留自检

只做替换的工具**没法告诉你它漏了**。所以这里把两步绑死：

```
替换 ──► 独立再扫一遍 ──► 有残留就抛错、不产出
```

精确词典（不靠正则猜）· **长值优先**（防短值吃掉长值）· 词典外的值用上下文规则兜底。

### `checkgate` — 检查器注册表 + 运行闸门

把「有哪几项检查 / 失败算阻塞还是警告 / 显示什么文案」收口到**一个 JSON**，  
加一项检查只改一处。四条 fail-closed：

注册表读不出 ⇒ **阻塞** · 没声明 level ⇒ **阻塞** · **超时 ⇒ 阻塞** · 脚本缺失 ⇒ 明说「没检查」

> 第 3 条是关键：**「判不了」不允许冒充「通过」。**

### `reslock` — 按资源分片的文件锁

不相干的资源**不互相排队**（分片）；任务干完了但进程还留着时，  
靠**持有方心跳**让等待方接管（防假占用）。

> ★ 踩过的坑：Windows 上 `os.kill(pid, 0)` 会**真的把进程杀掉**（Python 文档：非 `CTRL_*` 信号一律  
> `TerminateProcess`）⇒ 走 `OpenProcess + GetExitCodeProcess`。

### `contextbudget` — 上下文预算守卫

笔记 / 记忆 / 指令文件超限后会被**按字符静默截断**，尾部的约束悄悄消失、不报错。  
本工具量水位并预警：`ok / near / over`（接近线默认 90%），**只读不写**。

### `approvalgate` — 审批闸门

有副作用的操作必须有人批，且**不能自己批自己**：

只有 `approved` 放行 · **申请人 == 审批人 ⇒ 拒绝 + 记审计** · 同人同内容**幂等** · 全程留痕

### `checkpoint` — 幂等 + 断点续跑

任务中断后重跑，**要么重复副作用、要么跳错步** —— 两种错都不报错。  
这里用「**key + 输入指纹**」判断"这步做过没有"：输入一变就视为未完成；  
进度文件坏掉 ⇒ **全部重跑**（宁可多跑，绝不跳错）。

## 快速开始

```bash
# 34 项单元测试
python -m unittest discover -s tests -v

# 六个可跑示例（带 ⇒ 的两个刻意以退出码 1 收尾，证明它真的会拦）
python examples/redact_demo.py                  # 脱敏 + 残留自检
python examples/reslock_demo.py                 # 分片锁 + 心跳
python examples/checkpoint_demo.py              # 幂等 + 断点续跑
python examples/checkgate_demo/run.py           # ⇒ 有阻塞项 ⇒ 不放行
python examples/contextbudget_demo.py           # ⇒ 有文件超线
python examples/approvalgate_demo.py            # 审批闸门（防自批）
```

`checkgate` 的输出长这样：

```
═══ 检查闸门（fail-closed）═══
✓ 文档索引一致
✗ 有文档指向不存在的文件
    ✗ 有 2 处文档链接失效
⚠ 本机环境有缺口（不阻塞，但需显形）

判定：通过 1 / 警告 1 / 阻塞 1
```

## 方法论

工具解决具体问题；方法论解&#x51B3;**「换一个场景该怎么办」**。  
按三组看：**主线**（怎么带出 0 号 AI）→ **终局**（设想）→ **专题**（换场景怎么办）。

### [0 号 AI：从一个人，到一台能服务两类人的机器](docs/zero-agent.md) —— ★ 主线 · 主张

懂业务的人和懂代码的人大概率是两拨人，各自都没时间跨过去 ⇒  
由**一个双懂的人**把两层能力**一起**灌注给 **0 号 AI**，再**克隆**出去。  
含：为什么「空白机器 + 代码小白」才是主流 · 三步产生 · 克隆为什么有用 · 服务两类人。

### [怎么从 0 带出一个「懂业务」的 agent](docs/raising-an-agent.md) —— ★ 主线 · 流程

先立约束再给任务 · 教它**怀疑自己**而不是听话 · 用真实事故教 ·  
把经验**固化成机制** · 给它判断权 · 主动索要质疑。

### [人机共同进化](docs/human-agent-coevolution.md) —— 终局 · 设想

人和 AI 一起做一样**一开始谁也不知道会变成什么**的东西：  
两种协作模式 · 混沌是特征不是缺陷 · 天马行空 × 执行力 · 双向成长。

### [系统设计总览](docs/system-design.md)

分层与职责（**每层"不做什么"**）· 一次任务的完整路径 · 失败分类学 ·  
控制点地图 · 真值边界 · 人机边界 · 扩展点。

### [与 AI 协作的六条护栏](docs/ai-collaboration.md)

| 护栏              | 一句话                 |
| --------------- | ------------------- |
| **fail-closed** | 判不了 = 不通过           |
| **单一真源**        | 同一判断散落两处，就一定会静默漂移   |
| **验证独立于被测对象**   | 自己检查自己 = 没检查        |
| **护栏要真跑**       | 要能证明它「抓得住」，而不只是「通过」 |
| **上下文预算**       | 防静默截断，且接到既有必跑路径上    |
| **给 agent 写文档** | 歧义 = 静默失败           |

### [怎么安全地改一个正在跑的系统](docs/changing-safely.md)

行为等价性验证 · 破坏性操作**绝不原地改**（临时目录 → 校验 → 原子替换）·  
只增不删 + 留档 · 配置模板注入（未替换即失败）· 分片取样（**没查过 ≠ 查过了**）· 路径无关。

### [集群开发的三块基建](docs/distribution-and-approval.md)

| 需要什么                                   | 缺了会怎样           |
| -------------------------------------- | --------------- |
| 能力可分发（单一真源 → 打包 → 投递 → **幂等安装 + 可校验**） | 别人用不上，或各自版本不同   |
| 危险操作有闸门（防自批 + 幂等 + 审计）                 | 靠自觉的约束 = 没有约束   |
| **多维度定权**（主体 × 资源 × 操作，判据不可伪造）         | 要么全开、要么全关，没有中间档 |

> 合起来：**把「只有作者本人能维护」，变成「一群人都能维护，而且不会互相踩」。**

### [编排层：幂等与续跑](docs/orchestration.md)

幂等 · 断点续跑 · **输入指纹** · 原子写 · 任务状态机与心跳 · 重试的边界 · 人机边界。

## 从哪来

这些工具与经验，来自一套**生产级自动化系统**（已泛化，无业务细节）：

- 面向**多个外部 Web 平台**的数据采集与合规自动化；
- 数十个租户、几十个自动化任务、多台机器、**无人值守**定时运行；
- 四层结构「调度 → 执行 → 守卫 → 数据」，守卫层负责并发、脱敏、发布前自检；
- 能力**分发给多名使用者**，带审批闸门与分级权限。

| 指标           | 值                            |
| ------------ | ---------------------------- |
| 发布前一致性检查器    | 14 项（注册表驱动，加一项只改一处）          |
| 自动化脚本 / 复用单元 | 80+ / 30+                    |
| 批处理性能        | 150 个目标：**352s → 69s**（约 5×） |
| 静默失败         | 六类各有守卫 + 回归用例                |

> ★ **主系统代码不公开**：含客户数据与商业流程，合规上不可外发。  
> 本仓库只放**与业务无关**的通用部分；  
> 完整的逐日工作记录另有脱敏存档，**面试时可提供**。
