# Case Study：让无人值守的自动化「不静默出错」

> 一份关于 **fail-closed 设计**的实践记录。
> 内容已泛化：不含客户、平台或业务细节；只保留**结构、判断与踩坑**。

---

## 0. 一句话

我维护了一套**无人值守**的多平台自动化系统。它最大的风险不是崩，而是
**没崩、也没报错，但结果是错的**。这篇记录三类这样的失败，以及我为它们做的三件设计。

---

## 1. 背景

| 维度 | 情况 |
|---|---|
| 形态 | 面向多个外部 Web 平台的数据采集 + 合规操作，浏览器自动化驱动 |
| 规模 | 数十个租户；80+ 脚本、30+ 复用单元；多台机器 |
| 运行方式 | **无人值守** —— 定时触发，出事时人不在场 |
| 关键约束 | 数据敏感，**产出物不得含真值**；错一次代价很高 |

「无人值守」把容错的标尺整个抬高了：**没有人会在旁边发现异常**。
系统必须自己保证「**没把握的时候，宁可停下，也不假装成功**」——这就是 fail-closed。

---

## 2. 三类静默失败（都是真实撞见过的）

### 失败一：脱敏「漏一处」

导出产物的脱敏，最初就是「拿到真值列表 → 逐个替换」。
问题是：**这个工具没法告诉你它漏了。**

> 真实案例：一次人工复查时发现，某条日志里写着「实测通过（账号 10000001）」——
> 这个账号**不在**本机配置里，所以脱敏词典根本没覆盖它。
> 替换逻辑「成功」了，产物「看起来」是干净的。

**根因**：词典只覆盖**已知**的值；而文档里可能引用**别的**同类值。
**替换成功 ≠ 干净**。

### 失败二：自检「没跑却报通过」（假绿）

推送前有一道自检闸门。早期它把判据**手写在两处**：运行脚本里一份，健康看板里一份。
加一项检查要改两处，漏一处就**静默少跑**——而更糟的是判定行**无条件打印「✅ 可以推送」**。

> 真实案例：一次新加的检查器，失败分支被写成了「警告」而不是「阻塞」。
> 于是**真缺陷以「能推」的形式过去了**。退出码是 0，看起来一切正常。

**根因**：① 判据散落两处 ⇒ 静默漏跑；② 退出码 0 被当成了「全绿」。
**「没有阻塞项」≠「没有问题」。**

### 失败三：锁「假占用」

浏览器自动化任务之间要互斥。最初是一把**全局锁**：一开浏览器就抢、持到脚本结束。

> 真实案例：平台运行机制变化后，**脚本跑完、进程却留着等待会话复用** ⇒
> 业务早在 5 分钟前就完成了，锁还占着，**白占满整个 TTL（45 分钟）**。
> 后续任务全被无声堵死。

**根因**：锁的存活判据是「pid 活着 + 未超 TTL」，但**「进程活着」不代表「还在干活」**。
另外一个坑：粒度太粗——两个**不碰同一资源**的任务也被迫排队。

---

## 3. 设计与取舍

### 决定一：把「有哪几项检查」做成**单一真源**的注册表

**做法**：所有一致性检查及其「红/黄」「显示文案」收口到一个 JSON（`check-levels.json`）。
运行脚本和健康看板**都读它**，不再各自硬编码。加一项检查 = 只改一处。

**判据原则**：失败 = 「**要推上去的东西本身有问题**」⇒ 阻塞；
失败 = 「**本机环境 / 远端状态**」⇒ 警告（显形，但不阻塞）。

**但数据化引入了新风险**（这是最关键的一段）：

> 把「跑哪几项」从**硬编码**换成**读注册表**之后，原来那 13 个手写块是**被挑选过的**
> ——它们都不会挂住。数据化把这层**隐含保护**移除了：
> 谁往注册表里写一个「读 stdin / 卡在网络上」的检查器，这一步就会跟着一起挂。

**补法**：给每次调用加**单脚本超时**，且**超时按阻塞处理** ——
「判不了」绝不允许冒充「通过」，并且文案**显式**写「超时·判不了」，不冒充内容结论。

> **教训：数据化 / 抽象化会移除原先靠「人工挑选」提供的隐含保护，必须显式补回。**

### 决定二：判定行不再无条件打「✅」

**做法**：把警告条数**摆到眼前**，只有 `0 阻塞 / 0 警告` 才叫 ✅；
只要退出码 0，也明确写「**能推 ≠ 全绿**」。

### 决定三：锁从「全局互斥」改成「按资源分片 + 持有方心跳」

**分片**：先盘点所有任务实际用到的资源——发现**只有一个是真正的账号级共享资源**，
其余都自带租户标识、本不需要互斥。于是锁按资源名分片：
不同资源互不阻塞；不传资源名则退化为全局锁（**向后兼容**）。

**心跳**：持有方定期刷新 `beat`；等待方见 `beat` 过期即可接管 ——
不必等 pid 死、也不必等 TTL。真还在跑时 `beat` 一直是新的，**绝不会被误抢**。

**一个跨平台坑**（值得单独记）：

> 原实现是 Node，用 `process.kill(pid, 0)` 安全判活。
> 迁到 Python 时若照抄成 `os.kill(pid, 0)` —— **在 Windows 上会把那个进程真的杀掉**：
> Python 的 `os.kill` 对非 `CTRL_*` 信号一律走 `TerminateProcess`，`0` 也不例外。
> ⇒ 必须改用 `OpenProcess` + `GetExitCodeProcess`。

### 决定四：脱敏从「替换」升级为「替换 + 独立自检」（fail-closed）

- 词典来自**已知真值**（配置），不靠正则猜；
- **长值优先**替换（否则短值会吃掉长值的子串：`A` 先替 ⇒ `AB` 变成 `<占位>B`）；
- 补一条**兜底规则**：命中「上下文关键词 + 8 位数字」形态也替换；
- **替换完再扫一遍**，有残留就**抛错、不产出**。

## 4. 结果

| 指标 | 值 |
|---|---|
| 发布前一致性检查器 | **14 项**，注册表驱动，加一项只改一处 |
| 自动化脚本 / 复用单元 | 80+ / 30+ |
| 批处理性能 | 150 个目标：**352s → 69s（约 5×）** |
| 三类静默失败 | 各自有守卫 + **回归用例**（不是"改完就算完"） |
| 抽取出的可公开工具 | 3 个（本仓库 `failclosed/`） |

三个工具**都带自测**（内置自测 28 项 + 单元测试 18 项，共 46 项），且示例可跑 ——
其中 `checkgate` 示例刻意包含一个阻塞项，退出码为 1，用来证明闸门**真的会拦**。

---

## 5. 可迁移的判断

1. **「判不了」必须和「不通过」一样对待。**
   超时、异常、缺配置——只要没跑成，就不能算通过。否则守门人本身就是漏洞。

2. **数据化 / 抽象化会移除隐含保护，要显式补回。**
   把硬编码换成配置，顺手也把「人工挑选」的安全余量换没了。要主动想：
   *原来靠什么保证它是安全的？那个东西还在吗？*

3. **验证必须独立于被测对象。**
   脱敏的残留检查不是「再跑一遍替换」，而是**独立再扫一遍**；
   也正因如此，才抓到了词典之外的账号 ID。**自己检查自己，等于没检查。**

4. **判据要有单一真源。**
   同一个判断散落在两处，就一定会漂移，而且是静默漂移。

5. **「进程活着」≠「在干活」；「没报错」≠「没问题」。**
   这两句几乎概括了这篇记录的全部动机。

---

## 6. 局限与下一步

- `redact` 的兜底规则仍需按场景定制，不是放之四海皆准；
- `reslock` 是**单机**文件锁；跨机器需要换成分布式租约（如带过期的 KV）；
- 检查器本身的质量决定了闸门的价值 —— 闸门只能保证「**没跑成不会冒充跑通**」，
  不能保证「检查项设计得好」。
