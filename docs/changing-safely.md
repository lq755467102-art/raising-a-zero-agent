# 怎么安全地改一个**正在跑**的系统

> 前面几篇讲「怎么发现问题」；这篇讲**「怎么动手改，才不会改坏」**。
> 五条模式，都来自真实事故；每条都写清「撞到什么 / 怎么做 / 判据是什么」。

---

## 1. 行为等价性：重构时先证明「只有该变的变了」

**撞到什么**：重构之后**"看起来对"**——但某处行为已经悄悄变了，没人发现。

**怎么做**：

```
改动前 ──► 跑两遍，确认输出**逐字节一致**（先证明基线本身是稳定的）
      ──► 改
      ──► 与基线**逐行比对**：只有该变的地方变了
```

**判据**：不是「看起来对」，而是「**与基线一致**」。
如果基线本身跑两遍就不一致（有随机性），那比对没有意义 —— **要先消除随机性**，再谈等价。

> 这条把"重构"从**信仰**变成了**可以证明的事**。

---

## 2. 破坏性操作：**绝不原地改**

**撞到什么**：刷新 / 重建类脚本习惯 `rm -rf` 之后重写。
中途失败 ⇒ 数据没了；更坏的是 —— **脚本返回 0**，成了一只"成功的失败"。

**怎么做**：

```
导出 / 构建到**临时目录** ──► 校验通过 ──► **原子替换**（rename / mv）
                          └─ 校验不通过 ──► 中止，原物**一动不动**
```

**两条附加纪律**：

- 校验必须**独立于构建过程**（自己检查自己 = 没检查）；
- ★ **逆向验证**：删除 / 替换之后，**实际去看一眼它到底发生没有** ——
  不能只信退出码。有的环境下破坏性命令出现过「返回 0 却没真做」的情况。

---

## 3. 只增不删 + 留档

**撞到什么**：自动清理"顺手"把还有用的东西删了。

**怎么做**：

- 快照 / 归档**只追加**，旧版**改名留档**而不是删除；
- 删除**需要人工许可**，且先列清单、说明后果。

**代价与取舍**：这样会累积垃圾（占空间）。
**这是有意的取舍** —— 用「定期人工清理」换「**永不误删**」。
把"删除"这类不可逆动作交给**有判断力的人**，而不是交给脚本的 `if`。

---

## 4. 配置分层：模板注入，**未替换即失败**

**撞到什么**：部署副本里的 `{{占位符}}` 没被替换，跑起来是错的，**但不报错**。

**怎么做**：

```
真源配置（不入库）  ──►  模板（带占位符，入库）  ──►  注入生成部署副本
                                              └─► 生成后**检查残留占位符**，有 ⇒ 失败
```

**关键**：把"注入不完整"从**静默错误**变成**显式失败**。
另外，真源（含凭据、真实 ID）**只在本机**，模板才进仓库 —— 这是"最小暴露"的落点。

---

## 5. 成本控制：分片取样，而不是每次全量

**撞到什么**：每轮都全量核对，单次要几分钟；无人值守时会把整条流水线拖住。

**怎么做**：

- 按日 / 按批**轮换**，每轮只核对一部分；
- ★ 未核对的部分**明确标注"没查过"**，**不假装查过**。

**为什么强调后半句**：分片取样的风险是"抽样变成了漏检"。
所以真正要守的不是"查得快"，而是 —— **「把没查的当成查过的」**。
这和本文第 2、4 条，以及 [fail-closed 那篇](ai-collaboration.md) 是同一条底线。

---

## 6. 可移植性：路径无关

**撞到什么**：换台机器 / 换个目录，脚本就崩了 —— 或者更糟，**静默失明**（不崩，但什么都没找到）。

**怎么做**：

- 仓库根用**一个函数**统一解析，支持多种真实布局；
- 该函数本身加**回归检查**，防止某次重构让它退化。

**为什么单独列**：可移植性问题的坏处不在"报错"，而在**它常常不报错**。

---

## 收束：一条共同线索

这六条其实是同一句话的不同侧面：

> **「改」这件事，要么**可验证**，要么**不做**。**

| 阶段 | 要求 |
|---|---|
| 改之前 | 能证明**基线是稳定的**（跑两遍一致） |
| 改的过程 | **原子化**：要么全成，要么原物不动 |
| 改之后 | **独立复核** + 逆向验证（真的变了吗） |
| 没做的事 | **绝不冒充做了**（没查过 ≠ 查过了） |
