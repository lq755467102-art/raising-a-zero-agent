# 能力分发 · 审批闸门 · 多维度定权

> 一份关于**把「一个人做的项目」变成「一群人能一起做」**的架构经验。
> 面向的是「集群开发」的基础设施，与具体业务无关。

---

## 为什么需要这三样

一个人做项目，靠**记住**就够了：「这个别乱改」「那个要小心」。
一旦变成**多个人 + 多台机器**，就必须靠**机制** —— 否则约束会在第一次交接时失效。

要撑起「集群开发」，至少需要三件事同时成立：

| # | 需要什么 | 缺了会怎样 |
|---|---|---|
| 1 | **能力可分发** | 一个人写的东西，别人用不上；或者用上了但版本各不相同 |
| 2 | **危险操作有闸门** | 谁都能改、谁都能发 —— 靠自觉的约束等于没有约束 |
| 3 | **权限可分级** | 要么全开（危险），要么全关（没用），中间没有档位 |

本文记录这三件事的做法与踩坑。

---

## 一、能力分发：单一真源 → 打包 → 投递 → 安装

一条完整的链路，四步都有讲究：

| 步骤 | 做法 | 关键点 |
|---|---|---|
| **单一真源** | 能力单元（代码 + 说明）只在一处维护 | 别让"某台机器上的那份"变成事实上的第二真源 |
| **打包** | 确定性打包 | 同样内容 ⇒ 同样哈希，便于比对 |
| **投递** | 走一个"橱窗"分发，带说明与版本 | 使用者看到的是「这是什么、怎么用」，不是一堆文件 |
| **安装** | **幂等** + **可校验** + 旧版自动备份 | 装几次结果一样；装完能核对是否与真源一致 |

### ★ 最容易漏的一步：**校验**

安装不是"跑完就算"，而是"跑完能**证明**一致"。
没有校验的安装，会在换机器后变成一堆"看着装了、其实缺东西"的假象。

> **真实坑**：换机器后能力跑不起来，根因常常是**依赖漏登记** ——
> 能力引用的某个脚本没有跟着一起分发。于是补了一个检查器：
> **「能力引用的东西，必须都已登记分发」**，漏一个就报错。
> 这类"幽灵依赖"不会在你开发的那台机器上暴露，只会在别人机器上炸。

---

## 二、审批闸门：不能靠自觉

**撞到什么**：有副作用的操作（改配置、发布、动别人的数据）如果没人守，就会被
**静默放行**。而最隐蔽的一种绕过是 —— **申请人自己把申请批了**：
形式上"审过了"，实质上等于没审。

**怎么做**（落点：[`approvalgate.py`](../failclosed/approvalgate.py)）：

| 规则 | 为什么 |
|---|---|
| **只有 `approved` 放行**；未知状态 / 不存在 / 已驳回 ⇒ 不放行 | fail-closed：判不了就不放行 |
| **申请人 == 审批人 ⇒ 拒绝**，并**记入审计** | 防自批——形式上的分离审批，实质是绕过 |
| 同一人 + 同内容 + 仍待审 ⇒ **幂等** | 防重复排队把审批台刷爆 |
| 每次状态变更写**审计**（谁、何时、从什么到什么） | 事后能追，且"被拒绝的自批"也留痕 |

一句话：**闸门的价值不在"有流程"，而在"流程绕不过去"。**

## 三、多维度定权

**「角色」这一个维度说不清权限。** 至少需要三个维度：

| 维度 | 要回答的问题 | 例子（泛化） |
|---|---|---|
| **主体**（谁） | 是所有者 / 开发者 / 使用者？ | owner / dev / user |
| **资源**（对什么） | 哪份数据、哪个仓库、哪个空间？ | 某个只读空间 vs 某个可写空间 |
| **操作**（做什么） | 读 / 写 / 发布 / 审批？ | 能看 vs 能改 vs 能批 |

### 三条关键判断

1. **★ 判据要用「改不了的东西」。**
   身份不能靠本地标记（`git config user.email` 改一行就能冒充），
   要靠**平台事实**：能否推送受保护分支、是否是某个资源的 owner ——
   这些由**对端平台**决定，本地改不了。

2. **凭据制，而非职位制。**
   能做什么取决于**你持有哪份凭据**，不取决于你叫什么、什么职位。
   好处：授权可撤销、可过期、可最小化。

3. **复杂度倒置。**
   权限模型本身可以很复杂（矩阵、继承、例外），
   但**使用者那一端必须薄**：普通使用者只需要知道「我点这个按钮行不行」，
   不需要理解矩阵。复杂度留在**有权限、也需要理解它的那一侧**。

---

## 四、这三样合起来 = 集群开发的可能性

| 有了什么 | 于是可以做到 |
|---|---|
| 能力可分发 + 幂等安装 + 校验 | 一个人写的能力，**N 个人**立刻能用，且版本一致 |
| 审批闸门 | **多人并行贡献**，危险操作仍有人守 |
| 多维度定权 | **非技术同事也能安全参与**（只读 / 只申请，不碰写） |
| 单一真源 | 多人多机**不会各自漂移** |

一句话总结：

> **把「只有作者本人能维护」，变成「一群人都能维护，而且不会互相踩」。**

---

## 五、诚实的边界

- 这三件事**互相依赖**：缺任何一件，另外两件都会**退化成形式**
  （能分发但没审批 ⇒ 谁都能发；有审批但没分级 ⇒ 人人都是审批人）。
- **审批的价值取决于"审批人真的会看"** —— 工具只能保证金流程不被绕过，
  **不能**保证判断质量。
- 多机部署的复杂度是真实的：**先把单机做扎实**，再谈分发。
  过早追求"集群"会得到一个谁都不敢改的系统。
