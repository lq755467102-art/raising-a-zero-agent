# 漂移：为什么"改得快"就必然"漂得快"

> 这一篇讲**系统层**的漂移 —— 判据、文档、行为、版本。
> **人机之间的认知漂移**是另一回事，见 [认知漂移](cognitive-drift.md)。

## 一、漂移躲不掉

**高频迭代 = 高频漂移。**

只要东西在改，就有**好几处**需要跟着改：判据、文档、别人脑子里的印象、已经发出去的版本。
而"跟着改"这件事，**一定会漏**。

> 所以正确的目标**不是"不漂"**，而是 —— **让漂移能被发现**。

这句话是这一篇的立论，下面所有做法都从它推出来。

---

## 二、四种形态，四种防法

| 漂移形态 | 它是怎么发生的 | 防法 |
|---|---|---|
| **判据散落两处** | 同一个判断写在两个地方，改了 A 忘了 B ⇒ **检查悄悄少跑一项** | **单一真源** |
| **文档与代码对不上** | 代码改了、文档没改 ⇒ 读文档的人被**误导**，而且他看不出来 | **提交前自检** |
| **改了行为，别人不知道** | 重构时顺手改了行为，调用方还按老假设在用 | **行为等价性验证** |
| **旧版本累积** | 每改一次留一份，越滚越乱，分不清哪份是"活的" | **只增不删 + 留档** |

四条防法有一个共同点：**它们都不是"禁止修改"，而是"让修改的后果立刻显形"。**
（见 §四）

---

## 三、为什么漂移特别难被发现

因为它**不报错**。

| | 显性失败 | **漂移** |
|---|---|---|
| 有信号吗 | 有（崩了 / 报错 / 红） | **没有** |
| 谁先发现 | 你自己 | **下一个踩到的人** |
| 什么时候暴露 | 立刻 | 可能几周后，而且归因很难 |

更麻烦的是，它常常**伪装成正常**：

- 检查少跑了一项 ⇒ 输出**还是"全绿"**；
- 文档过期了 ⇒ 读起来**还是通顺的**（数字不对不会让人停顿）；
- 行为悄悄变了 ⇒ 测试**还是过的**（如果测试也按新行为写的）。

> ⇒ 所以漂移属于「**静默失败**」那一族 —— 它只能**预防**，没法"出事后再处理"，
> 因为它出事的时候**不告诉你**。

---

## 四、★ 反直觉的结论

**最好的防漂移手段，是"让漂移可见"，而不是"禁止修改"。**

两个选项摆在一起看：

| 做法 | 代价 | 能持续吗 |
|---|---|---|
| **禁止修改**（冻结） | 停止迭代 —— 对一个还在长的东西等于判死刑 | ❌ |
| ★ **让漂移可见** | 每次改动时自动暴露"哪些地方跟着变了" | ✅ |

具体就是这套组合：

| 你改了什么 | 该发生什么 |
|---|---|
| **判据** | 它只该有**一个家**（单一真源）—— 改一处，所有用它的地方一起变 |
| **代码** | 提交前跑闸门：文档、索引、注册表**漂了就报错** |
| **行为** | 先跑一遍记下基线，改完**逐行比对**（「看起来对」不是判据） |
| **版本** | 旧的**留档**、新的**原子替换** —— 并且**逆向验证它真的换成了** |

## 五、本项目的三个真实例子

### 例 1 · 判据散落两处 ⇒ 检查静默少跑

同一个判断写在两个文件里，改了一处、漏了另一处。
结果是**检查少跑了一项**，而输出仍然是"全绿"。

**修法**：收口到**一处**（一张 JSON 登记表），加一项检查只改这一处。
后来它又进化了一次：连"检查该怎么显示、失败算阻塞还是警告"也一起收进那张表 ——
于是**加检查时，代码一行都不用动**。

### 例 2 · 文档里的数字过期了，没人发现

一篇文档里写着"3 类失败 / 3 个工具 / 46 项测试"，而实际已经是 5 类 / 5 个 / 84 项。 <!-- doccheck-ignore：这里的数字是**引文**，是别人写错的，不是本仓库的声明 -->

**讽刺的是**：那份文档的主题正是"防静默失败"——**而它自己被静默漂移了。**

**修法**不是"以后注意"，而是：**把计数交给检查器**。
（本项目就有这么一个检查：文档里写的数量必须与实际文件数一致，不一致就报错。）

### 例 3 · 同一份"事实"抄了两处

有一条规则同时写在两个地方。后来有人只改了一处 ——
于是两份文档开始各说各话，**而两边看起来都对**。

**修法**：把第二处**改成从第一处派生**（而不是手抄）。
判据是：**凡是"手抄"的地方，都是漂移的候选地。**
