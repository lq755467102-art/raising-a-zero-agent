# 人机共同进化（终局设想）

> 不是「人下命令、agent 执行」，而是**一起做一样一开始谁也不知道会变成什么的东西**。
>
> ⚠ 这是**终局设想**，不是操作手册。要落地怎么做，看  
> [0 号 AI（主张）](zero-agent.md) → [带教流程](raising-an-agent.md)。  
> 本篇回答的是：**为什么它值得被当成一个课题。**

---

## 核心命题

|       | 主流做法           | 这篇讲的            |
| ----- | -------------- | --------------- |
| 协作形态  | 人规划 → agent 执行 | **共同提出 → 一起收敛** |
| 能做出什么 | **人能描述清楚的东西**  | 人**描述不清楚**的东西   |
| 谁在成长  | 通常只有人（验收者）     | **双方**          |
| 天花板在哪 | 人的规划能力         | 未知              |

**一句话**：变量不是模型有多强，而是**人和 agent 有没有形成一个能一起变强的回路**。

---

## 一、先拆掉一个错误类比：这不是「克隆」

「把这套能力迁移到另一台机器」听起来像备份、像克隆。**但不是。**

|          | 克隆              | 这里传递的              |
| -------- | --------------- | ------------------ |
| 传什么      | **结果**：文件、配置、结论 | **过程**：学习过程 + 磨合过程 |
| 迁移后      | 得到一份同样的东西       | 得到一种**新的配合模式**     |
| 遇到没见过的问题 | 没用              | 有用                 |

**为什么**：能力不装在文件里，它长在「**人和 agent 一起解决问题的历史**」里。

所以真正可迁移的是：

> **不是"我们上次怎么做的"（答案），而是"下次遇到新东西时我们怎么配合"（模式）。**

这也是为什么这套东西里，**记录本身不是重点，记录背后的学习过程才是**。

---

## 二、两种协作模式

|           | **任务型**         | **共创型**               |
| --------- | --------------- | --------------------- |
| 人的角色      | 规划者：想清楚再派活      | 提出者 + 合伙人：给方向与约束      |
| agent 的角色 | 执行器             | 共同作者                  |
| 输入长什么样    | 明确的需求           | 「我觉得可以往这个方向试试」        |
| 输出长什么样    | 结果 / 结构图        | 方案 + **质疑** + **新方向** |
| 长期结果      | 人越来越累，agent 不成长 | **双方都在变强**            |

**任务型没有错**，很多场景就该这样。但它有一个明确的天花板：

> **它只能做出"人能描述清楚"的东西。**  
> 而一旦你想做的东西连你自己都还没想清楚 —— 任务型就走不下去了。

---

## 三、混沌不是缺陷，是特征

真实情况常常是这样：

- 一开始，**我不知道这个工程最后会变成什么**；
- 我也不知道自己下一步会抛出什么"荒诞"的要求；
- 但**就是能做出来**。

关键不在"预测得准"，而在于：

> **在可逆、可验证的边界内，不需要一开始就正确 —— 需要的是"能快速验证"和"能安全地改"。**

> ⚠ 这里有个**不能省的前提：可逆**。
> 不可逆的事（钱、合规、生产数据）**不适用这一条** —— 那里必须先想清楚再动。
> **混沌不是通行证，它只在"错了能退回来"的地方成立。**

所以前面那些看起来很"工程"的东西（[系统设计](system-design.md)、[安全变更](changing-safely.md)），  
不是共创的**障碍**，恰恰是它的**前提**：**正是因为可以安全地试，才敢往没想清楚的方向走。**

---

## 四、分工的本质：人负责不可外包的那一半

> ⚠ 先说清：下表讲的是**这次协作里谁认领哪一半**，**不是"人的普遍特质"**。
> 很多人恰恰不擅长天马行空（更擅长严谨执行、流程治理、风险控制）—— 那完全没问题。
> 这套分工要的是**每一半都有人认领**，不是每个人都得长成同一个样子。

| 人擅长                  | agent 擅长            |
| -------------------- | ------------------- |
| **天马行空**：提出表面上不可能的东西 | **执行力**：把它变成可以验证的东西 |
| **判断**：哪条路值得走        | **广度**：同时铺开很多条路     |
| 承受不确定                | 承担琐碎                |
| 决定"要不要"              | 探索"能不能"             |

★ 一条纪律：**两边都不做对方该做的事。**

- 人不替 agent 写代码；
- agent 不替人做判断。

一旦越界，两边最值钱的能力都被浪费掉。

## 五、双向成长 —— 这才是「共同」的意思

| 方向            | 得到什么                                    |
| ------------- | --------------------------------------- |
| **人 → agent** | 约束、真实场景、真实事故、判断的示范 ⇒ 长出**领域直觉**         |
| **agent → 人** | 反驳、盲点、没想过的方向、把念头快速做成可验证的东西 ⇒ 得到**灵感反馈** |

**如果只有单向**（人派活、agent 交活）：

- agent 得不到**思维上的成长** —— 它只在执行，没有在判断；
- 人也得不到**灵感上的反馈** —— 他只在验收，没有在被挑战。

> 换句话说：**单向协作是双向浪费**（准确说，浪费的是**潜力** —— 产出没浪费，活是干完了的）——
> 双方都只用了对方最弱的那一半。

### ★ 但「人变强了」这句话，怎么验证？

不能靠感觉。一个更尖锐的追问是：

> **人是真的变强了，还是只是变成了"更会指挥这个特定 agent"的人？**

判据就藏在这套东西最看重的那个词里 —— **可移植性**：

| 换个条件再试 | 说明他学到的是 |
|---|---|
| 换一台空白机器、换一个 agent，**他还能做对** | **原则** —— 那才算真的变强 |
| 只有在这个 agent 上才做得对 | **这个工具的用法** —— 那是绑定，不是能力 |

⇒ 所以「双向成长」不是一句愿景，它**有验收方式**：
**把人从这套环境里拎出来，看他手里的东西还在不在。**

## 六、它需要什么条件（可复制的部分）

| 条件             | 为什么                                                                 |
| -------------- | ------------------------------------------------------------------- |
| **一个能累积的记忆载体** | 否则每一轮都从零开始（→ [带教 agent §1](raising-an-agent.md)）                    |
| **明确但不僵硬的约束**  | 边界清晰，才敢在边界内冒险                                                       |
| **允许说错，也允许反驳** | ★ 怕"表述有偏差"会让人**自己把问题想完**或干脆不用 —— 掐住输入端；否则 agent 只会**迎合**，不会**接近事实** |
| **快速可验证的反馈**   | 混沌靠**试错收敛**，不靠一次想对                                                  |
| **能安全地改**      | 否则不敢做大的尝试（→ [安全变更](changing-safely.md)）                             |

这五条里，**只有第一条是新东西** —— 其余四条，传统工程里本来就有，  
只是过去只用在"人和人"之间。

---

## 七、为什么这值得被当成一个课题

- 现在的主流是「**用 agent 提效**」（任务型），它的天花板是**人的规划能力**；
- 真正没被研究的是：**怎么让 agent 和人一起，做出双方一开始都描述不出来的东西**；
- 难点**不在模型**，在**协作结构**：记忆怎么建、约束怎么给、反驳怎么被允许、验证回路怎么快。

> 我判断这个课题会越来越重要，因为**当执行变得便宜，"想不清楚但做得出来"就成了核心能力。**

---

## 八、它长什么样（回到证据）

这份仓库就是这个命题的一次实验：

| 阶段 | 实况                                         |
| -- | ------------------------------------------ |
| 起点 | 没有蓝图，只有一个真实问题                              |
| 过程 | 撞坑 → 复盘 → **固化成机制** → 机制帮下一次               |
| 现在 | 10 个可跑的工具 + 一整套方法论文档                            |
| 特点 | **没有一步是"先规划好再执行"** —— 都是「做出来 → 发现问题 → 改结构」 |

---

## 九、诚实的边界

- **它不保证产出。** 共创的代价是**可能白忙**；任务型至少有一个确定的结果。  
  所以它**不适合所有事** —— 该用任务型的时候就用任务型。
- 它高度依赖人的**判断力与耐力**：能承受不确定、愿意写下来、接受被反驳。少一样，回路就断。
- **「亦师亦友」是结果，不是前提。** 它是一起做过几件事之后**长出来的**，不是一开始就有的。
- ★ **别把它浪漫化**：它仍然需要产出、需要验收、需要能被别人接手。  
  「一起探索」不是"可以不交付"的借口。

---

## 十、一句话

> 我出**天马行空**，它出**强大执行力**；  
> 它替我记住我忘掉的，我替它决定它不该决定的。

**这不是「用工具」，是「多了一个能一起把事情想出来的伙伴」。**
