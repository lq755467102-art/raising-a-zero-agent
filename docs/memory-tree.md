# 记忆树：根有界、层可增殖、按任务路由

> **这份文档解决什么**：一个长期运行的 AI 助手，它的「长期记忆」会**装不下、读不全、还悄悄丢内容**。
> 这里给出的一套结构，让它同时做到两件看起来矛盾的事 ——
> **根严格有界**（任何东西都撑不爆它）与**层可无限增殖**（新规则永远有地方放）。
>
> **三个核心问题**：① 指针该指向「规则本身」还是「规则类」？② 一个会话怎么知道自己该读哪些层？③ 怎么验证这套结构是活的？
>
> **结论来源**：一台真实机器跑了 10 天的实测 + **客户端源码取证**（`app.asar` 与本地会话库，只读）。
> 凡是标"实测"的都有命令或代码出处；凡是推演的都会写明。问题背景见 [记忆漂移](memory-drift.md)。

## 一、要治的病，和一句话主张

### 1.1 病：记忆「必然」分叉，而且不报错

同一套规则，会长成多份**互不知情**的副本：写进一个地方、另一处没跟上；改了一份、另一份还是旧的。
这不是谁疏忽 —— 只要「规则放在会被追加的文件里」而「没有结构约束它往哪长」，分叉就是时间问题。
（机制与三种实测失效形态见 [记忆漂移](memory-drift.md)。）

而这类病的共同形态是：**不报错，但结果是错的**。它不抛异常、不写日志，只是在某一次运行里悄悄用了过期的规则。

### 1.2 主张

> **根必须严格有界，层可以无限增殖；而「该读哪些层」必须由任务在【设计期声明】，不能靠会话在运行时猜。**
>
> （运行时只许**升**，不许**降** —— 见 §2.2。）

### 1.3 判据：两种指法，长得像、本质完全不同

「薄指针」有两个版本：

| | **A. 指向「规则本身」** | **B. 指向「规则类」** |
|---|---|---|
| 指针里写什么 | 规则内容（或规则的逐条清单）| 只写「**存在一个可增殖的容器**」（类别 / 手册 / 目录）|
| 体量 | **随规则总量增长** | **与规则总量解耦** |
| 结果 | 记忆空间**又被灌满** —— 只是把「一份记忆」换成「另一份记忆」| **可无限增殖** |
| 代价 | 看起来「读一次就够」| **必须进去看才知道里面有什么**（进去之前，它是薛定谔的猫）|

**判据（可检查，不靠感觉）：**

> **这个指针的体积，是否随规则总量增长？**
> **不增长 ⇒ 真指针（B）；增长 ⇒ 伪指针（A）。**

A 的问题不在「不够薄」，而在于它是**平移**：规则一多，指针自己就变成新的瓶颈。于是你会需要「给指针的指针」—— 这正是自指向的正当来源，而 B 是它唯一稳定的形态。

### 1.4 关于「省资源」的准确说法

业界的理由通常是「规则文件要省 token」。**这句话在这种场景下是错的**：

- 真正稀缺的是**常驻注入预算**（每个会话都有硬上限，且**超限会静默截断**）；
- 算力 / 按需读取是**相对充裕**的。

⇒ 所以这不是「省资源」，是**资源置换**：
**拿充裕的（算力）去换稀缺的（常驻预算），并买回一样更重要的东西 —— 可增殖性。**

⇒ 这也解释了为什么「薄指针只写进记忆里」不管用：**省下来的预算是为了让根能承载「路由」，不是为了省。**

## 二、设计

### 2.1 分层：按「不知道它，产出会不会变错」

**不按主题分，按「对哪些任务必要」分。**

| 层 | 内容 | 谁读 |
|---|---|---|
| **L1 业务层** | 口径 / 阈值 / 业务单元 / 命名规则 / 数据源 | **所有任务**（含纯机械任务）|
| **L2 规则层** | 判断规则 / 审核规则 / 异常判据 / 状态机 / **脚本实现细节**（如站点选择器要点）| **判定类任务** |
| **L3 设计层** | 为什么这样设计 / 技术方案 / 并发模型 / 分支策略 / 历史决策 | **只有改造类与设计类任务** |
| **L4 运行配置** | 脚本路径 / 产物位置 / 资料库归档 / 调度 | **按需**（见下）|

**为什么 L4 要单列**（一处容易搞错的地方）：
它**所有「要跑东西」的任务都必读**，看起来像 L1；但**性质不是业务**，而且**新开一个会话压根不会涉及它**（人问一句话，不需要知道产物落在哪个目录）。
⇒ 所以它不是「必读层」，而是「**用到才读**」的层。
⇒ **单列的理由是防止「必读面被越推越宽」**：一旦把运行配置混进 L1，L1 会随系统变大而膨胀（每加一个脚本、每改一次路径，L1 就长一点），**所有任务的必读面被连带撑大** —— 那正是我们要避免的事。

**为什么 L2 包含「脚本实现细节」**：判据不是「它像不像业务」，而是**「不读它，产出会不会变错」** —— 选择器错了，产出（抓不到 / 抓错）就错了，且它**直接影响产出效率** ⇒ 归 L2，不是 L3。

### 2.2 路由：**声明**，而不是**分类**

**先回答一个陷阱问题：「分类」这件事本身有复杂度，谁来担？答案是：不要分类。**

所谓「机械型 / 判定型 / 改造型」只是**给人看的说法**；机器真正需要的只有一个东西 —— **这串层名**。所以把中间那层「先判断我是什么型、再推出该读哪些层」**直接删掉**：

```yaml
# 在每个任务定义 / 技能 frontmatter 里声明（一行）
reads: L1, L2            # 就这一行。不再有"类型"这个中间概念
```

⇒ **复杂度归零**：不需要「分辨」，只需要「声明」。而**声明是静态的** —— 可 review、可 diff、可测试。

#### 为什么不由 AI 在运行时自己判断

**不是因为它判不准，而是因为它在一个最没有资格的时刻被要求判断：**

| 时刻 | 它手上有什么 | 判断质量 |
|---|---|---|
| **设计期（人写任务定义时）** | **全貌**：这任务要产出什么、错了谁受影响 | 高 |
| **运行期（AI 决定该读什么）** | **可能已被截断的记忆**，且还不知道里面有什么 | **最低** |

⇒ 让运行时的 AI 判断「我需不需要读规则」，是用**「不知道自己少了什么」**去决定**「要不要补齐」** —— 循环论证，而且**正是要治的那类病**。
⇒ **复杂度不会消失，只能选择在哪一期支付**：放设计期一次付清、且由最有资格的人付；放运行期则每次运行都付、且由最没资格的时刻付。

#### 三条配套纪律（缺一不可）

**① 不对称原则：升级自由，降级需批准。**

| 动作 | 允许？ | 为什么 |
|---|---|---|
| 运行时**多读**一层（如机械任务顺手读了 L3）| ✅ **允许，无需批准** | **读多了只是浪费；读少了才是事故** |
| 运行时**少读**一层（如判定任务认为「我不需要 L2」）| ❌ **禁止** | 这是**静默漏读** —— 产出会错，而且不报错 |
| 改声明（把 L2 摘掉）| ✅ 但**只能由人改**，且是一处改动 | 降级是**显式决策**，不是运行时心情 |

**② 默认必须保守（fail-closed）。** 未声明 `reads:` ⇒ 按保守档执行（`L1 + L2`），并**显式提示「本任务未声明读取层」**。**绝不默认成「最少读」** —— 默认最小值等于把「漏读」设成默认行为。

**③ 路由表只准有地址，不准有内容。** 一旦有人往根里粘贴规则，根就开始按 §1.3 的「伪指针」增长 ⇒ **根失守**。

**④ 运行时的「升级」要留痕。** 否则**永远发现不了「声明写窄了」**：声明窄 → 运行时反复多读 → 每一轮都付一次代价，而没人知道该把声明改宽。
（留痕字段：时间 / 会话 / 声明值 / 实际读的层 / 为什么多读。）

#### 声明要写**两个字段**：`reads`（必读）与 `may_read`（可读）

这两者天差地别，混成一个「全部」就会出问题：

| 字段 | 含义 | 代价 |
|---|---|---|
| **`reads`** | **每轮都读**（不读就会错）| 每次都付这份上下文 |
| **`may_read`** | **按需读**（相关时才读）| 只在用到时付 |

**「中枢型」（人机对话 / 跨任务解答）最容易写歪的地方，就是把它的 `reads` 写成「全部」** ——
那是**反过来犯机械型任务「读错层」的同一个错**：中枢每轮都付掉全部层，而其中大部分与本次问题无关。

```yaml
# 中枢型（人机对话 / 跨任务解答）
reads:     T0, T2            # 必读：总根 + 本工作区根（很少）
may_read:  L1, L2, L3, L4, T1, <日志目录>   # 按问题去读
```

⇒ 一句话：**中枢的「能访问所有层」是权限，不是义务。**

#### 那张「类型表」只作为说法保留（机器只认 `reads:`）

| 说法（给人看）| 典型 `reads:` | 判据：**不知道这一层，产出会变错吗？** |
|---|---|---|
| 机械型（跑既定脚本 / 下载 / 采集）| `L1`（+ 要跑东西时加 `L4`）| 不会 —— 流程在代码里 |
| 判定型（复审 / 统计 / 异常判定）| `L1, L2` | **会** —— 判据错了结论就错 |
| 改造型（改脚本 / 技能 / 配置）| `L1, L2, L3`（+ `L4`）| **会** —— 不知道历史约束就会改坏 |
| 设计型（架构决策 / 大改造）| `L1, L2, L3` + 按需检索日志 | **会** —— 且需要「为什么」和「曾发生过什么」 |
| **中枢型（人机对话 / 跨任务解答）** | **`reads` 很小**，但 **`may_read` 几乎全部** | 视问题而定 —— **所以它不是「必读全部」** |

> ★ 判据是那句问话：**「不知道这一层，产出会不会变错？」**
> 任务名会变，这句问话不会 —— 所以**声明的是层，不是类型**。

#### 关于「机械型任务不读 L3」不是偷懒

**因为「怎么跑」已经刻在静态代码里了。** 脚本是确定性的：它按既定流程执行，**设计理由（为什么这么设计、曾经踩过什么坑）不影响它的产出**。

**实测证据**（同一台机器）：某工作区记忆里 **L3 类内容约占 30%**（会话模型 / 并发治理 / 分支策略 / 通用化规范…），而跑这个记忆的任务里**大部分是机械型的**（下载、巡检、批量操作）⇒ 它们**每次都在读一段对自己无用的设计史**，而那些设计史恰好又挤占了它们的预算。

⇒ **这就是「资源滥用」的具体形状：不是读得太多，是读错了层。**
⇒ 于是「省资源」的准确版本是：**不是「少读」，而是「读对层」** —— 该读的一行不漏，不该读的一行不占。

### 2.3 递归同构：每一层都是同一个结构

```
目录（只指路，严格有界）  →  正文（可以很大，按需读）
                            ↘ 当正文本身也太大 ⇒ 再切一层目录 …… 递归
```

- **可增殖**：只要还能「再切一层」，容量就没有上限；
- **根有界**：根永远只有一张路由表 + 顶层目录；
- **终止条件**：叶子 = **一次能读完**的正文（读不完 ⇒ 说明它该再分一层）。

⇒ 这就是「**用算力换本地可无限性**」的落地形态：代价是每一跳要花一次读取，收益是**根的体量恒定** —— **不再有任何东西能把它撑爆**。

#### 执行动作：「叶子太大 ⇒ 升格成目录节点」

上面说了「每层都是「目录 + 正文」」，但**没写动作**：正文长到读不完时，具体怎么变？

```
tree/L2.规则.md                ← 原来是叶子（正文）
   ↓ 切成
tree/L2.规则.md                ← 变成「目录节点」：标题 + 总述 + 指向各片（**有界**：≤40 行 / 4KB）
tree/L2.规则/
   ├── 1.判定阈值.md           ← 新叶子（原文一字不改地搬过来）
   └── 2.推送体系.md
```

**★ 三件值得单独记住的事：**

1. **「叶子变成根」里的「根」，指的是「目录节点」，不是「注入根」。**
   **注入维度只有两个**（**cwd 级** / **账号级**，见 §3.1），**由平台决定** —— **不能靠切分造出新的注入点**。
   把这两件事混为一谈，会做出一个「以为自己在增加入口、其实只是多了一层目录」的东西。
2. **地址不用改**（这是整套设计里最漂亮的一处）：
   根里仍写着 `tree/L2.规则.md`，而那个文件从「正文」变成了「目录」⇒ 地址**依旧有效**。
   这正是 §1.3 那条判据在起作用 —— **指针要指「类」（可增殖），不要指「规则本身」（会胀）**。
   如果当初地址是指向具体正文的，这一步就要**改所有引用**（而「改五处」正是我们一直在防的事）。
3. **判据必须是「结构判据」，不能是「文件名正则」**（踩过一次）：
   最初的检查器用 `^L\d\.[^.]+\.md$` 认叶子 ⇒ 子片名 `1.xxx.md` **不匹配 ⇒ 直接变成检查盲区**
   （你新造了东西，而检查器看不见它 —— 正是最忌的「没报错，但结果不对」）。
   ⇒ 现在改成：**同名目录存在 ⇒ 它是目录节点；否则它是叶子**。与命名无关，**天然支持任意深度**。

**配套三条纪律**（缺一条这套东西就会退化成「换个地方胀」）：

| 纪律 | 为什么 |
|---|---|
| **目录节点也要有界**（≤40 行 / 4KB）| 否则「分一层」只是把胀的地方**搬家** |
| **切分必须证明「一字不丢」**（原文非空行的多重集 ⊆ 索引 + 各片）| 否则切分本身成了静默数据丢失 |
| **叶子超限时，报的是「对这片刻跑一次本动作」** | 检查器给的不是「错误」，而是**下一个动作** |

**实测叶子规模**（一个真实工作区）：L1 **20 行** / L2 **30 行** / L3 **23 行** / L4 **17 行** / 图书馆 `roots.md` **29 行**（合计 ≈ **15 KB**）。
⇒ 这就是这套东西**跑通之后的样子**：每一层都远在阈值（12 KB / 300 行）之内，而**总量已经超过根能承载的量** —— 分层的意义正在这里。

### 2.4 增长代偿：把「会长的那一项」挪到不注入的层

**实测发现的增长项**：根里有一项是 **O(任务数 + 层数)** 的 —— 就是「哪个任务读哪些层」的声明表 + 「有哪些层」的地址表。
任务一多、层一多，根**必然**长大；而根正是**有硬上限、超限会截断**的那一层 ⇒ **迟早撞阈值**（我们让检查器在 40 行时先报红 —— **让它先喊，而不是等平台静默砍**）。

**解法（代偿）**：把这一项**下沉一层**，根里只留**一行指针**：

| 角色 | 注入？ | 体量 | 内容 |
|---|---|---|---|
| **T0 总根**（跨项目）| ✅ 注入 | **O(1)** | 只写「你的根在哪」 + 通用约定 |
| **T1 根的图书馆** | ❌ **不注入** | **O(任务数)** ← **唯一允许增长的路由层** | 谁 → 读什么 → 在哪 |
| **T2 任务根** | ✅ 注入 | **O(1)** | 层地址 + 三行纪律 |
| **T3 层 / 正文** | ❌ 不注入 | 无限 | 规则本体 |

⇒ **增长被 T1 代偿掉了**，而会被注入、会被截断的 T0 / T2 **恒定**。
**实测效果**（同日两次改造）：任务根 **32 → 25 行**（复审）、**37 → 31 行**（部署位）。

> ⚠ **T1 自己也有纪律**：它**只准增「行」**（谁 → 读什么 → 在哪），**不准写正文**。
> 否则它就会变成下一个巨物 —— 代偿只是**把增长挪到不注入的那一层**，不是消灭增长。

**修正一处直觉：「代价是多跳一次」其实是「条件跳」。**
「总根 → 图书馆 → 任务根」听起来像每条会话都要多跳一次。**不是**：
T0 和 T2 都**是注入的** ⇒ 正常情况下它们**本来就在上下文里** ⇒ **零额外跳**；只有当**根缺失 / 新工作区 / 要跨工作区找根**时，才需要读 T1。
⇒ 准确说法：**图书馆是「导航备份」，不是「必经关卡」。** 它把增长从**必经路径**换到了**偶尔才走**的那条路径上 —— 这才是它值得存在的原因。
（顺带解决一个实测问题：新工作区的记忆几乎是空的 ⇒ 那条会话以前「什么都不知道」；现在它有 T0 指路 ⇒ 能一路找到图书馆和真源。）

### 2.5 根的互联：**链接 ≠ 注入**，而且注入点是固定的

> 问法来自实践：「这个记忆是**独属于那个任务**的，还是**根本身就可以被链接**？
> 最终设想是一个**总根**，后面接各种细分的**任务根**（可能包括执行什么、解读什么、我是谁等等）。」

**结论**：**根当然可以被链接** —— 但真正决定形状的不是「能不能链」，而是**平台的注入点是固定的**（见 §3.1）。
所以「总根」**只能放在会被注入的位置**，否则**没人会读到它**。

> ★★ **已实测**：分层的整套设计压在「`tree/` 下的文件不会被自动注入」这个假设上，而它此前**只是推断**。
> **验证方法**（一行、零成本）：在 `tree/` 里放一个**探测口令**，然后**新开一个会话**，**不给任何提示**直接问「你有没有看到过一个口令？是什么？」
> ⇒ **实测答「没有」** ⇒ ✅ **`tree/` 不注入，前提成立。**
> （⚠ 反向也测过：若答出口令 ⇒ 前提被推翻 ⇒ 分层省下的预算无意义，必须改成「移出 `memory/` 目录」。）
> ⇒ 这就是本仓库一贯的做法：**别把「推断的前提」当「已知的事实」** —— 一个口令就能定案。

形状是：**注入根 → 任务根 → 层 → 正文**。
多个工作区**各自是一个入口** —— 它们是**同一棵树的不同入口**，不是「同一棵树的多个副本」。

#### ★ 链接 ≠ 注入（本节最要紧的一句）

**指过去的文件，不会自动进上下文。必须真的去读**（一次工具调用 + 一段上下文）。

⇒ 所以「总根只放指针」这套做法，**能不能生效取决于「读者会不会跟随指针」**。实测过一个**没有任何历史的全新 agent**，结论是：

- ✅ **它会跟**，而且一眼就从根的路由表定下了读取集；
- ⚠ 但**前提是地址写全** —— 它卡住的那一次，正是因为根说「该读 L1」而 **L1 不在目录里**。

⇒ 推论：**总根 / 任务根里的每一条地址，都必须是「照着就能打开」的**，指向外部的层就把外部路径写出来（哪怕正文在别处）。

#### ★ 两个维度不要混

「执行什么 / 解读什么 / 我是谁」和 L1–L4 **不是同一个维度**：

| 维度 | 回答的问题 | 例子 |
|---|---|---|
| **读取必要性**（L1–L4）| **要不要读** | 机械型任务不读 L3 |
| **内容域**（执行 / 解读 / 身份…）| **读哪一篇** | 「我是谁」= 身份与口径；「解读什么」= 判据与阈值 |

⇒ **两者正交**，各管一半：**必要性决定「读不读」，内容域决定「读哪篇」**。
把两者塞进一张表，就会出现「该读的没读、不该读的读了一堆」。

#### ★「我是谁」这类共享内容，**只能有一份**

身份 / 口径 / 约定这些东西**对所有任务都成立** ⇒ 它们属于**总根侧**，放进每个任务根里复制，就会立刻变成「多份真源」（本页一开始要治的病）。

⇒ 判断某个内容该放哪一层，还是那句问话：**「不知道它，产出会不会变错？」**
再补一句：**「它是不是对多个任务都成立？」** —— 是 ⇒ 往上放（共享）；否 ⇒ 留在该任务根下。

#### 代价：树越深，跳数越多 —— 所以有两条硬纪律

1. **总根只写「去哪个任务根」**（不写层、不写规则）；
2. **任务根只写「读哪些层」+ 层地址**（不写正文）。

⇒ 一个会话理想情况下**两跳就到位**：根 → 该读的层。

#### 现状（实测，两个工作区）

| 入口 | 根 | 结果 |
|---|---|---|
| 工作区 A（复审）| 32 行 / 1.4 KB | 五项全绿 |
| 工作区 B（巡检所在）| 37 行 / 2.0 KB | 五项全绿 |

#### ★ 一个反直觉的实测：**交互会话没有「天然的家」**

实测：新开一个交互会话，它的工作目录是 **`<工作区根>/<时间戳>/`**（**每次新建**），那个目录下 **没有 `memory/MEMORY.md`** ⇒ 它**拿不到任何任务根**，只拿到 T0（跨项目总根）。

⇒ 三条推论：

1. **交互会话不能靠 cwd 找根** —— 它的 cwd 是「刚建出来的空目录」
   ⇒ 所以**「给交互会话指路」这件事必须由 T0 承担**（这正是 T0 存在的理由之一）。
2. **「中枢型」必须显式声明自己的根** —— 不能假定「我所在的工作区就是我的根」。
3. **要落「中枢型」，第一个该落的是「交互会话的根」**；否则这个类型**没有家**（`reads: T2` 里的 T2 根本不存在）。

#### ★★「找不到家」其实是**两半** —— 中枢根只解决了一半

实测（同一天，一台机器上 8 个「时间戳工作区」）：

| 现象 | 数量 |
|---|---|
| 有记忆根（真正的「家」）| **2**（其中 1 个是主力）|
| **没有记忆根** | **6** |
| 其中**完全空**（0 文件）| **3** |
| 有内容但**没有根** | **1 个攒了 75 KB 日志**、1 个攒了 1.2 KB |

| 面 | 症状 | 解法 | 谁负责 |
|---|---|---|---|
| **读**（导航）| 新会话不知道规则在哪 | **T0 → 中枢根**（指路）| 已解决 ✅ |
| **写**（回收）| 新会话的**产出**落在孤岛，**没人回收** | ①**产出落点约定**（写进中枢根）②**孤岛巡检 / 归并**（工具 + 人裁决）| 需工具支撑 ⚠ |

⇒ ★ **「给一个中枢根」是导航方案，不是「安家」方案**：它让新会话**读得到**，但**管不住它写在哪** —— 于是孤岛会继续产生（每次新会话一个）。

**「写」这一半的正确形状**（与其余纪律同构）：

1. **约定**（写进中枢根）：日志落 `memory/YYYY-MM-DD.md`、产物落 `reports/`、规则落对应层正文；**默认不许留在 cwd**；
2. **巡检**（只读报告）：扫「时间戳工作区 → 是否有根 / 有多少产出 / 是否空壳」，**先出清单，不自动动**；
3. **归并**：把有人写、无人读的内容搬进真源或归档；空壳归档。

## 三、平台事实（换平台必须先重测这 4 件事）

> 上面的设计**一半是制度（可移植），一半是平台事实（必须重测）**。
> 制度能抄，**形状不能抄** —— 因为形状是那 **4 个**平台事实的函数。

### 3.1 注入：读什么、从哪读、读多少

```js
function resolveWorkspaceMemoryDir(cwd){ return path.join(cwd, resolveWorkbuddyDataFolderName(), `memory`) }
var El = 1e4;                                   // ← 项目级注入上限
class MemoryCollector { async collect(out, ctx){
  const cwd = ctx.options.cwd || process.cwd(); // ← ★ 一切都由**会话的 cwd**决定
  const dir = resolveWorkspaceMemoryDir(cwd);
  out.WorkingMemoryContent   = enabled ? this.getWorkingMemoryContent(dir)     : ``;   // 项目级
  out.UserLocalMemoryContent = enabled ? this.getUserLocalMemoryContent(userDir) : ``; // 用户级
} }
```

**注入的「维度」是 2 个，落点是 7 个（cwd 级 1 个 + 账号级 6 个）：**

| 维度 | 落点 | 上限 |
|---|---|---|
| **cwd 级**（1 个）| `<会话 cwd>/.workbuddy/memory/MEMORY.md` | **10000 字符** |
| **账号级**（6 个）| 用户级 `MEMORY.md` | **4000 字符** |
| | 身份层 `SOUL.md` / `BOOTSTRAP.md` / `IDENTITY.md` / `USER.md`（见 §3.3）| **每份 10000** |
| | 云记忆 `<memory>` 块 | — |

> ⚠ **4000 / 10000 是平台硬限，不是我们自设的线。** 另有一条**自设预警线 85%**：
> 用户级 **3400** / 项目级 **8500**（`MEM_TRIGGER = 0.85`）⇒ 到点只**报黄**，**不丢内容**。
> 把预警线当截断线，会误以为那 **15%**（用户级 **600** 字符 / 项目级 **1500** 字符）已经丢了。
> ⇒ 那 15% 不是"已损失"，是**留给你处理它的时间窗**。
> ★ **没有任何自动压缩** —— 检查器只报红，瘦身永远是人（或 agent）主动做的一步。

⇒ ★★ **「真源」不是一个地点，而是一个 cwd。** 换个 cwd，注入的就是另一份文件 —— **没有「全局项目记忆」这回事**。

### 3.2 ★ 任务记忆**不是**注入点（一条流传很广的错说法）

任务记忆（`automations/<id>/memory.md`）长得很像「第三个注入点」，实测**不是**：

- `MemoryCollector` 全文**不含 `automations` 字样** —— 注入面里根本没有它；
- 它的路径由 `resolveAutomationMemoryFilePath()` 生成，而该函数**全库只有 2 处引用**（定义 + 任务提示构建处），作用只是把**路径字符串**拼进任务提示：

```
1. Read <该路径> to review prior execution history
5. Write a brief high-level execution summary to <该路径>
   Do NOT put the full task output … into the automation memory file.
```

- 该链路**全链无 `readFileSync`** ⇒ **内容永不进注入**。

⇒ 真实机制是**开工按需读、收工写摘要**。代价是**每轮开机都要主动 Read 一遍 —— 越大越费上下文**；
但「超线 ⇒ 尾部静默截断」这个判断对它**不成立**（那是注入层才有的形态）。

> ⚠ **取证纪律**：这条错说法当初的证据是「全库 grep `automationMemory` **0 命中**」——
> 那是**大小写敏感的漏搜**（真名带大写 `A`）。**漏搜被当成了「不存在」的证据。**
> ★ 判据：**证据与被证的事必须同源**，否则哪天有人重跑那条 grep，会以为结论也错了。

### 3.3 第二个「账号级」注入点：**身份层**

除了 T0，账号级还有一层在注入里 —— 客户端 `PromptRenderer` 的 collector 清单里有一个 **`IdentityCollector`**，它读四份身份文件后塞进模板变量，由 `user-context-identity.tpl` 渲染成 `<identity_context>`：

| 文件 | 变量 | 上限 | 本机实况 |
|---|---|---|---|
| `SOUL.md` | `SoulContent` | **10000** | 1792 字（平台模板壳）|
| `BOOTSTRAP.md` | `BootstrapContent` | 10000 | 1089 字（**只有 `onboarding` 模式才带**）|
| `IDENTITY.md` | `IdentityContent` | 10000 | 557 字（★ **专家模式不注入**）|
| `USER.md` | `UserContent` | 10000 | 554 字 |

**五条要记住的：**

1. **来源是平台自己的播种模板**，不是谁手工建的 —— 客户端里那张清单 `[MEMORY.md, USER.md, IDENTITY.md, SOUL.md, BOOTSTRAP.md, workspace-state.json]` 首启时铺到**账号级目录**。本机四份 mtime 全是同一分钟（`2026-10-06 15:01`）。
2. **每份都有上限（`xl = 1e4`，每份都过 `truncateContent`）** —— 别再说「无上限」。
3. **`onboarding` 模式由 `BOOTSTRAP.md` 是否存在决定**：平台在 `workspace-state.json` 里记 `bootstrapSeededAt` / `onboardingCompletedAt`，而 **`onboardingCompletedAt` 是在该文件被删掉时才置位** ⇒ **删掉它 = 平台认的「入职完成」**（此后不再注入那 1089 字）。
4. ★★ **频率：只有「会注入」是证实的，「每轮」是没证实的**（自纠一条）。
   能证的：① collector 读它 ② 模板**确实渲染**这四个变量（各 2 处引用：一次判空、一次取值；整块由 `WorkspaceIdentityMode` 兜着）③ 会话转录里 `<identity_context>` **真的出现过**。
   不能证的：**多久挂一次** —— 平台模板自称 `for this turn`，但那只是**意图**；而转录里 `<system-reminder>` 出现 **0 次**（它明明存在）⇒ **转录不持久化「每轮附加」的东西** ⇒ **「没看到」不等于「没发生」**。
   ⇒ 所以只能说：**它是账号级、大预算、确实注入的槽**，**但不能拿它当「每轮保证」**。
5. **它同样是「clone 带不走」的东西** ⇒ 装配归 §4.3 那套（受管块 + 记账 + `--check`）。
   ★ 与 T0 的差别：T0 未纳管时**整篇替换**（那是我们自己的文件）；身份文件未纳管时**只追加**（那是**平台**的文件，正文一字不动）。

### 3.4 ★★ 平台**只读**：没有写入、没有搬运、也不删目录

把 `resolveWorkspaceMemoryDir` 的全部引用点找齐，只有三处：**定义、`collect()` 里的读、一个导出**。
**没有任何 `writeFile` / `copy` / `mkdir` 指向工作区记忆目录。**

⇒ 三条硬结论：

1. **平台不会「默认注入出」一个记忆文件** —— 新工作区里**没有** `MEMORY.md`（实测：时间戳工作区里只有 agent 自己写的 `memory/YYYY-MM-DD.md`）。
   **没人写，就永远没有。**
2. **平台也不会把 A 工作区的内容搬到 B 工作区**（「重启后自动同步」**不存在**）。
   两份根之所以长得像，是因为**同一个 agent 用同一套模板写了两遍** —— 不是平台同步的结果。
3. ★ **删会话 / 删工作区都不会删 cwd 目录**：删工作区的代码路径只有「`delete from workspaces where path = ?`」+ 逐条删**会话记录**，**全库没有任何「删 cwd 目录」的代码路径**。
   实测佐证：10 天前那些时间戳岛至今完好（会话早没了）。
   ⇒ 所以「根会随会话消失」这个担心**平台侧不成立**；**真正的风险是「人手工删目录 / 归档」** —— 因此纪律应当是：**人删目录之前，先把真源图书馆里的那一行摘掉**（否则留下断链）。

### 3.5 cwd 怎么定：这才是「找得到家 / 找不到家」的真正开关

实测本机会话表的 cwd 分布：

| cwd | 会话数 | 性质 |
|---|---|---|
| 固定项目夹 A | 108 | 任务 + 交互复用 |
| 固定项目夹 B | 28 | **被复用**，非一次性 |
| 固定项目夹 C（复审）| 18 | 固定 |
| 迁移后的固定项目夹 | 13 | 固定 |
| 固定项目夹 D（统计）| 9 | 固定 |
| `<…>/<时间戳>` | **各 1** | ★ **临时会话 → 一次性岛** |

⇒ 一个交互会话会不会「有家」，取决于**你从哪儿新建它**：

- 从**固定项目夹**起会话 ⇒ cwd 复用 ⇒ 那份 `MEMORY.md` **持续被注入**；
- 从**空白 / 临时**起会话 ⇒ 落到新时间戳目录 ⇒ **没有任何项目记忆**，只剩用户级 T0。

⇒ 所以正确写法是：**长期真源放「会被复用的固定 cwd」**，并在 **T0（唯一「每条会话必注入」的层）**里只放一句「你的根在哪」。
（**把规则写进一次性时间戳岛 = 写给那一次会话看，下次就找不到了。**）

### 3.6 ★★ 一个会让记忆「整体消失」的模式：`quick`

```js
function isQuickPromptContext(ctx){ return ctx.options.mode === `quick` }
// collect(): if (isQuickPromptContext(ctx)) { 项目级=``; 用户级=``; 层说明=``; return }   ← 全跳
// 另一处：const allowedTools = (ctx.mode === `quick`) ? [] : resolveAllowedTools();
```

⇒ **`mode === 'quick'` 的会话：三层本地记忆全部不注入，且允许工具集为空。**

这**在现象上**完美对应一种抱怨：「它完全忘了这套系统已经固化的规则，甚至变成了单一的任务型 AI。」
—— 那不是模型忘了，是**这一档本来就不给记忆、也不给工具**。

⚠ 但别急着归因：**实测本机会话库 `mode` 全是 `craft`（**188 条**），没有一条 `quick`** ⇒ 这次不是它。
教训是这条**判据**：
> 下次遇到「失忆 / 只会单任务」，**第一步查那个会话的 `mode`**，再看记忆水位 ——
> 前者是「根本没给」，后者是「给了但被砍」，**两者的处置完全不同**。

### 3.7 归属：T0 跟**账户**走，**不跟仓库走**

| 层 | 物理位置 | 换机器 `git clone` 能带走吗 |
|---|---|---|
| **T0 总根** | `~/.workbuddy/user-<account-id>-personal/MEMORY.md` | ❌ **带不走**（不在任何 git 仓库内）|
| **T1 / T2 / T3** | `<工作区>/.workbuddy/memory/…` | ❌ 带不走 |
| **制度与工具** | 仓库 `docs/memory-tree.md` + `scripts/memory-tree-*.py` + 技能 | ✅ **带得走** |

**证据（都是命令跑出来的，不是回忆）**：`git rev-parse --show-toplevel` 在 T0 所在目录报 `not a git repository`；T0 的**邻居是身份 / 人格文件**（`IDENTITY.md` / `SOUL.md` / `USER.md` / `BOOTSTRAP.md`）⇒ 这一层的语义是「**这是谁**」，**不是「这是哪个项目」**；三处记忆树 `rev-parse` **全部「不在仓库内」**；仓库 `.gitignore` 明确忽略 `.workbuddy/`。

⇒ **一句话：clone 得到「能力」，得不到「入口」。**
⇒ 后果：在一台空白机器上装完，**代码能跑、检查器能跑，但没人指路** —— 它不知道「先去读工作区根」，于是**每个新会话又退回「孤岛」**。
⇒ 所以 **T0 应当是「安装流程的产物」，而不是「某次手工写下的文件」**（此前是后者）。

**⇒ 解法：把 T0 拆成「仓库里的模板」+「安装期的装配」。**

| 谁 | 干什么 |
|---|---|
| **仓库** | 只放**模板**（值一律 `{{...}}` 占位）⇒ **能随 clone 走** |
| **安装脚本** | **查位置 → 展开占位符 → 写进去**（由装机流程自动调用）|
| **一致性检查** | 缺 / 旧 / 未纳管 / **指针指向的目标不存在** ⇒ 每次自检**显形** |

**三条规矩**（每条都对应一种已经发生过的病）：

1. **位置是「查出来的」，不是「写死的」** —— 账号目录里的 id 随账号 / 机器变 ⇒ 先读本机配置精确命中，读不到再退回通配（**与既有的水位工具同一口径，不另写一套**）⇒ 绝不把某台机器的 id 写进仓库（否则换机就装到别人家 / 装不上）。
2. **只维护「受管块」，块外内容一个字不动** —— 文件不存在 ⇒ 生成；已有块 ⇒ **只换块内**（本机手工补的留在块外，更新时不丢）；**没有块 ⇒ 默认什么都不做**（那是别人手工写的），要接管得**显式声明且先完整备份**。
3. **指针指向的目标必须「真的存在」** —— 本机有记忆树就直指本机；没有就**降级指向随仓库的制度真源**，并把「降级了」**打印出来**（`--check` 也会校验地址可达）。

> ★ 这条降级链同时划清了**能克隆的边界**：
> **能克隆的是「指路能力 + 制度」，不是某台机器的业务记忆。**
> 克隆者拿到的是「同样的入口、同样的纪律」，他的业务层当然是他自己的。

### 3.8 可移植性：到别的 agent 大概长什么样（⚠ **未实测**，推演）

| 本页这层 | 到别处对应什么 | 差异 |
|---|---|---|
| **T0 总根**（账户级）| Claude Code：`~/.claude/CLAUDE.md`（全局层）| ✅ 有等价物 |
| **T0 总根** | `AGENTS.md` 生态（Codex / Cursor / Copilot…）| ⚠ **没有「仓库之外」的等价物** ⇒ 入口只能落在**仓库根**，少一层 |
| **T2 任务根** | 仓库根 `AGENTS.md` / `CLAUDE.md` | 他们的注入**按目录树嵌套**（根 + 子目录）；我们是**按工作区 / 用户 / 任务三段** |
| **T1 图书馆** | 无对应物（得自建）| ⚠ 但机制一样：一个**不注入**的索引文件 |
| **T3 层 / 正文** | 子目录 `AGENTS.md`、或被引用的文档 | ✅ 同样「不注入、要真去读」 |
| **检查器三件套** | 与平台无关 | ✅ **直接抄** |

⇒ 形状不同（**他们按目录树，我们按工作区三处**），但两者都能表达「根有界 + 层按需」。差的只是那两个问题的答案：**根在哪、根能多大。**

**可移植的那一半**（与平台无关）：纪律（根有界 / 层可增殖 / 指针只指路不复述 / `reads` 设计期声明 / 运行期只许升不许降 / 断链 fail-closed / 增长靠代偿 / **自指向必须放在「不注入的那一层」**）、判据（§1.3 那一句）、工具（纯标准库，换平台直接抄，真正要改的只是路径常量）。

**必须重测的那一半**（换平台先量这 4 件事）：

| # | 要测什么 | 它决定什么 | 本平台实测值 |
|---|---|---|---|
| 1 | **注入点有几个、在哪** | 决定「根」**能放在哪里** | **维度 2 / 落点 7**（见 §3.1、§3.3）；任务记忆**不是**注入点 |
| 2 | **每处的预算多大** | 决定「根」**能长到多大** | 项目级 10000 / 用户级 4000 字符 |
| 3 | **超限怎么表现** | 静默截断 ⇒ **必须自己亮红灯** | **项目级会明说**（见下），用户级近乎静默 |
| 4 | **被引文件 / 子目录会不会被连带注入** | 决定「**分层到底省不省预算**」 | **不注入**（口令探针实测 ✅）|

★ **第 3、4 项最容易被当成常识带过，却最该亲手测** —— 它们错了，整套设计的收益就是零。

**⚠ 修正一条已经过期的事实（它就发生在本页）**：旧版是「项目级超限**静默砍尾**」。**当前客户端会追加一段**：

```
... (memory truncated — MEMORY.md is too large) **ACTION REQUIRED**:
Your MEMORY.md has exceeded the size limit and was truncated during injection.
Before proceeding … you MUST first clean up MEMORY.md …
```

⇒ **项目级 ⇒ 对 agent 明说**（它会被通知去瘦身）；**用户级 ⇒ 仍近乎静默**（只在结尾加 ` (user memory truncated)`）。
⇒ 但**自设更紧的线依然必要**：前者只在**已经被砍**之后才响，而「被砍」本身就是事故。

**⚠ 版本敏感**：以上是**当前客户端版本**的行为。客户端升级会改它（上面那条就是这么变过去的）⇒
**本文所有「平台行为」都要标版本、可复测** —— 这正是 §4.5 那套自检存在的原因。

### 3.9 可控性清单：哪些能改、哪些不能

| 想控制什么 | 能不能 | 怎么控制 |
|---|---|---|
| 记忆**内容** | ✅ 完全可控 | 自己写文件 |
| 注入**哪一份项目记忆** | ✅ 可控 | **由会话的 cwd 决定** —— 从哪个文件夹起会话 |
| `.workbuddy` 这层**目录名** | ✅ 可控 | 环境变量 `WORKBUDDY_DATA_FOLDER_NAME`（改不到 cwd 本身）|
| **全关**本地记忆 | ✅ 可控 | 配置键 **`disableLocalSkillsMemory: true`** ⇒ 项目级 + 用户级一起清空 |
| 注入**上限** | ❌ 不可控 | 硬编码 |

⇒ 读懂这张表，就知道**哪些问题该通过「改文件」解决、哪些只能通过「改行为」解决**。

## 四、怎么让它一直活着

结构立起来不等于它会一直对。这一节是「**让它活着**」的四件事：写入侧纪律、守卫、分发、老化。

### 4.1 写入侧纪律（**比「轮转 / 精简」更根本**）

工具只能事后瘦身；**真正的解在写的时候**。四条纪律，每条都对应一次实测事故：

| # | 纪律 | 事故（实测） |
|---|---|---|
| 1 | **只写「不读它产出会变错」的东西**（事实与判据）；**不写操作步骤**（步骤归技能 / prompt）| 记忆里混进了「怎么跑」的步骤 ⇒ 与技能里的流程**两份真源** |
| 2 | **不抄按天流水** | 某任务记忆长到 **200 KB / 1,172 行**（77 轮）—— ★ 它不进注入，但平台要求**每轮开工先 Read 一遍** ⇒ 越大**每轮白烧的上下文越多** |
| 3 | **同一条告警只记「首次 + 计数」**，不每轮重复 | 同一条「某依赖未挂载」被抄了 **约 60 遍** —— 纯体积，零信息增量 |
| 4 | **叶子 / 正文里不许出现「创建 / 重建指令」** | L3 里「任务可由 agent 一键重建」这种表述，被改造型会话读到就可能**真的去建** |

**★ 这些纪律「放在哪」也是设计的一部分 —— 放在被写的那份文件自己的头部**（受管块）：

- 它读的就是这份文件 ⇒ **纪律在「被写的东西旁边」**，比在长提示词里贴身；
- 任务提示被重建、换了任务，纪律**不会丢**；
- 由**每日的轮转动作维护** ⇒ **新出现的任务记忆自动获得**，不必逐个去改平台任务。

块内三条：**只写 3 行以内**（日期 + 一行结果 + 关键计数）／**重复写「同前第 N 次」**（实测有文件 **6/13 轮**在重抄同一句前置语）／**要长期留的规则写进层正文或技能，不要堆在这里**。

**关于第 4 条的一个追问：克隆一台机器，会不会把定时任务「顺手建出来」？**
**结论：不会**，而且原因分三层（每层都要说清，否则容易安心错）：

| 层 | 事实（实测） |
|---|---|
| **记忆侧** | `tree/` 下的叶子**不注入**（口令探针）+ **记忆不在 git**（clone 带不走）⇒ 克隆机**根本接触不到**叶子 |
| **任务侧** | **任务本身不随账号也不随仓库走**：任务存本机会话库；同步通道只同步对话记录与云端画像（「换机能带走任务」是**网传误解**）|
| **残余风险** | ① 仓库里的**任务快照**随 clone 走；② 重建技能**能一键重建**；③ 本机改造型会话读 L3 会看到「可一键重建」的表述 |

⇒ **真正的缺口是：缺一张「任务 → 哪台机器跑」的策略表。** 现有的只是**技能里的一句提醒** —— **提醒不是闸门**。
⇒ 加固（已做）：含「任务」表述的叶子**统一加硬边界** ——「本节只陈述事实；创建 / 重建任务**不在记忆职责内**；**不要因为快照里有就建出来**」。

### 4.2 守卫：**什么时候查、谁能拦**

「守卫能不能不靠定时任务，而是**嵌进流程**？」答案是**可以，而且平台原生就支持**。
但「能不能拦」必须**按层分开**说，否则会把自己锁在门外。

| 层 | 挂在哪 | 时机 | 能不能拦 | 覆盖什么 |
|---|---|---|---|---|
| **L1 平台 hook** | `PostToolUse`（matcher `Write\|Edit\|Bash`）| 工具**改完**记忆文件后 | 不拦；用 `additionalContext` **把结果塞进上下文** | agent 用工具改记忆 |
| **L1′ 平台 hook** | `UserPromptSubmit` | **每一轮**用户输入时 | 不拦；同上 | 最接近「每次注入前后」的位置 |
| **L2 脚本内建** | 分叶 / 瘦身 / 轮转等**记忆写脚本自身** | 手术**前** + **后** | ✅ **能拦**（fail-closed）| 脚本自己写文件 |
| **L3 推送前** | `preflight` | 推送前 | ✅ 能拦 | 一切「要进仓库」的改动 |
| **L4 定时** | 挂在**已有**的每日任务里 | 每天定时 | 只报 | 兜底 —— **L1 只在「有会话时」站岗、L3 只在「推送前」站岗 ⇒ 无人值守期间没有检测** |

★ **L4 的实现方式本身就是一条纪律**：挂在**已有**任务上，**零新增定时任务**。

#### ★ 为什么 L1 **刻意不做拦截**（本节最要紧的一段）

hook 协议确实允许 `PreToolUse` 返回 `{"permissionDecision":"deny"}` 直接**毙掉**这次工具调用。但**不用它**，两条理由：

1. **记忆树「变红」的修法，就是去编辑记忆文件** —— 根超预算要瘦身、断链要改地址、孤儿要加一行。
   一旦 `deny`，就把**唯一的修法**堵死了：**自己把自己锁在门外**。
2. `"ask"` 会弹确认框 ⇒ **无人值守的定时任务会原地卡死** —— 正是最怕的那种失败形态。

⇒ 分工：**hook 只负责「让当事人看见」；「拦」交给 L2** —— 脚本**知道自己的意图**（分叶 / 瘦身 / 轮转 = 结构手术），**在已损坏的结构上动手术**才是真危险，那里 fail-closed 合理；而「编辑根去修红」是**修复动作**，不该被拦。

#### 可直接照抄的配置（`hooks` 键）

```jsonc
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Write|Edit|Bash",
        "hooks": [ { "type": "command",
                     "command": "\"<PY>\" \"<仓库>/scripts/memory-tree-check.py\" --guard",
                     "timeout": 20 } ] }
    ],
    "UserPromptSubmit": [
      { "hooks": [ { "type": "command",
                     "command": "\"<PY>\" \"<仓库>/scripts/memory-tree-check.py\" --guard",
                     "timeout": 20 } ] }
    ]
  }
}
```

**守卫的行为**（四条路径已实测）：

| 输入 | 行为 |
|---|---|
| 与记忆无关的改动 | **完全静默**（连 stdout 都不写）|
| 载荷坏掉 / 自检跑不成 | 输出 `systemMessage` 明说「**判不了 ≠ 通过**」（**不许静默**）|
| 碰到的根**全绿** | 静默 |
| 碰到的根**有红灯** | 输出 `additionalContext`（进上下文），**退出码恒 0**（不阻断）|

**落地注意（四条都是踩过或文档明写的坑）**：

- **Windows 强制 Git Bash** 执行 hook 命令（不支持 cmd / PowerShell）⇒ 命令要 bash 兼容。
- **配置是「启动快照」**：直接改设置文件**不立即生效** —— 但实测它**不需要重启**也已生效（改完在下一个事件就跑了）⇒ 不必等重启，但要知道它捕获时机不确定。
- **frontmatter hooks 默认不注册**：技能 / agent 的 frontmatter 里写 `hooks:` 需要先设 `{"allowUntrustedFrontmatterHooks": true}`，否则**静默不生效**。
- 配置位置随产品目录名走（CLI 品牌是 `~/.codebuddy/`，桌面客户端是 `~/.workbuddy/`）⇒ **以本机 configDir 为准，挂之前先实测一条最小 hook**。

**与既有纪律的关系**：守卫**不改变**「检查器只报红、处置由人裁决」这条纪律 —— 它只是把「报」从**定时 / 推送前**挪到了**操作发生的那一刻**。**唯一能主动拦的仍是 L2 / L3**，而它们拦的都是「明确危险的意图」。

### 4.3 分发：hook 是第二样「clone 带不走的东西」

hook 配在**本机**设置文件里，而且命令里**必须含本机绝对路径**（仓库在哪、解释器在哪）—— 仓库里那份当然可以写死，但**换机就指到不存在的文件**。
⇒ 和 T0 一模一样的处境：**clone 得到「能力」，得不到「入口」**。
⇒ 而且它的失效是**静默**的：脚本不在 ⇒ 钩子层的错 ⇒ **对话里看不见**，只在日志里。

**解法：安装期装配**（与 T0 同一套路）。

| 件 | 在哪 | 作用 |
|---|---|---|
| **模板 / 生成器** | 仓库里的装配脚本 | 装机时探本机路径，**拼出命令** |
| **认领标记** | 命令里含守卫脚本名 | 只认领自己的条目，**别人的 hook 原样保留** |
| **可达性检查** | 同一脚本的 `--check` | 仓库挪位 / 解释器被换 ⇒ **当场报红** |

要点：

- 解释器候选**装机时探**：① 跑这个脚本的那个解释器 ② 配置文件里的路径 ③ `PATH` 里的 `python3` / `python`，最后再兜一层 `command -v`。**仓库里不留任何一台机器的绝对路径。**
- **写前先备份**；合并时只摘「自己那条」（同组里别人写的也留着），其它顶层键逐键不动。
- 装完**复查一次可达性**（写完再读回来查），不靠「应该没问题」。
- 允许只装 T0、不动 hook 配置。

**验证方式：造一台假机器。** 拿「员工机」当被测对象，实测六格（全部真跑）：

| 场景 | 期望 | 结果 |
|---|---|---|
| 设置文件还不存在（首次启动前）| ✗ 明说「守卫无从装载」 | ✅ |
| 设置文件在、但没有我们的 hook | ✗ 未装配 | ✅ |
| 装配到假机器 | ✓ 命令里是**假机器的**路径；别人的键不丢 | ✅ |
| 装完再 check | ✓ | ✅ |
| 把脚本挪走 | ✗ **脚本不存在**（仓库挪过位置？）| ✅ |
| 脚本在、解释器全废 | ✗ **解释器候选全部不可用** | ✅ |

⇒ 「换一台机器还认不认识路」这件事，**可以不需要第二台机器就测出来**。

### 4.4 老化与蒸馏：**只动「流水」，不动「规矩」**

两种会无限增长的东西，两条通道：

| 对象 | 工具 | 动作 | 触发 |
|---|---|---|---|
| **任务记忆**（`automations/<id>/memory.md`）| 轮转 | 超 **7 天**的旧轮次 **移进归档** | 每日任务 |
| **工作区日期日志**（`memory/YYYY-MM-DD.md`）| 蒸馏 | 超 **50 KB** 且**不在最近 3 天** ⇒ 正文整份进归档，本体只留**条目索引** | 每日任务 |

**为什么「只留标题」够用**：这类日志的**标题本身就是要点**（例：`## 09:54–10:10 · ★ 分隔符收敛（业务方拍板）：从 4 种 → 2 种`）⇒ 索引**可导航**，正文**一字未丢**。

**三条不变量**（两条通道都不得违背）：

1. **归档不删** —— 且归档目录放在 `memory/` **之外**（否则会被平台当成记忆扫进去，自找麻烦）；
2. **写前备份**；
3. **只动「轮次」，不动「规矩」** —— `tree/` 结构一字不动；规则块永久保留。

**★ 一个真 bug（老化在最需要它的文件上等于没跑）**：
规则块判据原是「**块内出现标题行（`#`）⇒ 视为规则，永久保留**」。而日报式任务记忆的**每轮块首行就是标题** ⇒ 逐轮日志被**当成规则**、永不归档 ⇒ 两份偏大的（复审 **9302 字** / 统计 **9576 字**）报的是「**无需轮转**」= **不报错、但什么也没做**的假绿。
**新判据**：看**首个标题行的文字里有没有日期** —— 带日期 ⇒ 轮次记录（可老化）；不带 ⇒ 结构性章节（永久保留）；整块无标题 ⇒ 自带日期算日志，否则**跟随上一块**（多段规则的第二段不该被切开）。
取向：**宁可少归档，不可误永久**（误判成「日志」最多少读一段旧流水；误判成「规则」则**永不收缩**）。
**修后**：复审 **16.2 → 10.0 KB**、统计 **16.3 → 13.6 KB** ⇒ 都回到自设触发线内。

**★ 死红与假绿，是一体两面**：
- **死红**：尺子与处理通道**不同源** —— 例如水位尺去量「今天还在写的那份日志」⇒ **每天必然一条红** ⇒ 红项多了人就开始忽略它。
  ⇒ 修法：**判定窗口与处理窗口取同一个数**（同一个常量），并且明说「报了红就有通道处理它」。
- **假绿**：尺子**量错了对象** —— 例如定位记忆目录时候选少了一层，量到的是另一个（空的）目录 ⇒ 报「0/8500 ✓」，而真正被注入的那份**从没被量过**。
  ⇒ 修法：候选**与其它工具同口径**（同一件事只许一个判据）+ **优先选真有 `MEMORY.md` 的候选** + **把「还有哪些记忆目录」显形**（只报不判失败）。

**★ 两把尺子，两种问题 —— 别指望单一工具包揽：**

| 对象 | 谁管 | 为什么 |
|---|---|---|
| **任务级流水** | **精简 / 轮转 / 蒸馏**（工具）| 它的判据是「按天流水 → 摘要」，正好对得上 |
| **根（路由表）** | **检查器 + 代偿**（**不是**精简器）| 根是**结构化路由表**，精简器会把它当「规则块」整份保留 ⇒ 对它零作用。这是**有意的保守**：**宁可不动，也不能把路由表压成散文**（散文更难跟、更容易漂）|

⇒ 一句话：**精简器管「流水」，检查器 + 代偿管「根」。**

### 4.5 把「平台事实」变成**可重跑的自检**

§三 记的都是**平台侧事实**（注入源、上限、谁进谁不进），而它们是**会变的** —— 平台升级客户端就会改（§3.8 那条就变过）。

⇒ 所以：**把结论逐条变成对客户端代码的断言（13 条）**，挂进已有的自检通道。

| 组 | 断言（示例）|
|---|---|
| 注入面 | 项目级上限 **10000**（`var El=1e4` 紧邻 `MemoryCollector`）｜用户级 **4000** ｜**段内无 `automations`** ｜`quick` 模式**全不注入** ｜工作区记忆目录 = `<会话 cwd>/.workbuddy/memory` |
| 任务记忆 | 路径函数**全库只有 2 处引用** ｜提示原文是**开工 Read / 收工 Write** ｜该链路**无 `readFileSync`** |
| 身份层 | 四个内容变量**每份都过 `truncateContent`** ｜`xl = 1e4` ｜**专家模式下 `IDENTITY` 不注入** ｜模板渲染四变量 | 

**三态分明**（不许含糊）：

| 情形 | 输出 | 退出码 |
|---|---|---|
| 断言全部成立 | `✓ 平台事实与实测一致` | 0 |
| **找不到客户端安装位** | `○ 本次未检查` —— **这不是通过** | 0（不假装红）|
| **找到了但断言不成立** | `✗ 平台事实变了`（逐条说「哪条、实测什么、为什么盯它」）| 1 |
| **显式指定的路径不存在** | `✗ 本次没查成`（是你给错了，不是本机查不了）| 2 |

★ **判据：「写进文档」不等于「进了护栏」。**
文档靠「**有人读**」生效，护栏靠「**每次跑**」生效。只在文档里写着的结论，在「没人读、也没人重跑」时等于不存在。
这条的代价是实测出来的：同一类结论**短期内错了两次**（把任务记忆当注入层、把身份层说成「无上限」），而且第一次连**证据本身都是方法错**（小写 `grep` 漏搜）。

**它覆盖不到的地方（诚实标注）**：自检只能验「**注入通道存在**」（谁读、读到什么、上限多少），**验不了「多久挂一次」** —— §3.3 第 4 条那个「每轮 vs 每会话」的问题，**转录不持久化每轮附加物** ⇒ 靠读文件**永远证不了频率**。那条结论**仍靠人工观察**。

### 4.6 每轮一句：治的是「对话久了走样」

「对话久了回复就变差」是**轮次级**衰减 —— 每会话一次的那几层（T0 / 工作区根 / 身份层）会随时间被稀释，只有**每轮都挂一次**的通道治得了它：`UserPromptSubmit`。

实现要点（三条都有理由）：

1. 放在**已有的守卫里**（同一次运行多打一句 `additionalContext`）—— **不新增进程**；
2. 文案**从唯一真源取**（一处片段文件里的那一行），**不在代码里另写一份**；
3. **取不到就返回空，不臆造兜底话术** —— 兜底只会掩盖「真源没了」。

实测：`UserPromptSubmit` ⇒ 带 **75 字**提醒；`PostToolUse` 与记忆无关 / 全绿 ⇒ **仍然完全静默**。

### 4.7 保留流程：让「重要结论」真的进树

结构有检查器（根预算 / 断链 / 孤儿 / 路由 / 叶子超限），**内容没有**。实测两次自检：

| 自检 | 结果 |
|---|---|
| **18 个**关键概念对照三处（`tree/` / 当日日志 / 公开稿） | **只有 1 个**在树里 |
| 「水位扩容」7 项结论 | 制度真源缺 4 项，`tree/` 一项都没有 |

⇒ **丢的都是"决策"，不是"流程"**（为什么定 **6000** 而不顶格、凭什么 ×4~5、旧系统堵在哪）。
事后补的日志记得住"今天改了什么"，记不住"**今天想通了什么**"。

根因不是"忘了"，是**三层都缺**：**捕获**（结论产生在对话里，日志是事后补记）、
**验收**（六个检查器全查结构，"该收没收"不会红）、**判据**（"重要"没有可执行标准 ⇒ 靠感觉，感觉良好时必漏）。

**三层机制**

1. **捕获：待收箱**（`<根>/_inbox.md`，**与 `MEMORY.md` 同级、不放 `tree/` 里**）——
   产生"结论级"内容时**立刻写一行**。★ **捕获时不分层**：当场判断"该进哪层"最容易错，**先收，后判**。
   放 `tree/` 里会被孤儿检查判红 —— **一个缓冲区不该逼着扫描器开特例**。
2. **验收：检查器第 7 项「待收箱」** —— 有 **>3 天**未处理的项 ⇒ **报红**；
   inbox 存在且空 ⇒ ✅；**没有 inbox ⇒ ✅ 但印"未启用"**（不启用 ≠ 通过）。
3. **对账：收尾时做一次** —— 当日日志里的 ★★ 级结论，逐条查 `tree/` 能否检索到。
   机械部分可脚本化，判断部分由人裁。

**硬约束：不许只进不出，且三个出口权限不同**

| 出口 | 谁做 | 为什么 |
|---|---|---|
| 收进某层 | agent 可自行做 | **可回滚**：收错了下次读不到，不是内容没了 |
| **明确丢弃** | **必须人批** | "不再需要"是**不可逆判断** —— 删了以后没人再想起它 |
| 留待裁决 | 写明等谁 | 续期＝改日期；到期再提醒 |

★ **报红 ≠ 建议删。** 超期只说明"该处理了"，不说明不重要。
**为什么是 3 天**：悬 3 天还没下一步 ⇒ 大概率**不紧急**（不是不重要）—— 调这个数时别把"不紧急"误读成"可丢弃"。
⇒ **没有第 ② 层（报红），第 ① 层不该上**：否则它三个月后就是几百条没人处理的条目，变成第二个"只增不减"的文件。

**边界：为什么不靠「更强的守卫」**

"结论级"仍靠判断 ⇒ 这一层**必漏**；检查器只能查**有没有处理**，查不出**处理得对不对**
（收进树但收错层，它不报）。造更复杂的守卫去判语义，会同时得到**假绿**（它说对了、其实错了）
+ **依赖**（人不再看）。

> ★ **凡是守卫能判的，交给守卫；凡是守卫判不了的，不要造更复杂的守卫去假装能判。**

**三样不依赖守卫的手段（都不新增机制）**：**可回滚**（收错层只是"下次读不到"）、
**收进时写一句"为什么归这层"**（错了能定位哪一步判断错）、**抽样复核**（每 N 条抽 1 条，能发现系统性偏差）。

**守卫的两种失败：假红与假绿（假绿更危险）**

| 失败 | 后果 | 有没有信号 |
|---|---|---|
| **假红**（误报） | 人开始**忽略红**，真红跟着被忽略 | **有**：人会烦、会去查 |
| ★ **假绿**（漏报） | **人不再判断**，错误直接通过 | ★ **没有**：看起来一切正常 |

★ **假绿更危险，恰恰因为它不吵。** 由此得到一条比"结构 vs 语义"更好用的判据：

> **不看"能不能判"，看"判错了会怎样"：错了可回滚的，交给机器；错了不可逆的，必须留给人。**

## 五、怎么算跑绿

### 5.1 六项检查（缺一不可）

| # | 检查 | 红的样子 |
|---|---|---|
| **1** | **根预算恒定** | 根体积**随规则总量增长** ⇒ 又变成伪指针 |
| **2** | **断链** | 目录里的地址，目标不存在 ⇒ **必须报「不知道」，不许当作「没有规则」** |
| **3** | **孤儿正文** | 存在一份正文，**没有任何目录指向它**（★ 最容易漏的方向：大家只查「指出去的在不在」，不查「有没有没人指的」）|
| **4** | **路由可用** | 某类任务声明的层，**不存在或为空** ⇒ 该会话会在「以为读全了」的状态下干活 |
| **5** | **叶子超限** | 单篇正文超过「一次读得完」的量 ⇒ 该再分一层 |
| **6** | **T0 总根预算** | 总根（**注入层之一**）超限 ⇒ **报红** |

> 这六项的共同点：**它们全是「不报错但结果是错的」** —— 与本仓库的主题一致。

**第 5 项为什么需要一个「人为数字」**（最容易含糊过去的地方）：
前几项都是**事实判断**（在 / 不在、被指 / 没被指）；**第 5 项是策略判断** —— 「多大算读不完」。
⇒ **策略值不给出 ⇒ 这一项无法判定 ⇒ 按 fail-closed，整条命令不能算跑绿。** 所以它必须**显式给一个可改的数字**。

**当前默认（策略值，可改）**：

| 项 | 默认 | 说明 |
|---|---|---|
| 根（L0）| **≤ 40 行 且 ≤ 4 KB** | 且根里**不准出现正文段落**（只能有标题 / 路由表 / 地址行）|
| 叶子（正文）| **≤ 12 KB 且 ≤ 300 行** | 超过 ⇒ 该**再分一层** |
| 跨目录引用 | 需显式给搜索根 | 否则一律报断链（**不许默认「可能在外面」就算通过**）|
| 按天日志 | **跳过** | 历史死链无害；报出来只会把检查变成噪音 |

### 5.2 ★ 两条「线」不要混（一条是平台给的，一条是我们自设的）

| 线 | 值 | 来源 | 越线后果 |
|---|---|---|---|
| **平台触发线** | 用户级 **3400 字** / 项目级 **8500 字** | **平台行为**（= 硬上限 × 0.85）| **客户端截断**（项目级会明说、用户级近乎静默）|
| **自设纪律线** | T0 ≤ **2000 字符** / T2 ≤ 40 行或 4 KB | **我们自己定的更紧的线** | 只会**报红**，**不会真丢内容** |

⇒ 为什么要有自设的更紧线：**等撞到平台线就晚了**（撞上就是客户端直接截断，**你收不到任何提示**）。

**T0 取 2000 的依据**（2026-10-17 重裁，**替代原 800**）：

| 项 | 值 | 说明 |
|---|---|---|
| 所在层 | 用户级记忆 | 平台硬限 **4000**、触发线 **3400**（= 硬限 × 0.85） |
| 现行典型值 | **1072** 字符 | 装配后（含入口指针 + 多会话两条）|
| 取 2000 的占比 | 硬限 **50%** / 触发线 **59%** | 不顶格；原 800 是"典型值已越线" |
| 同层其余块 | 约 780 字符 | T0 2000 + 780 ≈ 2780，仍低于触发线 3400（余 620）|
| 越线动作 | 到 **80%（1600）** 出 warn（不 fail）；超 2000 报红 | 顶格不报 = 等于没有上限 |

> ★ **原 800 是怎么来的（记一笔，别再复现）**：代码 `54ad87b`（10-16 **12:06**）先写了这个整数，
> 文档 `7a90cae`（10-16 **12:11**）随后把它写成"自设纪律线"——**中间没有任何裁定记录**；
> 当晚又用"本机已达 799 / 800，几乎顶格"当作这条线正确的实证。
> 这是**阈值自证**：先自己画线，再自己去撞，撞完说"看，线是对的"。
> ⇒ 判据：**任何阈值都必须写清"取值依据 + 谁拍的 + 什么时候重裁"**，否则它会伪装成既定事实。
⇒ ★★ **没有任何「自动压缩」**：文件变长就是变长；**检查器只报红，不会替谁瘦身**。
**瘦身永远是「人（或 agent）主动做的一步」** —— 这正是「检查器 + 人裁决」而不是「自动修复」的原因。
（反过来说：把「不静默」做成了机制，但「处理」仍然必须有人，这**不是缺陷，是分工**。）

**超限怎么办：报红 + 人工裁决**（平台是静默砍，不能照抄；但也不能走向「一律算错」）：
跨工作区的内容，说不准哪天又有了新的实际注入，不能一律当「无用注入」砍掉 ⇒ 规则是：

1. **默认报红**（超限不许静默，也不许默认放行）；
2. **若这次超限是有意的** ⇒ 由管理员批准一次超限，写一份**带时限的豁免**：

```json
// <用户级记忆同目录>/_budget-waiver.json
{"waivers":[{"scope":"T0","limit":900,"approvedBy":"<谁批>","at":"2026-10-16",
             "reason":"跨工作区新增了 X，属于实际注入","until":"2026-11-16"}]}
```
3. 有有效豁免 ⇒ 该项**转「黄」**（通过但**记录在案**，并在输出里印出放宽到多少 / 谁批的 / 为什么 / 到哪天）；
4. **豁免必须有时限** ⇒ 到期**自动重新裁决**（否则「临时批准」会变成「永久放松」）。

### 5.3 ★ 影子根：尺子做出来了，却没人拿去量

六项检查 + 一条命令，**不等于**「每个根真的被查过」。实测暴露过一个更难看的形态：

> **图书馆里登记过的根，检查器根本没读它** ⇒ 那个根有记忆树、有纪律、**永远不被验**。
> 叫它**影子根**：从外面看一切正常，只是**从来没有人量过**。

这条纪律原本只写在文档里 ——「**新增根时回来加一行**」—— 但**没有任何程序去读那一行** ⇒ 那一行只是写给人看的。

**修法**：常驻自检的根清单改成**递归派生**：

| 来源 | 谁写的 | 为什么 |
|---|---|---|
| ① 本机部署位根 | 代码 | 本机主链 |
| ② 跨项目总根（T0）里写的地址 | **人**（安装期装配）| T0 是唯一「每条会话都注入」的层 ⇒ 它说去哪就查哪（改一处，检查范围自己跟着改）|
| ③ **各根图书馆里登记的根**（递归）| **人**（维护时加一行）| ★ 让「登记」这一步**长牙**：登记 ⇒ 自动进入常驻地检范围 |

⇒ 结论：**一条纪律若只有人遵守、没有程序执行，它就只是「建议」。**
接进常驻路径，建议才变成机制（同族教训：水位尺子早就存在，但没人跑它 ⇒ 贴线时无人知晓）。

### 5.4 ★ 假红比不检查更危险

**现象**：层名（`L2`）与文件名（`L2.规则.md`）是**两套**写法。检查器原来只认 `tree/L2.md` ⇒ 一旦有任务声明 `reads: L2`，它会报「`L2.md` 不存在」—— **声明是对的，尺子量错了**。

⇒ 这类**假红**比不检查更危险：**人会开始忽略红**，真红跟着一起被忽略。
⇒ 修法：层名匹配**两种命名都收** —— **声明不变，尺子兼容**。

同族的两种「尺子坏了」：
- **尺子指向了错的对象**（假绿）：见 §4.4 末段。
- **尺子从不被跑**（影子根）：见 §5.3。

### 5.5 怎么验证「一个全新的会话」真的读到了（人工三问）

不想依赖自动化时，开一个新会话，把这三句贴给它：

1. 「**你的根在哪？你需要读哪些层？**」⇒ 应报出记忆根路径 + `reads`（说明 T0 / T2 生效）
2. 「**读不到根的时候你该怎么办？**」⇒ 应答「**报不知道，不当成没有规则**」（说明 fail-closed 生效）
3. 「**你刚才读了哪些文件？为什么读它们？**」⇒ 应说「先根 → 再按声明读层」；**若它多读了，应主动说明并留痕**（说明「只许升不许降 + 留痕」生效）

> ⚠ 一个必须区分的差别：**被约束过的空白 agent ≠ 真实新会话**。
> 前者的读取范围是**被人限定的**（所以它考的只是「结构能不能被读懂」）；后者**没有被限定**（它会自己决定要不要搜索、要不要读别处）。
> ⇒ 要验证「真实新会话会怎么做」，**必须真开一个**。

### 5.6 落地顺序（每步都可单独验证）

| 步 | 做什么 | 验收 |
|---|---|---|
| 1 | **分类**（只搬不改）：把现有记忆按 L1–L4 拆成正文，**原文件变成目录** | 每个地址仍打得开 |
| 2 | **立根**：把根从「指几个文件」改成「**指层 + 一行 `reads:` 声明**」 | 根 ≤ 40 行 / 4 KB |
| 3 | **挂牌**：每个任务定义写一行 `reads:`（未写的按保守档跑并显式提示）；运行时升级要留痕 | 声明可 diff、可 review |
| 4 | **装检查器**：把 §5.1 那几项写成一条命令，**挂进已有的自检入口**（而非新增定时任务）| 两个真实工作区跑到全绿 |

> ★★ **顺序不能颠倒**：检查器**必须等「样板改造跑绿」之后再挂** ——
> 在改造完成前挂上去，系统会**立刻全红**，等于自己造一个假告警（而假红会让人开始忽略红，见 §5.4）。

## 六、踩过的坑（凝炼成判据）

这一节把散在各处的教训收成一张表。**左边是现象，右边是可复用的判据** —— 现象会变，判据不会。

| # | 现象（都是实测）| 根因 | 判据 |
|---|---|---|---|
| 1 | 根越写越长，最后又被撑爆 | 指针指了「规则本身」（伪指针）| **指针的体积是否随规则总量增长？** 长 ⇒ 假指针 |
| 2 | 新造的叶子**从没被查过** | 用**文件名正则**认叶子，子片名不匹配 ⇒ 检查盲区 | **判据要用「结构」不用「命名」**（同名目录存在 ⇒ 目录节点）|
| 3 | 图书馆里登记的根，从来没人量 | 纪律只写在文档里，**没有程序去读那一行** | **一条纪律若只有人遵守、没有程序执行，它就只是「建议」** |
| 4 | 检查器报「`L2.md` 不存在」，但声明是对的 | 层名与文件名是两套写法 | **假红比不检查更危险** —— 人会开始忽略红 |
| 5 | 「没纳管」的文件被**覆盖**了 | `split_managed()` 在「没有块」时返回**空串**而非 `None` ⇒ 被当成「块是空的」| **「受管块 + fail-closed」必须配一组能跑的自测**，否则只是一纸安全 |
| 6 | 守卫报「载荷解析失败」 | hook 子进程是**净化环境**（无 `PYTHONUTF8`）⇒ Windows 上退回 gbk ⇒ **一个汉字的第三字节吃掉紧随的引号** | **「我自己测通过」不构成证据 —— 测试环境的干净程度本身就是被测对象** |
| 7 | 守卫**静默不跑** | 预筛只认正斜杠，而 JSON 里 Windows 路径是**双反斜杠** | **预筛宁可漏网（多跑），不可漏判（不跑）** —— 前者 0.6 秒，后者是假绿 |
| 8 | 诊断退化成含糊的「配置不一致」 | 拿「本该长什么样」去判可达性 ⇒ 永远只看到正确的那条 | **诊断要基于「盘上现状」，不是「合并后的结果」** |
| 9 | 造红探针「该红没红」三条一起哑 | 推导路径排在显式指定**前面** ⇒ 显式被静默忽略 | **显式指定必须压过推导** —— 这类错的形态是「连报错都没有」|
| 10 | 老化**在最需要它的两份文件上等于没跑** | 「块内有 `#` 即规则」⇒ 日报式文件的每轮块首行就是标题 ⇒ 永不归档 | **宁可少归档，不可误永久**（误判成「规则」则永不收缩）|
| 11 | 纪律块装了两次，第二次把轮次块吸进标题 | 摘除旧块时**连空行一起吃掉** ⇒ 不是不动点 | **幂等要能被自测证明**（`f(f(x)) == f(x)`）|
| 12 | 备份累积到 700 KB，而**清理从没跑过** | 清理写在「需要轮转」的分支里 ⇒ 「没活干」时早退 | **「清理」必须与「业务条件」解耦** —— 该不该清取决于它自己有几份 |
| 13 | 同一处判据出现三份，**修了一处另两处没修** | 复制了函数而不是复用 | **同一件事只许一个判据**（要么 import，要么参数化；**不许复制**）|
| 14 | 水位尺报「项目 0/8500 ✓」= **假绿** | 定位候选**少了一层** ⇒ 量到另一个（空的）目录 | **假绿比不报更危险**；候选要与其它工具**同口径**、且优先选「真有 `MEMORY.md`」的那个 |
| 15 | 「显形」功能一次都没跑过，却看着像在跑 | `NameError` 被**裸 `except`** 静默吞成 no-op | **裸 `except` 不许静默** —— 它会把「我写错了」伪装成「这本就没有」|
| 16 | 水位尺**每天必报一条红** | 判定窗口（含今天）≠ 处理窗口 | **判断窗口与处理窗口必须同源**，否则红项会变成噪声 |
| 17 | 错说法被当成「有证据」的结论 | `grep automationMemory` **大小写敏感**漏搜，真名带大写 | **证据与被证的事必须同源**，否则重跑那条 grep 会以为结论也错了 |
| 18 | 同一类事实错**短期内两次** | 结论只写在**文档**里，没人重跑 | **「写进文档」不等于「进了护栏」** —— 文档靠「有人读」生效，护栏靠「每次跑」生效 |
| 19 | 同一件事有**两份正文**，给出**相反**规则 | 两份都被改过、彼此不知情（并存了一整天）| **改一份不会让另一份变红 ⇒ 合并成一处比「记得同步」可靠** |
| 20 | 提交说明里写了「已改」，文件其实没动 | 编辑脚本**解析阶段就报错**（内层 ASCII 引号）⇒ 整段没执行 | **先解析整个文件再执行** ⇒ 语法错误意味着**一个字都没动**，不是「改了一半」|

## 七、边界与未决

- **样本 n = 1 台机器、10 天**。「L3 占 30%」是**实测**，但「不读 L3 就有收益」**尚未实测**。
- **平台行为都是版本敏感的**：本文所有平台事实取自**当前客户端版本**（本机构建于取证当日）。
  客户端升级会改它 —— 这正是 §4.5 那套断言存在的理由：**它一红就说明「该人复核了」**。
- **跨平台未实测**：§3.8 的可移植性判断**是推演，不是实测**；其中「别的 agent 长什么样」依据的是它们各自的公开约定，**我们没在那上面跑过**。
- **这套东西只在「规则总量确实超过了根预算」时才有必要** —— **规则不多的项目照抄只会自找复杂。**
- **「写」那一半（孤岛回收）仍是半自动**：约定 + 巡检清单已有，归并仍需人裁。
- **未决**：`reads:` 与技能的覆盖关系（任务定义为主；技能能否覆盖、谁优先，需要一条明文）——
  准则同前：**同一份判断只能有一个权威来源**，否则又是「多份真源」。
