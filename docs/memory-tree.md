# 记忆树：根有界、层可增殖、按任务路由

> 本页回答三个问题：
> **① 指针该指向「规则本身」还是「规则类」？② 一个会话怎么知道自己该读哪些层？③ 怎么验证这套结构是活的？**
> 结论来自一台跑了 10 天的机器的实测（见 [记忆漂移](memory-drift.md)）。

---

## 零、一句话

**根必须严格有界，层可以无限增殖；而且"该读哪些层"必须由任务在【设计期声明】，不能靠会话在运行时猜。**
（运行时只许**升**，不许**降** —— 见 §三。）

---

## 一、★ 两种指法：天大的区别

「薄指针」有两个版本，长得像，本质完全不同：

| | **A. 指向「规则本身」** | **B. 指向「规则类」** |
|---|---|---|
| 指针里写什么 | 规则内容（或规则的逐条清单） | 只写"**存在一个可增殖的容器**"（类别 / 手册 / 目录） |
| 体量 | **随规则总量增长** | **与规则总量解耦** |
| 结果 | 记忆空间**又被灌满**——只是把"一份记忆"换成"另一份记忆" | **可无限增殖** |
| 代价 | 看起来"读一次就够" | **必须进去看才知道里面有什么**（进去之前，它是薛定谔的猫） |

### 判据（可检查，不靠感觉）

> **这个指针的体积，是否随规则总量增长？**
> **不增长 ⇒ 真指针（B）；增长 ⇒ 伪指针（A）。**

A 的问题不在"不够薄"，而在于它是**平移**：规则一多，指针自己就变成新的瓶颈。
于是你会需要"给指针的指针"——**这正是自指向的正当来源**，而 B 是它唯一稳定的形态。

### 关于"省资源"的准确说法

业界的理由通常是「规则文件要省 token」。**这句话在这种场景下是错的**：

- 真正稀缺的是**常驻注入预算**（每个会话都有硬上限，且**超限静默截断**）；
- 算力／按需读取是**相对充裕**的。

⇒ 所以这不是"省资源"，是**资源置换**：
**拿充裕的（算力）去换稀缺的（常驻预算），并买回一样更重要的东西——可增殖性。**

⇒ 这也解释了为什么"薄指针只写进记忆里"不管用：**省下来的预算是为了让根能承载"路由"，不是为了省。**

## 二、层：一个会话到底该读哪些层

把记忆按**"不懂它，产出会不会变错"**分层（不是按主题分，按"对哪些任务必要"分）：

| 层 | 内容 | 谁读 |
|---|---|---|
| **L1 业务层** | 口径 / 阈值 / 业务单元 / 命名规则 / 数据源 | **所有任务**（含纯机械任务）|
| **L2 规则层** | 判断规则 / 审核规则 / 异常判据 / 状态机 / **脚本实现细节**（如站点选择器要点）| **判定类任务** |
| **L3 设计层** | 为什么这样设计 / 技术方案 / 并发模型 / 分支策略 / 历史决策 | **只有改造类与设计类任务** |
| **L4 运行配置** | 脚本路径 / 产物位置 / 资料库归档 / 调度 | **按需**（见下）|

**关于 L4 为什么要单列**（这是一处容易搞错的地方）：

它**所有"要跑东西"的任务都必读**，看起来像 L1；但**性质不是业务**，而且
**新开一个会话压根不会涉及它**（人问一句话，不需要知道产物落在哪个目录）。
⇒ 所以它不是"必读层"，而是"**用到才读**"的层。

⇒ **单列的理由是防止"必读面被越推越宽"**：一旦把运行配置混进 L1，
L1 会随着系统变大而膨胀（每加一个脚本、每改一次路径，L1 就长一点），
**所有任务的必读面被连带撑大** —— 那正是我们要避免的事。

**关于 L2 包含"脚本实现细节"**（例如站点选择器要点）：判据不是"它像不像业务"，
而是**"不读它，产出会不会变错"** —— 选择器错了，产出（抓不到/抓错）就错了，
且它**直接影响产出效率** ⇒ 归 **L2**，不是 L3。

### 为什么"机械型任务不读 L3"不是偷懒

**因为"怎么跑"已经刻在静态代码里了。** 脚本是确定性的：它按既定流程执行，
**设计理由（为什么这么设计、曾经踩过什么坑）不影响它的产出**。

**实测证据**（同一台机器）：

- 某工作区记忆里，**L3 类内容约占 30%**（WebBridge 会话模型 / 并发治理落地 / 分支策略 / 通用化规范…），
  而跑这个记忆的那些任务里，**大部分是机械型的**（下载、巡检、批量操作）。
- ⇒ **它们每次都在读一段对自己无用的设计史**，而那些设计史恰好又挤占了它们的预算
  ⇒ **这就是"资源滥用"的具体形状：不是读得太多，是读错了层。**

⇒ 于是"省资源"的准确版本是：
**不是"少读"，而是"读对层"** —— 该读的一行不漏，不该读的一行不占。

## 三、路由：会话怎么知道自己需要什么（本设计的本源）

### ★★ 先回答一个陷阱问题：「分类」这件事本身有复杂度，谁来担？

**答案是：不要分类。**

因为所谓"机械型 / 判定型 / 改造型"只是**给人看的说法**；机器真正需要的只有一个东西 ——
**这串层名**。所以把中间那层「先判断我是什么型、再推出该读哪些层」**直接删掉**：

```yaml
# 在每个任务定义 / 技能 frontmatter 里声明（一行）
reads: L1, L2            # 就这一行。不再有"类型"这个中间概念
```

⇒ **复杂度归零**：不需要"分辨"，只需要"声明"。而**声明是静态的** —— 可 review、可 diff、可测试。

### 为什么不由 AI 在运行时自己判断

**不是因为它判不准，而是因为它在一个最没有资格的时刻被要求判断：**

| 时刻 | 它手上有什么 | 判断质量 |
|---|---|---|
| **设计期（人写任务定义时）** | **全貌**：这任务要产出什么、错了谁受影响 | 高 |
| **运行期（AI 决定该读什么）** | **可能已被截断的记忆**，且还不知道里面有什么 | **最低** |

⇒ 让运行时的 AI 判断"我需不需要读规则" —— **是用"不知道自己少了什么"去决定"要不要补齐"**，
这是循环论证，而且**正是本仓库要治的那类病**（没报错，但结果是错的）。

⇒ **复杂度不会消失，只能选择在哪一期支付**：
**放设计期：一次付清，且由最有资格的人付；放运行期：每次运行都付，且由最没资格的时刻付。**

### 三条配套纪律（缺一不可）

**1. 不对称原则：升级自由，降级需批准。**

| 动作 | 允许？ | 为什么 |
|---|---|---|
| 运行时**多读**一层（如机械任务顺手读了 L3）| ✅ **允许，无需批准** | **读多了只是浪费；读少了才是事故** |
| 运行时**少读**一层（如判定任务认为"我不需要 L2"）| ❌ **禁止** | 这是**静默漏读** —— 产出会错，而且不报错 |
| 改声明（把 L2 摘掉）| ✅ 但**只能由人改**，且是一处改动 | 降级是**显式决策**，不是运行时心情 |

**2. 默认必须保守（fail-closed）。**
未声明 `reads:` ⇒ **按保守档执行（L1 + L2）**，并**显式提示"本任务未声明读取层"**。
**绝不默认成"最少读"** —— 默认最小值等于把"漏读"设成默认行为。

**3. 路由表只准有地址，不准有内容。**
一旦有人往根里粘贴规则，根就开始按 §一的"伪指针"增长 ⇒ **根失守**。

### 那张表长什么样（示意，不是机制）

"类型"只作为**说法**保留在这里，方便人读；**机器只认 `reads:` 那串层名**：

| 说法（给人看）| 典型 `reads:` | 判据：**不知道这一层，产出会变错吗？** |
|---|---|---|
| 机械型（跑既定脚本 / 下载 / 采集）| `L1`（+ 要跑东西时加 `L4`）| 不会 —— 流程在代码里 |
| 判定型（复审 / 统计 / 异常判定）| `L1, L2` | **会** —— 判据错了结论就错 |
| 改造型（改脚本 / 技能 / 配置）| `L1, L2, L3`（+ `L4`）| **会** —— 不知道历史约束就会改坏 |
| 设计型（架构决策 / 大改造）| `L1, L2, L3` + 按需检索日志 | **会** —— 且需要"为什么"和"曾发生过什么" |

> ★ 判据仍然是那句问话：**「不知道这一层，产出会不会变错？」**
> 任务名会变，这句问话不会 —— 所以**声明的是层，不是类型**。

## 四、递归同构（自指向的正当用法）

每一层都是**同一个结构**：

```
目录（只指路，严格有界）  →  正文（可以很大，按需读）
                            ↘ 当正文本身也太大 ⇒ 再切一层目录 …… 递归
```

- **可增殖**：只要还能"再切一层"，容量就没有上限；
- **根有界**：根永远只有一张路由表 + 顶层目录；
- **终止条件**：叶子 = **一次能读完**的正文（读不完 ⇒ 说明它该再分一层）。

⇒ 这就是"**用算力换本地可无限性**"的落地形态：代价是每一跳要花一次读取，
收益是**根的体量恒定**——**不再有任何东西能把它撑爆**。

## 五、怎么算"跑绿"（五项检查，缺一不可）

| # | 检查 | 红的样子 |
|---|---|---|
| **1** | **根预算恒定** | 根体积**随规则总量增长** ⇒ 又变成 A 型伪指针 |
| **2** | **断链** | 目录里的地址，目标不存在 ⇒ **必须报"不知道"，不许当作"没有规则"** |
| **3** | **孤儿正文** | 存在一份正文，**没有任何目录指向它**（★ 最容易漏的方向：大家只查"指出去的在不在"，不查"有没有没人指的"）|
| **4** | **路由可用** | 某类任务声明的层，**不存在或为空** ⇒ 该会话会在"以为读全了"的状态下干活 |
| **5** | **叶子超限** | 单篇正文超过"一次读得完"的量 ⇒ 该再分一层（否则就是"分叉 × 截断"的复发） |

> 这五项的共同点：**它们全是"不报错但结果是错的"** —— 与本仓库的主题一致。

## 六、落地顺序（每步都可单独验证）

1. **分类**（只搬不改）：把现有记忆按 L1 / L2 / L3 / L4 拆成正文，**原文件变成目录**。
2. **立根**：把 L0 从"指几个文件"改成"**指层 + 一行 `reads:` 声明**"。
3. **挂牌**：每个任务定义 / 技能写一行 `reads:`（**未写的按保守档 L1+L2 跑，并显式提示**）。
4. **装检查器**：把 §五 五项 + **"声明里的层是否存在"** 写成一条命令，
   挂进已有的自检入口（而非新增定时任务）。

## 七、已定 / 待定

**已定（2026-10-16）**：

1. ✅ **「运行配置」单列一层（L4）** —— 理由：新会话常常**压根不涉及**它，
   用到才读；若并入 L1，L1 会随系统膨胀、把所有任务的必读面连带撑大。
2. ✅ **脚本实现细节（如站点选择器要点）归 L2** —— 判据是它**直接影响产出与效率**，不是"像不像业务"。
3. ✅ **不设"任务类型"这个中间概念** —— 直接声明 `reads:`（层名）；类型只作为给人看的说法。
4. ✅ **分类复杂度放在"设计期"**（人写任务定义时），**不放在运行期**；
   运行期只允许**升**（多读），不允许**降**（少读）。

**待定**：

1. ⬜ **`reads:` 的语法与落点**：写进任务定义、技能 frontmatter，还是两者都支持？
   （倾向：任务定义为主，技能可覆盖 —— 但"谁覆盖谁"要有明文。）
2. ⬜ **"叶子一次能读完"的量化**：多少算"一次能读完"？（需要一个可检查的阈值，否则第 5 项检查跑不绿。）
3. ⬜ **升级算不算"该被记录"**：AI 自主多读了一层，要不要留痕（便于事后判断声明是不是写窄了）？

---

## 八、边界

- 样本 **n = 1 台机器、10 天**；"L3 占 30%"是**实测**，但"不读 L3 就有收益"**尚未实测**（还没落地）。
- 本页是**设计**，不是结论：§五 的检查器目前**不存在**，§六 的四步**只完成了第 0 步（分类方案）**。
- 这套东西只在"规则总量确实超过了根预算"时才有必要 —— **规则不多的项目照抄只会自找复杂。**
