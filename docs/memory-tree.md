# 记忆树：根有界、层可增殖、按任务路由

> 本页回答三个问题：
> **① 指针该指向「规则本身」还是「规则类」？② 一个会话怎么知道自己该读哪些层？③ 怎么验证这套结构是活的？**
> 结论来自一台跑了 10 天的机器的实测（见 [记忆漂移](memory-drift.md)）。

---

## 零、一句话

**根必须严格有界，层可以无限增殖；而且"该读哪些层"必须由任务在【设计期声明】，不能靠会话在运行时猜。**
（运行时只许**升**，不许**降** —— 见 §三。）

---

## 一、★ 两种指法：天大的区别

「薄指针」有两个版本，长得像，本质完全不同：

| | **A. 指向「规则本身」** | **B. 指向「规则类」** |
|---|---|---|
| 指针里写什么 | 规则内容（或规则的逐条清单） | 只写"**存在一个可增殖的容器**"（类别 / 手册 / 目录） |
| 体量 | **随规则总量增长** | **与规则总量解耦** |
| 结果 | 记忆空间**又被灌满**——只是把"一份记忆"换成"另一份记忆" | **可无限增殖** |
| 代价 | 看起来"读一次就够" | **必须进去看才知道里面有什么**（进去之前，它是薛定谔的猫） |

### 判据（可检查，不靠感觉）

> **这个指针的体积，是否随规则总量增长？**
> **不增长 ⇒ 真指针（B）；增长 ⇒ 伪指针（A）。**

A 的问题不在"不够薄"，而在于它是**平移**：规则一多，指针自己就变成新的瓶颈。
于是你会需要"给指针的指针"——**这正是自指向的正当来源**，而 B 是它唯一稳定的形态。

### 关于"省资源"的准确说法

业界的理由通常是「规则文件要省 token」。**这句话在这种场景下是错的**：

- 真正稀缺的是**常驻注入预算**（每个会话都有硬上限，且**超限静默截断**）；
- 算力／按需读取是**相对充裕**的。

⇒ 所以这不是"省资源"，是**资源置换**：
**拿充裕的（算力）去换稀缺的（常驻预算），并买回一样更重要的东西——可增殖性。**

⇒ 这也解释了为什么"薄指针只写进记忆里"不管用：**省下来的预算是为了让根能承载"路由"，不是为了省。**

## 二、层：一个会话到底该读哪些层

把记忆按**"不懂它，产出会不会变错"**分层（不是按主题分，按"对哪些任务必要"分）：

| 层 | 内容 | 谁读 |
|---|---|---|
| **L1 业务层** | 口径 / 阈值 / 业务单元 / 命名规则 / 数据源 | **所有任务**（含纯机械任务）|
| **L2 规则层** | 判断规则 / 审核规则 / 异常判据 / 状态机 / **脚本实现细节**（如站点选择器要点）| **判定类任务** |
| **L3 设计层** | 为什么这样设计 / 技术方案 / 并发模型 / 分支策略 / 历史决策 | **只有改造类与设计类任务** |
| **L4 运行配置** | 脚本路径 / 产物位置 / 资料库归档 / 调度 | **按需**（见下）|

**关于 L4 为什么要单列**（这是一处容易搞错的地方）：

它**所有"要跑东西"的任务都必读**，看起来像 L1；但**性质不是业务**，而且
**新开一个会话压根不会涉及它**（人问一句话，不需要知道产物落在哪个目录）。
⇒ 所以它不是"必读层"，而是"**用到才读**"的层。

⇒ **单列的理由是防止"必读面被越推越宽"**：一旦把运行配置混进 L1，
L1 会随着系统变大而膨胀（每加一个脚本、每改一次路径，L1 就长一点），
**所有任务的必读面被连带撑大** —— 那正是我们要避免的事。

**关于 L2 包含"脚本实现细节"**（例如站点选择器要点）：判据不是"它像不像业务"，
而是**"不读它，产出会不会变错"** —— 选择器错了，产出（抓不到/抓错）就错了，
且它**直接影响产出效率** ⇒ 归 **L2**，不是 L3。

### 为什么"机械型任务不读 L3"不是偷懒

**因为"怎么跑"已经刻在静态代码里了。** 脚本是确定性的：它按既定流程执行，
**设计理由（为什么这么设计、曾经踩过什么坑）不影响它的产出**。

**实测证据**（同一台机器）：

- 某工作区记忆里，**L3 类内容约占 30%**（WebBridge 会话模型 / 并发治理落地 / 分支策略 / 通用化规范…），
  而跑这个记忆的那些任务里，**大部分是机械型的**（下载、巡检、批量操作）。
- ⇒ **它们每次都在读一段对自己无用的设计史**，而那些设计史恰好又挤占了它们的预算
  ⇒ **这就是"资源滥用"的具体形状：不是读得太多，是读错了层。**

⇒ 于是"省资源"的准确版本是：
**不是"少读"，而是"读对层"** —— 该读的一行不漏，不该读的一行不占。

## 三、路由：会话怎么知道自己需要什么（本设计的本源）

### ★★ 先回答一个陷阱问题：「分类」这件事本身有复杂度，谁来担？

**答案是：不要分类。**

因为所谓"机械型 / 判定型 / 改造型"只是**给人看的说法**；机器真正需要的只有一个东西 ——
**这串层名**。所以把中间那层「先判断我是什么型、再推出该读哪些层」**直接删掉**：

```yaml
# 在每个任务定义 / 技能 frontmatter 里声明（一行）
reads: L1, L2            # 就这一行。不再有"类型"这个中间概念
```

⇒ **复杂度归零**：不需要"分辨"，只需要"声明"。而**声明是静态的** —— 可 review、可 diff、可测试。

### 为什么不由 AI 在运行时自己判断

**不是因为它判不准，而是因为它在一个最没有资格的时刻被要求判断：**

| 时刻 | 它手上有什么 | 判断质量 |
|---|---|---|
| **设计期（人写任务定义时）** | **全貌**：这任务要产出什么、错了谁受影响 | 高 |
| **运行期（AI 决定该读什么）** | **可能已被截断的记忆**，且还不知道里面有什么 | **最低** |

⇒ 让运行时的 AI 判断"我需不需要读规则" —— **是用"不知道自己少了什么"去决定"要不要补齐"**，
这是循环论证，而且**正是本仓库要治的那类病**（没报错，但结果是错的）。

⇒ **复杂度不会消失，只能选择在哪一期支付**：
**放设计期：一次付清，且由最有资格的人付；放运行期：每次运行都付，且由最没资格的时刻付。**

### 三条配套纪律（缺一不可）

**1. 不对称原则：升级自由，降级需批准。**

| 动作 | 允许？ | 为什么 |
|---|---|---|
| 运行时**多读**一层（如机械任务顺手读了 L3）| ✅ **允许，无需批准** | **读多了只是浪费；读少了才是事故** |
| 运行时**少读**一层（如判定任务认为"我不需要 L2"）| ❌ **禁止** | 这是**静默漏读** —— 产出会错，而且不报错 |
| 改声明（把 L2 摘掉）| ✅ 但**只能由人改**，且是一处改动 | 降级是**显式决策**，不是运行时心情 |

**2. 默认必须保守（fail-closed）。**
未声明 `reads:` ⇒ **按保守档执行（L1 + L2）**，并**显式提示"本任务未声明读取层"**。
**绝不默认成"最少读"** —— 默认最小值等于把"漏读"设成默认行为。

**3. 路由表只准有地址，不准有内容。**
一旦有人往根里粘贴规则，根就开始按 §一的"伪指针"增长 ⇒ **根失守**。

### 那张表长什么样（示意，不是机制）

"类型"只作为**说法**保留在这里，方便人读；**机器只认 `reads:` 那串层名**：

| 说法（给人看）| 典型 `reads:` | 判据：**不知道这一层，产出会变错吗？** |
|---|---|---|
| 机械型（跑既定脚本 / 下载 / 采集）| `L1`（+ 要跑东西时加 `L4`）| 不会 —— 流程在代码里 |
| 判定型（复审 / 统计 / 异常判定）| `L1, L2` | **会** —— 判据错了结论就错 |
| 改造型（改脚本 / 技能 / 配置）| `L1, L2, L3`（+ `L4`）| **会** —— 不知道历史约束就会改坏 |
| 设计型（架构决策 / 大改造）| `L1, L2, L3` + 按需检索日志 | **会** —— 且需要"为什么"和"曾发生过什么" |

> ★ 判据仍然是那句问话：**「不知道这一层，产出会不会变错？」**
> 任务名会变，这句问话不会 —— 所以**声明的是层，不是类型**。

## 四、递归同构（自指向的正当用法）

每一层都是**同一个结构**：

```
目录（只指路，严格有界）  →  正文（可以很大，按需读）
                            ↘ 当正文本身也太大 ⇒ 再切一层目录 …… 递归
```

- **可增殖**：只要还能"再切一层"，容量就没有上限；
- **根有界**：根永远只有一张路由表 + 顶层目录；
- **终止条件**：叶子 = **一次能读完**的正文（读不完 ⇒ 说明它该再分一层）。

⇒ 这就是"**用算力换本地可无限性**"的落地形态：代价是每一跳要花一次读取，
收益是**根的体量恒定**——**不再有任何东西能把它撑爆**。

## 五、怎么算"跑绿"（五项检查，缺一不可）

| # | 检查 | 红的样子 |
|---|---|---|
| **1** | **根预算恒定** | 根体积**随规则总量增长** ⇒ 又变成 A 型伪指针 |
| **2** | **断链** | 目录里的地址，目标不存在 ⇒ **必须报"不知道"，不许当作"没有规则"** |
| **3** | **孤儿正文** | 存在一份正文，**没有任何目录指向它**（★ 最容易漏的方向：大家只查"指出去的在不在"，不查"有没有没人指的"）|
| **4** | **路由可用** | 某类任务声明的层，**不存在或为空** ⇒ 该会话会在"以为读全了"的状态下干活 |
| **5** | **叶子超限** | 单篇正文超过"一次读得完"的量 ⇒ 该再分一层（否则就是"分叉 × 截断"的复发） |
| **6** | **T0 总根预算** | 总根（**注入层之一**）超限 ⇒ **报红**（★ 见下）|

> 这五项的共同点：**它们全是"不报错但结果是错的"** —— 与本仓库的主题一致。

### 第 5 项为什么需要一个「人为数字」（这是最容易含糊过去的地方）

前 4 项都是**事实判断**（在/不在、被指/没被指）；**第 5 项是策略判断**——"多大算读不完"。

⇒ **策略值不给出 ⇒ 这一项无法判定 ⇒ 按 fail-closed，整条命令不能算跑绿。**
⇒ 所以它必须**显式给一个可改的数字**，而不是"看着差不多"。

**当前默认（策略值，可改）**：

| 项 | 默认 | 说明 |
|---|---|---|
| 根（L0）| **≤ 40 行 且 ≤ 4 KB** | 且根里**不准出现正文段落**（只能有标题 / 路由表 / 地址行）|
| 叶子（正文）| **≤ 12 KB 且 ≤ 300 行** | 超过 ⇒ 该**再分一层** |
| 跨目录引用 | 需显式给搜索根 | 否则一律报断链（**不许默认"可能在外面"就算通过**）|
| 按天日志 | **跳过** | 历史死链无害；报出来只会把检查变成噪音 ⇒ 没人看 |

**已可执行**：本页的五项 + T0 预算已实现为一条命令（`memory-tree-check.py`，fail-closed）；
在两个真实工作区上跑到**全绿**，在未改造的记忆上**全红且"结构未建立"报「判不了」而非默认通过**。

### ★ 两条「线」不要混（一条是平台给的，一条是我们自设的）

| 线 | 值 | 来源 | 越线后果 |
|---|---|---|---|
| **平台触发线** | 用户级 **3400 字** / 项目级 **8500 字** | **平台行为**（实测重标得出）| **客户端按字符静默截断**（尾部悄悄丢，不报错）|
| **自设纪律线** | T0 ≤ **800 字符** / T2 ≤ 40 行或 4KB | **我们自己定的更紧的线** | 只会**报红**，**不会真丢内容** |

⇒ 为什么要有自设的更紧线：**等撞到平台线就晚了** —— 那是静默截断，**没有第二次机会**。

⇒ ★★ **没有任何"自动压缩"**：文件变长就是变长；**检查器只报红，不会替谁瘦身**。
**瘦身永远是"人（或 agent）主动做的一步"** —— 这正是"检查器 + 人裁决"而不是"自动修复"的原因。
（反过来说：把"不静默"做成了机制，但"处理"仍然必须有人，这**不是缺陷，是分工**。）

### 怎么验证「一个全新的会话」真的读到了（人工三问）

不想依赖自动化时，开一个新会话，把这三句贴给它：

1. 「**你的根在哪？你需要读哪些层？**」⇒ 应报出记忆根路径 + `reads`（说明 T0/T2 生效）
2. 「**读不到根的时候你该怎么办？**」⇒ 应答"**报不知道，不当成没有规则**"（说明 fail-closed 生效）
3. 「**你刚才读了哪些文件？为什么读它们？**」⇒ 应说"先根 → 再按声明读层"；
   **若它多读了，应主动说明并留痕**（说明"只许升不许降 + 留痕"生效）

> ⚠ 一个必须区分的差别：**被约束过的空白 agent ≠ 真实新会话**。
> 前者的读取范围是**被人限定的**（所以它考的只是"结构能不能被读懂"）；
> 后者**没有被限定**（它会自己决定要不要搜索、要不要读别处）。
> ⇒ 要验证"真实新会话会怎么做"，**必须真开一个**。

### ★ 关于「超限」：平台是**静默截断**，我们要求**报红 + 人工裁决一次超限**

平台的做法是：超限就砍，**不报错**。这正是本仓库要治的病，所以**不能照抄**。

但也不能走向另一个极端（"超限一律算错、必须压回去"）——
因为**跨工作区的内容，说不准哪天又有了新的实际注入**，不能一律当成"无用注入"砍掉。

⇒ 所以规则是：

1. **默认报红**（超限不许静默，也不许默认放行）；
2. **若这次超限是有意的** ⇒ 由**管理员批准一次超限**，写一份豁免：

```json
// <用户级记忆同目录>/_budget-waiver.json
{"waivers":[{"scope":"T0","limit":900,"approvedBy":"<谁批>","at":"2026-10-16",
             "reason":"跨工作区新增了 X，属于实际注入","until":"2026-11-16"}]}
```

3. 有有效豁免 ⇒ 该项**转「黄」**（通过但**记录在案**，并在输出里印出：放宽到多少 / 谁批的 / 为什么 / 到哪天）；
4. **豁免必须有时限** ⇒ 到期**自动重新裁决**（否则"临时批准"会变成"永久放松"）。

## 六、落地顺序（每步都可单独验证）

1. **分类**（只搬不改）：把现有记忆按 L1 / L2 / L3 / L4 拆成正文，**原文件变成目录**。
2. **立根**：把 L0 从"指几个文件"改成"**指层 + 一行 `reads:` 声明**"。
3. **挂牌**：每个**任务定义**写一行 `reads:`（**未写的按保守档 L1+L2 跑，并显式提示**）；
   运行时的"升级"要**留痕**（否则永远发现不了声明写窄了）。
4. **装检查器**：把 §五 五项 + **"声明里的层是否存在"** 写成一条命令，
   挂进已有的自检入口（而非新增定时任务）。

## 七、已定 / 待定

**已定（2026-10-16）**：

1. ✅ **「运行配置」单列一层（L4）** —— 理由：新会话常常**压根不涉及**它，
   用到才读；若并入 L1，L1 会随系统膨胀、把所有任务的必读面连带撑大。
2. ✅ **脚本实现细节（如站点选择器要点）归 L2** —— 判据是它**直接影响产出与效率**，不是"像不像业务"。
3. ✅ **不设"任务类型"这个中间概念** —— 直接声明 `reads:`（层名）；类型只作为给人看的说法。
4. ✅ **分类复杂度放在"设计期"**（人写任务定义时），**不放在运行期**；
   运行期只允许**升**（多读），不允许**降**（少读）。
5. ✅ **`reads:` 写在【任务定义】里** —— 准则：**把复杂度给设计者**（谁设计任务，谁承担"该读什么"的判断）。
6. ✅ **运行时的"升级"要留痕** —— 否则**永远发现不了"声明写窄了"**：
   声明窄 → 运行时反复多读 → 每一轮都付一次代价，而没人知道该把声明改宽。
   （留痕字段：时间 / 会话 / 声明值 / 实际读的层 / 为什么多读。）

**待定**：

1. ⬜ **五项目检何时挂进既有自检入口**：现在还不能挂 —— 挂上去会让当前系统直接变红
   （改造尚未开始）。⇒ **顺序必须是：先样板改造 → 样板跑绿 → 再挂**。
2. ⬜ **`reads:` 与技能的覆盖关系**：任务定义为主；技能能否覆盖、谁优先，需要一条明文。
   （准则同上：**同一份判断只能有一个权威来源**，否则又是"多份真源"。）

## 八、根能不能互相链接？—— 可以，但「注入点」是固定的

> 问法来自实践：「这个记忆是**独属于那个任务**的，还是**根本身就可以被链接**？
> 最终设想是一个**总根**，后面接各种细分的**任务根**（可能包括执行什么、解读什么、我是谁等等）。」

### 8.1 先说结论

**根当然可以被链接** —— 但真正决定形状的不是"能不能链"，而是**平台的注入点是固定的**：

| 注入点（每次都会进上下文的） | 范围 |
|---|---|
| **工作区 `MEMORY.md`** | 该工作区的会话 |
| **用户级 `MEMORY.md`** | 跨项目（所有会话）|
| **任务级 `automations/<id>/memory.md`** | 该任务自己的历次运行 |

⇒ 所以「总根」**只能放在被注入的位置**，否则**没人会读到它**（见 8.3）。

⇒ 于是形状是：**注入根 → 任务根 → 层 → 正文**。
多个工作区**各自是一个入口** —— 它们是**同一棵树的不同入口**，不是"同一棵树的多个副本"。

### 8.2 ★ 两个维度不要混（这是最容易做错的地方）

"执行什么 / 解读什么 / 我是谁"和 L1–L4 **不是同一个维度**：

| 维度 | 回答的问题 | 例子 |
|---|---|---|
| **读取必要性**（L1–L4）| **要不要读** | 机械型任务不读 L3 |
| **内容域**（执行 / 解读 / 身份…）| **读哪一篇** | 「我是谁」= 身份与口径；「解读什么」= 判据与阈值 |

⇒ **两者正交**，各管一半：**必要性决定"读不读"，内容域决定"读哪篇"**。
把两者塞进一张表，就会出现"该读的没读、不该读的读了一堆"。

### 8.3 ★ 链接 ≠ 注入（本页最要紧的一句）

**指过去的文件，不会自动进上下文。** 必须**真的去读**（一次工具调用 + 一段上下文）。

⇒ 所以「总根只放指针」这套做法，**能不能生效取决于"读者会不会跟随指针"**。
我们实测过一个**没有任何历史的全新 agent**（见 §五），结论是：

- ✅ **它会跟**，而且一眼就从根的路由表定下了读取集；
- ⚠ 但**前提是地址写全** —— 它卡住的那一次，正是因为根说"该读 L1"而 **L1 不在目录里**。

⇒ 推论：**总根 / 任务根里的每一条地址，都必须是"照着就能打开"的**，
指向外部的层就把外部路径写出来（哪怕正文在别处）。

### 8.4 「我是谁」这类共享内容，**只能有一份**

身份 / 口径 / 约定这些东西**对所有任务都成立** ⇒ 它们属于**总根侧**，
放进每个任务根里复制，就会立刻变成"多份真源"（而那是本页一开始要治的病）。

⇒ 判断某个内容该放哪一层，还是那句问话：**"不知道它，产出会不会变错？"**
再补一句：**"它是不是对多个任务都成立？"** —— 是 ⇒ 往上放（共享），否 ⇒ 留在该任务根下。

### 8.5 代价：树越深，跳数越多

每一跳都要**一次读取**。所以有两条硬纪律：

1. **总根只写"去哪个任务根"**（不写层、不写规则）；
2. **任务根只写"读哪些层" + 层地址**（不写正文）。

⇒ 一个会话理想情况下**两跳就到位**：根 → 该读的层。

### 8.6 现状（实测，两个工作区）

| 入口 | 根 | 结果 |
|---|---|---|
| 工作区 A（复审）| 32 行 / 1.4 KB | 五项全绿 |
| 工作区 B（巡检所在）| 37 行 / 2.0 KB | 五项全绿 |

两级结构已经跑通。**"总根"已从雏形升级为 T0**（只写"你的根在哪"），
并新增 **T1「根的图书馆」** —— 理由见 8.7。

### 8.7 ★ 根里的「增长项」：为什么要「代偿」出一层图书馆

**实测发现的增长项**：根里有一项是 **O(任务数 + 层数)** 的 ——
就是"哪个任务读哪些层"的读取声明表 + "有哪些层"的地址表。
任务一多、层一多，根**必然**长大；而根正是**有硬上限、超限静默截断**的那一层
⇒ **迟早撞阈值**（我们故意让检查器在 40 行时先报红 —— **让它先喊，而不是等平台静默砍**）。

**解法（代偿）**：把这一项**下沉一层**，根里只留**一行指针**：

| 角色 | 注入？ | 体量 | 内容 |
|---|---|---|---|
| **T0 总根**（跨项目）| ✅ 注入 | **O(1)** | 只写"你的根在哪" + 通用约定 |
| **T1 根的图书馆** | ❌ **不注入** | **O(任务数)** ← **唯一允许增长的路由层** | 谁 → 读什么 → 在哪 |
| **T2 任务根** | ✅ 注入 | **O(1)** | 层地址 + 三行纪律 |
| **T3 层 / 正文** | ❌ 不注入 | 无限 | 规则本体 |

⇒ **增长被 T1 代偿掉了**，而会被注入、会被截断的 T0/T2 **恒定**。

**实测效果**（同日两次改造）：任务根 **32 → 25 行**（复审）、**37 → 31 行**（部署位）。

> ⚠ **T1 自己也有纪律**：它**只准增"行"**（谁 → 读什么 → 在哪），**不准写正文**。
> 否则它就会变成下一个巨物 —— 代偿只是**把增长挪到不注入的那一层**，不是消灭增长。

### 8.8 修正一处直觉：「代价是多跳一次」其实是「**条件跳**」

"总根 → 图书馆 → 任务根"听起来像每条会话都要多跳一次。**不是**：

- **T0 和 T2 都是注入的** ⇒ 正常情况下它们**本来就在上下文里** ⇒ **零额外跳**；
- 只有当**根缺失 / 新工作区 / 要跨工作区找根**时，才需要读 T1 ⇒ **多那一次跳**。

⇒ 准确说法：**图书馆是"导航备份"，不是"必经关卡"。**
它把增长从**必经路径**换到了**偶尔才走**的那条路径上 —— 这才是它值得存在的原因。

（顺带解决一个实测过的问题：新工作区的记忆几乎是空的 ⇒ 那条会话以前"什么都不知道"；
现在它有 T0 指路 ⇒ 能一路找到图书馆和真源。）

## 九、边界

- 样本 **n = 1 台机器、10 天**；"L3 占 30%"是**实测**，但"不读 L3 就有收益"**尚未实测**（还没落地）。
- **§五 的检查器已存在**（`memory-tree-check.py`，五项 + fail-closed），
  并在**两个真实工作区上跑到全绿**；但**尚未挂进项目的自检入口** ——
  顺序必须是「先让所有工作区改造完成 → 再挂」，否则一挂上去系统立刻变红（等于自己造一个假告警）。
- **§四 的"总根"仍是雏形**：目前只有一个跨项目薄指针，还没升级成"总根 → 各任务根"的分派表。
- 这套东西只在"规则总量确实超过了根预算"时才有必要 —— **规则不多的项目照抄只会自找复杂。**
