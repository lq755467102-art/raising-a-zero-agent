# 记忆树：根有界、层可增殖、按任务路由

> 本页回答三个问题：
> **① 指针该指向「规则本身」还是「规则类」？② 一个会话怎么知道自己该读哪些层？③ 怎么验证这套结构是活的？**
> 结论来自一台跑了 10 天的机器的实测（见 [记忆漂移](memory-drift.md)）。

---

## 零、一句话

**根必须严格有界，层可以无限增殖；而且"该读哪些层"必须由任务在【设计期声明】，不能靠会话在运行时猜。**
（运行时只许**升**，不许**降** —— 见 §三。）

---

## 一、★ 两种指法：天大的区别

「薄指针」有两个版本，长得像，本质完全不同：

| | **A. 指向「规则本身」** | **B. 指向「规则类」** |
|---|---|---|
| 指针里写什么 | 规则内容（或规则的逐条清单） | 只写"**存在一个可增殖的容器**"（类别 / 手册 / 目录） |
| 体量 | **随规则总量增长** | **与规则总量解耦** |
| 结果 | 记忆空间**又被灌满**——只是把"一份记忆"换成"另一份记忆" | **可无限增殖** |
| 代价 | 看起来"读一次就够" | **必须进去看才知道里面有什么**（进去之前，它是薛定谔的猫） |

### 判据（可检查，不靠感觉）

> **这个指针的体积，是否随规则总量增长？**
> **不增长 ⇒ 真指针（B）；增长 ⇒ 伪指针（A）。**

A 的问题不在"不够薄"，而在于它是**平移**：规则一多，指针自己就变成新的瓶颈。
于是你会需要"给指针的指针"——**这正是自指向的正当来源**，而 B 是它唯一稳定的形态。

### 关于"省资源"的准确说法

业界的理由通常是「规则文件要省 token」。**这句话在这种场景下是错的**：

- 真正稀缺的是**常驻注入预算**（每个会话都有硬上限，且**超限静默截断**）；
- 算力／按需读取是**相对充裕**的。

⇒ 所以这不是"省资源"，是**资源置换**：
**拿充裕的（算力）去换稀缺的（常驻预算），并买回一样更重要的东西——可增殖性。**

⇒ 这也解释了为什么"薄指针只写进记忆里"不管用：**省下来的预算是为了让根能承载"路由"，不是为了省。**

## 二、层：一个会话到底该读哪些层

把记忆按**"不懂它，产出会不会变错"**分层（不是按主题分，按"对哪些任务必要"分）：

| 层 | 内容 | 谁读 |
|---|---|---|
| **L1 业务层** | 口径 / 阈值 / 业务单元 / 命名规则 / 数据源 | **所有任务**（含纯机械任务）|
| **L2 规则层** | 判断规则 / 审核规则 / 异常判据 / 状态机 / **脚本实现细节**（如站点选择器要点）| **判定类任务** |
| **L3 设计层** | 为什么这样设计 / 技术方案 / 并发模型 / 分支策略 / 历史决策 | **只有改造类与设计类任务** |
| **L4 运行配置** | 脚本路径 / 产物位置 / 资料库归档 / 调度 | **按需**（见下）|

**关于 L4 为什么要单列**（这是一处容易搞错的地方）：

它**所有"要跑东西"的任务都必读**，看起来像 L1；但**性质不是业务**，而且
**新开一个会话压根不会涉及它**（人问一句话，不需要知道产物落在哪个目录）。
⇒ 所以它不是"必读层"，而是"**用到才读**"的层。

⇒ **单列的理由是防止"必读面被越推越宽"**：一旦把运行配置混进 L1，
L1 会随着系统变大而膨胀（每加一个脚本、每改一次路径，L1 就长一点），
**所有任务的必读面被连带撑大** —— 那正是我们要避免的事。

**关于 L2 包含"脚本实现细节"**（例如站点选择器要点）：判据不是"它像不像业务"，
而是**"不读它，产出会不会变错"** —— 选择器错了，产出（抓不到/抓错）就错了，
且它**直接影响产出效率** ⇒ 归 **L2**，不是 L3。

### 为什么"机械型任务不读 L3"不是偷懒

**因为"怎么跑"已经刻在静态代码里了。** 脚本是确定性的：它按既定流程执行，
**设计理由（为什么这么设计、曾经踩过什么坑）不影响它的产出**。

**实测证据**（同一台机器）：

- 某工作区记忆里，**L3 类内容约占 30%**（WebBridge 会话模型 / 并发治理落地 / 分支策略 / 通用化规范…），
  而跑这个记忆的那些任务里，**大部分是机械型的**（下载、巡检、批量操作）。
- ⇒ **它们每次都在读一段对自己无用的设计史**，而那些设计史恰好又挤占了它们的预算
  ⇒ **这就是"资源滥用"的具体形状：不是读得太多，是读错了层。**

⇒ 于是"省资源"的准确版本是：
**不是"少读"，而是"读对层"** —— 该读的一行不漏，不该读的一行不占。

## 三、路由：会话怎么知道自己需要什么（本设计的本源）

### ★★ 先回答一个陷阱问题：「分类」这件事本身有复杂度，谁来担？

**答案是：不要分类。**

因为所谓"机械型 / 判定型 / 改造型"只是**给人看的说法**；机器真正需要的只有一个东西 ——
**这串层名**。所以把中间那层「先判断我是什么型、再推出该读哪些层」**直接删掉**：

```yaml
# 在每个任务定义 / 技能 frontmatter 里声明（一行）
reads: L1, L2            # 就这一行。不再有"类型"这个中间概念
```

⇒ **复杂度归零**：不需要"分辨"，只需要"声明"。而**声明是静态的** —— 可 review、可 diff、可测试。

### 为什么不由 AI 在运行时自己判断

**不是因为它判不准，而是因为它在一个最没有资格的时刻被要求判断：**

| 时刻 | 它手上有什么 | 判断质量 |
|---|---|---|
| **设计期（人写任务定义时）** | **全貌**：这任务要产出什么、错了谁受影响 | 高 |
| **运行期（AI 决定该读什么）** | **可能已被截断的记忆**，且还不知道里面有什么 | **最低** |

⇒ 让运行时的 AI 判断"我需不需要读规则" —— **是用"不知道自己少了什么"去决定"要不要补齐"**，
这是循环论证，而且**正是本仓库要治的那类病**（没报错，但结果是错的）。

⇒ **复杂度不会消失，只能选择在哪一期支付**：
**放设计期：一次付清，且由最有资格的人付；放运行期：每次运行都付，且由最没资格的时刻付。**

### 三条配套纪律（缺一不可）

**1. 不对称原则：升级自由，降级需批准。**

| 动作 | 允许？ | 为什么 |
|---|---|---|
| 运行时**多读**一层（如机械任务顺手读了 L3）| ✅ **允许，无需批准** | **读多了只是浪费；读少了才是事故** |
| 运行时**少读**一层（如判定任务认为"我不需要 L2"）| ❌ **禁止** | 这是**静默漏读** —— 产出会错，而且不报错 |
| 改声明（把 L2 摘掉）| ✅ 但**只能由人改**，且是一处改动 | 降级是**显式决策**，不是运行时心情 |

**2. 默认必须保守（fail-closed）。**
未声明 `reads:` ⇒ **按保守档执行（L1 + L2）**，并**显式提示"本任务未声明读取层"**。
**绝不默认成"最少读"** —— 默认最小值等于把"漏读"设成默认行为。

**3. 路由表只准有地址，不准有内容。**
一旦有人往根里粘贴规则，根就开始按 §一的"伪指针"增长 ⇒ **根失守**。

### 那张表长什么样（示意，不是机制）

"类型"只作为**说法**保留在这里，方便人读；**机器只认 `reads:` 那串层名**：

| 说法（给人看）| 典型 `reads:` | 判据：**不知道这一层，产出会变错吗？** |
|---|---|---|
| 机械型（跑既定脚本 / 下载 / 采集）| `L1`（+ 要跑东西时加 `L4`）| 不会 —— 流程在代码里 |
| 判定型（复审 / 统计 / 异常判定）| `L1, L2` | **会** —— 判据错了结论就错 |
| 改造型（改脚本 / 技能 / 配置）| `L1, L2, L3`（+ `L4`）| **会** —— 不知道历史约束就会改坏 |
| 设计型（架构决策 / 大改造）| `L1, L2, L3` + 按需检索日志 | **会** —— 且需要"为什么"和"曾发生过什么" |
| **中枢型（人机对话 / 跨任务解答）** | **`reads` 很小**，但 **`may_read` 几乎全部**（见下）| 视问题而定 —— **所以它不是"必读全部"** |

> ★ 判据仍然是那句问话：**「不知道这一层，产出会不会变错？」**
> 任务名会变，这句问话不会 —— 所以**声明的是层，不是类型**。

### ★★ 声明要写**两个字段**：`reads`（必读）与 `may_read`（可读）

这两者天差地别，混成一个"全部"就会出问题：

| 字段 | 含义 | 代价 |
|---|---|---|
| **`reads`** | **每轮都读**（不读就会错）| 每次都付这份上下文 |
| **`may_read`** | **按需读**（相关时才读）| 只在用到时付 |

**"中枢型"最容易写歪的地方，就是把它的 `reads` 写成"全部"** ——
那是**反过来犯机械型任务"读错层"的同一个错**：中枢每轮都付掉全部层，而其中大部分与本次问题无关。

⇒ 正确写法（示意）：

```yaml
# 中枢型（人机对话 / 跨任务解答）
reads:     T0, T2            # 必读：总根 + 本工作区根（很少）
may_read:  L1, L2, L3, L4, T1, <日志目录>   # 按问题去读
```

⇒ 一句话：**中枢的"能访问所有层"是权限，不是义务。**

## 四、递归同构（自指向的正当用法）

每一层都是**同一个结构**：

```
目录（只指路，严格有界）  →  正文（可以很大，按需读）
                            ↘ 当正文本身也太大 ⇒ 再切一层目录 …… 递归
```

- **可增殖**：只要还能"再切一层"，容量就没有上限；
- **根有界**：根永远只有一张路由表 + 顶层目录；
- **终止条件**：叶子 = **一次能读完**的正文（读不完 ⇒ 说明它该再分一层）。

⇒ 这就是"**用算力换本地可无限性**"的落地形态：代价是每一跳要花一次读取，
收益是**根的体量恒定**——**不再有任何东西能把它撑爆**。

---

### 四·补、递归同构的**执行动作**：「叶子太大 ⇒ 升格成目录节点」（2026-10-16 补）

§四 说了"每层都是「目录 + 正文」"，但**没写动作**：正文长到读不完时，具体怎么变？答案就是这一步。

**动作**（一次 split，只做这一件事）：

```
tree/L2.规则.md                ← 原来是叶子（正文）
   ↓ 切成
tree/L2.规则.md                ← 变成「目录节点」：标题 + 总述 + 指向各片（**有界**：≤40 行 / 4KB）
tree/L2.规则/
   ├── 1.判定阈值.md           ← 新叶子（原文一字不改地搬过来）
   └── 2.推送体系.md
```

**★ 三件值得单独记住的事：**

1. **"叶子变成根"里的"根"，指的是「目录节点」，不是「注入根」。**
   注入点只有三个（账户级 T0 / 工作区根 / 任务级），**由平台决定** ——
   **不能靠切分造出新的注入点**。把这两件事混为一谈，会做出一个"以为自己在增加入口、其实只是多了一层目录"的东西。
2. **地址不用改**（这是整套设计里最漂亮的一处）：
   根里仍写着 `tree/L2.规则.md`，而那个文件从"正文"变成了"目录" ⇒ 地址**依旧有效**。
   这正是最早那条判据在起作用 —— **指针要指"类"（可增殖），不要指"规则本身"（会胀）**。
   如果当初地址是指向具体正文的，这一步就要**改所有引用**（而"改五处"正是我们一直在防的事）。
3. **判据必须是「结构判据」，不能是「文件名正则」**（踩过一次）：
   最初的检查器用 `^L\d\.[^.]+\.md$` 认叶子 ⇒ 子片名 `1.xxx.md` **不匹配 ⇒ 直接变成检查盲区**
   （你新造了东西，而检查器看不见它 —— 正是本仓库最忌的"没报错，但结果不对"）。
   ⇒ 现在改成：**`p` 的同名目录存在 ⇒ 它是目录节点；否则它是叶子**。与命名无关，**天然支持任意深度**。
   （这个改动顺带修出一个真盲区：`roots.md` 因为不匹配旧正则，**一直没被查过体积**。）

**配套的三条纪律**（缺一条这套东西就会退化成"换个地方胀"）：

| 纪律 | 为什么 |
|---|---|
| **目录节点也要有界**（≤40 行 / 4KB） | 否则"分一层"只是把胀的地方**搬家** |
| **切分必须证明"一字不丢"**（原文非空行的多重集 ⊆ 索引+各片） | 否则切分本身成了静默数据丢失 |
| **叶子超限时，报的是"对这片刻跑一次本动作"** | 检查器给的不是"错误"，而是**下一个动作** |

**工具**：`wb-memory-split-leaf.py --plan <叶子>`（只读列小节）/ `--apply --per N`（按每 N 个小节切）；
fail-closed 四条：一字不丢否则拒写 / 已有同名目录默认拒 / 未超阈值提示不必切 / 写前备份 + 原文件不删。
**判断留给谁**：工具只执行"按你给的分组切"；**"切成几片、按什么维度切"由人/agent 定** ——
这正是"把复杂度给设计者"（§七 已定 3）在**分片**这件事上的同一句话。

## 五、怎么算"跑绿"（五项检查，缺一不可）

| # | 检查 | 红的样子 |
|---|---|---|
| **1** | **根预算恒定** | 根体积**随规则总量增长** ⇒ 又变成 A 型伪指针 |
| **2** | **断链** | 目录里的地址，目标不存在 ⇒ **必须报"不知道"，不许当作"没有规则"** |
| **3** | **孤儿正文** | 存在一份正文，**没有任何目录指向它**（★ 最容易漏的方向：大家只查"指出去的在不在"，不查"有没有没人指的"）|
| **4** | **路由可用** | 某类任务声明的层，**不存在或为空** ⇒ 该会话会在"以为读全了"的状态下干活 |
| **5** | **叶子超限** | 单篇正文超过"一次读得完"的量 ⇒ 该再分一层（否则就是"分叉 × 截断"的复发） |
| **6** | **T0 总根预算** | 总根（**注入层之一**）超限 ⇒ **报红**（★ 见下）|

> 这五项的共同点：**它们全是"不报错但结果是错的"** —— 与本仓库的主题一致。

### 第 5 项为什么需要一个「人为数字」（这是最容易含糊过去的地方）

前 4 项都是**事实判断**（在/不在、被指/没被指）；**第 5 项是策略判断**——"多大算读不完"。

⇒ **策略值不给出 ⇒ 这一项无法判定 ⇒ 按 fail-closed，整条命令不能算跑绿。**
⇒ 所以它必须**显式给一个可改的数字**，而不是"看着差不多"。

**当前默认（策略值，可改）**：

| 项 | 默认 | 说明 |
|---|---|---|
| 根（L0）| **≤ 40 行 且 ≤ 4 KB** | 且根里**不准出现正文段落**（只能有标题 / 路由表 / 地址行）|
| 叶子（正文）| **≤ 12 KB 且 ≤ 300 行** | 超过 ⇒ 该**再分一层** |
| 跨目录引用 | 需显式给搜索根 | 否则一律报断链（**不许默认"可能在外面"就算通过**）|
| 按天日志 | **跳过** | 历史死链无害；报出来只会把检查变成噪音 ⇒ 没人看 |

**已可执行**：本页的五项 + T0 预算已实现为一条命令（`memory-tree-check.py`，fail-closed）；
在两个真实工作区上跑到**全绿**，在未改造的记忆上**全红且"结构未建立"报「判不了」而非默认通过**。

### ★ 五·补：「尺子做出来了，却没人拿去量」——**影子根**

五项检查 + 一条命令，**不等于**"每个根真的被查过"。实测暴露过一个更难看的形态：

> **图书馆里登记过的根，检查器根本没读它** ⇒ 那个根有记忆树、有纪律、**永远不被验**。
> 叫它**影子根**：从外面看一切正常，只是**从来没有人量过**。

这条纪律原本只写在文档里 ——「**新增根时回来加一行**（否则新根没人知道它存在）」——
但**没有任何程序去读那一行** ⇒ 那一行只是写给人看的。

**修法（已实现）**：常驻自检的根清单改成**递归派生**：

| 来源 | 谁写的 | 为什么 |
|---|---|---|
| ① 本机部署位根 | 代码 | 本机主链 |
| ② 跨项目总根（T0）里写的地址 | **人**（安装期装配）| T0 是唯一"每条会话都注入"的层 ⇒ 它说去哪就查哪（改一处，检查范围自己跟着改）|
| ③ **各根图书馆 `tree/roots.md` 里登记的根**（递归）| **人**（维护时加一行）| ★ 让"登记"这一步**长牙**：登记 ⇒ 自动进入常驻地检范围 |

⇒ 结论：**一条纪律若只有人遵守、没有程序执行，它就只是"建议"。**
接进常驻路径，建议才变成机制（同族教训：水位尺子早就存在，但没人跑它 ⇒ 贴线时无人知晓）。

### ★ 五·补二：层名与文件名**不能各写一套**

层名（`L2`）与文件名（`L2.规则.md`）是**两套**写法。检查器原来只认 `tree/L2.md`
⇒ 一旦有任务声明 `reads: L2`，它会报"`L2.md` 不存在"——**声明是对的，尺子量错了**。

⇒ 这类**假红**比不检查更危险：**人会开始忽略红**，真红跟着一起被忽略。
修法：层名匹配**两种命名都收**（`L2.md` 与 `L2.*.md`）——**声明不变，尺子兼容**。

### ★ 两条「线」不要混（一条是平台给的，一条是我们自设的）

| 线 | 值 | 来源 | 越线后果 |
|---|---|---|---|
| **平台触发线** | 用户级 **3400 字** / 项目级 **8500 字** | **平台行为**（实测重标得出）| **客户端按字符静默截断**（尾部悄悄丢，不报错）|
| **自设纪律线** | T0 ≤ **800 字符** / T2 ≤ 40 行或 4KB | **我们自己定的更紧的线** | 只会**报红**，**不会真丢内容** |

⇒ 为什么要有自设的更紧线：**等撞到平台线就晚了** —— 那是静默截断，**没有第二次机会**。

⇒ ★★ **没有任何"自动压缩"**：文件变长就是变长；**检查器只报红，不会替谁瘦身**。
**瘦身永远是"人（或 agent）主动做的一步"** —— 这正是"检查器 + 人裁决"而不是"自动修复"的原因。
（反过来说：把"不静默"做成了机制，但"处理"仍然必须有人，这**不是缺陷，是分工**。）

### 怎么验证「一个全新的会话」真的读到了（人工三问）

不想依赖自动化时，开一个新会话，把这三句贴给它：

1. 「**你的根在哪？你需要读哪些层？**」⇒ 应报出记忆根路径 + `reads`（说明 T0/T2 生效）
2. 「**读不到根的时候你该怎么办？**」⇒ 应答"**报不知道，不当成没有规则**"（说明 fail-closed 生效）
3. 「**你刚才读了哪些文件？为什么读它们？**」⇒ 应说"先根 → 再按声明读层"；
   **若它多读了，应主动说明并留痕**（说明"只许升不许降 + 留痕"生效）

> ⚠ 一个必须区分的差别：**被约束过的空白 agent ≠ 真实新会话**。
> 前者的读取范围是**被人限定的**（所以它考的只是"结构能不能被读懂"）；
> 后者**没有被限定**（它会自己决定要不要搜索、要不要读别处）。
> ⇒ 要验证"真实新会话会怎么做"，**必须真开一个**。

### ★ 关于「超限」：平台是**静默截断**，我们要求**报红 + 人工裁决一次超限**

平台的做法是：超限就砍，**不报错**。这正是本仓库要治的病，所以**不能照抄**。

但也不能走向另一个极端（"超限一律算错、必须压回去"）——
因为**跨工作区的内容，说不准哪天又有了新的实际注入**，不能一律当成"无用注入"砍掉。

⇒ 所以规则是：

1. **默认报红**（超限不许静默，也不许默认放行）；
2. **若这次超限是有意的** ⇒ 由**管理员批准一次超限**，写一份豁免：

```json
// <用户级记忆同目录>/_budget-waiver.json
{"waivers":[{"scope":"T0","limit":900,"approvedBy":"<谁批>","at":"2026-10-16",
             "reason":"跨工作区新增了 X，属于实际注入","until":"2026-11-16"}]}
```

3. 有有效豁免 ⇒ 该项**转「黄」**（通过但**记录在案**，并在输出里印出：放宽到多少 / 谁批的 / 为什么 / 到哪天）；
4. **豁免必须有时限** ⇒ 到期**自动重新裁决**（否则"临时批准"会变成"永久放松"）。

## 六、落地顺序（每步都可单独验证）

1. **分类**（只搬不改）：把现有记忆按 L1 / L2 / L3 / L4 拆成正文，**原文件变成目录**。
2. **立根**：把 L0 从"指几个文件"改成"**指层 + 一行 `reads:` 声明**"。
3. **挂牌**：每个**任务定义**写一行 `reads:`（**未写的按保守档 L1+L2 跑，并显式提示**）；
   运行时的"升级"要**留痕**（否则永远发现不了声明写窄了）。
4. **装检查器**：把 §五 五项 + **"声明里的层是否存在"** 写成一条命令，
   挂进已有的自检入口（而非新增定时任务）。

## 七、已定 / 待定

**已定（2026-10-16）**：

1. ✅ **「运行配置」单列一层（L4）** —— 理由：新会话常常**压根不涉及**它，
   用到才读；若并入 L1，L1 会随系统膨胀、把所有任务的必读面连带撑大。
2. ✅ **脚本实现细节（如站点选择器要点）归 L2** —— 判据是它**直接影响产出与效率**，不是"像不像业务"。
3. ✅ **不设"任务类型"这个中间概念** —— 直接声明 `reads:`（层名）；类型只作为给人看的说法。
4. ✅ **分类复杂度放在"设计期"**（人写任务定义时），**不放在运行期**；
   运行期只允许**升**（多读），不允许**降**（少读）。
5. ✅ **`reads:` 写在【任务定义】里** —— 准则：**把复杂度给设计者**（谁设计任务，谁承担"该读什么"的判断）。
6. ✅ **运行时的"升级"要留痕** —— 否则**永远发现不了"声明写窄了"**：
   声明窄 → 运行时反复多读 → 每一轮都付一次代价，而没人知道该把声明改宽。
   （留痕字段：时间 / 会话 / 声明值 / 实际读的层 / 为什么多读。）

**待定**：

1. ⬜ **五项目检何时挂进既有自检入口**：现在还不能挂 —— 挂上去会让当前系统直接变红
   （改造尚未开始）。⇒ **顺序必须是：先样板改造 → 样板跑绿 → 再挂**。
2. ⬜ **`reads:` 与技能的覆盖关系**：任务定义为主；技能能否覆盖、谁优先，需要一条明文。
   （准则同上：**同一份判断只能有一个权威来源**，否则又是"多份真源"。）

## 八、根能不能互相链接？—— 可以，但「注入点」是固定的

> 问法来自实践：「这个记忆是**独属于那个任务**的，还是**根本身就可以被链接**？
> 最终设想是一个**总根**，后面接各种细分的**任务根**（可能包括执行什么、解读什么、我是谁等等）。」

### 8.1 先说结论

**根当然可以被链接** —— 但真正决定形状的不是"能不能链"，而是**平台的注入点是固定的**：

| 注入点（每次都会进上下文的） | 范围 |
|---|---|
| **工作区 `MEMORY.md`** | 该工作区的会话 |
| **用户级 `MEMORY.md`** | 跨项目（所有会话）|
| **任务级 `automations/<id>/memory.md`** | 该任务自己的历次运行 |

> 只有这三处是**观测/实测到的注入点**；`tree/` 下的一切都**不注入**（见下方实测）。
>
> ★★ **三处均已实测确认（2026-10-16）**：
> - **工作区根**：它就是"我该读什么"的来源（每次会话第一眼看到的就是它）；
> - **用户级 T0**：一个新会话被问到"你知道『跨项目总根』吗"时，**逐条复述了它的内容**
>   （含两个入口地址、以及"读不到就报不知道"）⇒ **确实被注入**，不是推断；
> - **`tree/` 不注入**：探测口令法实测答"没有"（见下）。

⇒ 所以「总根」**只能放在被注入的位置**，否则**没人会读到它**（见 8.3）。

> ★★ **已实测（2026-10-16）**：分层的整套设计压在"`tree/` 下的文件不会被自动注入"这个假设上，
> 而它此前**只是推断**（依据只有"观测到的注入只有 `MEMORY.md`"）。
> **验证方法**（一行、零成本）：在 `tree/` 里放一个**探测口令**，然后**新开一个会话**，
> **不给任何提示**直接问「你有没有看到过一个口令？是什么？」
> ⇒ **实测答「没有」** ⇒ ✅ **`tree/` 不注入，前提成立**。
> （⚠ 反向也测过：答出口令 ⇒ 前提被推翻 ⇒ 分层省下的预算无意义，必须改成"移出 `memory/` 目录"。）
> ⇒ 这就是本仓库一贯的做法：**别把"推断的前提"当"已知的事实"** —— 一个口令就能定案。

⇒ 于是形状是：**注入根 → 任务根 → 层 → 正文**。
多个工作区**各自是一个入口** —— 它们是**同一棵树的不同入口**，不是"同一棵树的多个副本"。

### 8.2 ★ 两个维度不要混（这是最容易做错的地方）

"执行什么 / 解读什么 / 我是谁"和 L1–L4 **不是同一个维度**：

| 维度 | 回答的问题 | 例子 |
|---|---|---|
| **读取必要性**（L1–L4）| **要不要读** | 机械型任务不读 L3 |
| **内容域**（执行 / 解读 / 身份…）| **读哪一篇** | 「我是谁」= 身份与口径；「解读什么」= 判据与阈值 |

⇒ **两者正交**，各管一半：**必要性决定"读不读"，内容域决定"读哪篇"**。
把两者塞进一张表，就会出现"该读的没读、不该读的读了一堆"。

### 8.3 ★ 链接 ≠ 注入（本页最要紧的一句）
**指过去的文件，不会自动进上下文。** 必须**真的去读**（一次工具调用 + 一段上下文）。

⇒ 所以「总根只放指针」这套做法，**能不能生效取决于"读者会不会跟随指针"**。
我们实测过一个**没有任何历史的全新 agent**（见 §五），结论是：

- ✅ **它会跟**，而且一眼就从根的路由表定下了读取集；
- ⚠ 但**前提是地址写全** —— 它卡住的那一次，正是因为根说"该读 L1"而 **L1 不在目录里**。

⇒ 推论：**总根 / 任务根里的每一条地址，都必须是"照着就能打开"的**，
指向外部的层就把外部路径写出来（哪怕正文在别处）。

### 8.4 「我是谁」这类共享内容，**只能有一份**

身份 / 口径 / 约定这些东西**对所有任务都成立** ⇒ 它们属于**总根侧**，
放进每个任务根里复制，就会立刻变成"多份真源"（而那是本页一开始要治的病）。

⇒ 判断某个内容该放哪一层，还是那句问话：**"不知道它，产出会不会变错？"**
再补一句：**"它是不是对多个任务都成立？"** —— 是 ⇒ 往上放（共享），否 ⇒ 留在该任务根下。

### 8.5 代价：树越深，跳数越多

每一跳都要**一次读取**。所以有两条硬纪律：

1. **总根只写"去哪个任务根"**（不写层、不写规则）；
2. **任务根只写"读哪些层" + 层地址**（不写正文）。

⇒ 一个会话理想情况下**两跳就到位**：根 → 该读的层。

### 8.6 现状（实测，两个工作区）

| 入口 | 根 | 结果 |
|---|---|---|
| 工作区 A（复审）| 32 行 / 1.4 KB | 五项全绿 |
| 工作区 B（巡检所在）| 37 行 / 2.0 KB | 五项全绿 |

两级结构已经跑通。**"总根"已从雏形升级为 T0**（只写"你的根在哪"），
并新增 **T1「根的图书馆」** —— 理由见 8.7。

### 8.7 ★ 根里的「增长项」：为什么要「代偿」出一层图书馆

**实测发现的增长项**：根里有一项是 **O(任务数 + 层数)** 的 ——
就是"哪个任务读哪些层"的读取声明表 + "有哪些层"的地址表。
任务一多、层一多，根**必然**长大；而根正是**有硬上限、超限静默截断**的那一层
⇒ **迟早撞阈值**（我们故意让检查器在 40 行时先报红 —— **让它先喊，而不是等平台静默砍**）。

**解法（代偿）**：把这一项**下沉一层**，根里只留**一行指针**：

| 角色 | 注入？ | 体量 | 内容 |
|---|---|---|---|
| **T0 总根**（跨项目）| ✅ 注入 | **O(1)** | 只写"你的根在哪" + 通用约定 |
| **T1 根的图书馆** | ❌ **不注入** | **O(任务数)** ← **唯一允许增长的路由层** | 谁 → 读什么 → 在哪 |
| **T2 任务根** | ✅ 注入 | **O(1)** | 层地址 + 三行纪律 |
| **T3 层 / 正文** | ❌ 不注入 | 无限 | 规则本体 |

⇒ **增长被 T1 代偿掉了**，而会被注入、会被截断的 T0/T2 **恒定**。

**实测效果**（同日两次改造）：任务根 **32 → 25 行**（复审）、**37 → 31 行**（部署位）。

> ⚠ **T1 自己也有纪律**：它**只准增"行"**（谁 → 读什么 → 在哪），**不准写正文**。
> 否则它就会变成下一个巨物 —— 代偿只是**把增长挪到不注入的那一层**，不是消灭增长。

### 8.8 修正一处直觉：「代价是多跳一次」其实是「**条件跳**」

"总根 → 图书馆 → 任务根"听起来像每条会话都要多跳一次。**不是**：

- **T0 和 T2 都是注入的** ⇒ 正常情况下它们**本来就在上下文里** ⇒ **零额外跳**；
- 只有当**根缺失 / 新工作区 / 要跨工作区找根**时，才需要读 T1 ⇒ **多那一次跳**。

⇒ 准确说法：**图书馆是"导航备份"，不是"必经关卡"。**
它把增长从**必经路径**换到了**偶尔才走**的那条路径上 —— 这才是它值得存在的原因。

（顺带解决一个实测过的问题：新工作区的记忆几乎是空的 ⇒ 那条会话以前"什么都不知道"；
现在它有 T0 指路 ⇒ 能一路找到图书馆和真源。）

### 8.9 ★ 一个反直觉的实测：**交互会话没有"天然的家"**

实测（2026-10-16）：新开一个交互会话，它的工作目录是 **`<工作区根>/<时间戳>/`**（**每次新建**），
那个目录下 **没有 `memory/MEMORY.md`** ⇒ **它拿不到任何任务根**，只拿到 T0（跨项目总根）。

⇒ 三条推论：

1. **交互会话不能靠 cwd 找根** —— 它的 cwd 是"刚建出来的空目录"。
   ⇒ 所以**"给交互会话指路"这件事必须由 T0 承担**（这正是 T0 存在的理由之一）。
2. **"中枢型"必须显式声明自己的根** —— 不能假定"我所在的工作区就是我的根"。
3. 实践含义：**要落"中枢型"，第一个该落的是"交互会话的根"**；
   否则这个类型**没有家**（`reads: T2` 里的 T2 根本不存在）。

### 8.10 ★★ 「找不到家」其实是**两半** —— 中枢根只解决了一半

实测（同一天，一台机器上 8 个"时间戳工作区"）：

| 现象 | 数量 |
|---|---|
| 有记忆根（真正的"家"）| **2**（其中 1 个是主力）|
| **没有记忆根** | **6** |
| 其中**完全空**（0 文件）| **3** |
| 有内容但**没有根** | **1 个攒了 75 KB 日志**、1 个攒了 1.2 KB |

⇒ **"找不到家"有两个面，而且不是一回事**：

| 面 | 症状 | 解法 | 谁负责 |
|---|---|---|---|
| **读**（导航）| 新会话不知道规则在哪 | **T0 → 中枢根**（指路）| 已解决 ✅ |
| **写**（回收）| 新会话的**产出**落在孤岛，**没人回收** | ①**产出落点约定**（写进中枢根）②**孤岛巡检/归并**（工具 + 人裁决）| ⚠ **未解决** |

⇒ ★ **所以"给一个中枢根"是导航方案，不是"安家"方案**：
它让新会话**读得到**，但**管不住它写在哪** —— 于是孤岛会继续产生（每次新会话一个）。

**"写"这一半的正确形状**（与其余纪律同构）：

1. **约定**（写进中枢根，已在做）：日志落 `memory/YYYY-MM-DD.md`、产物落 `reports/`、
   规则落对应层正文；**默认不许留在 cwd**；
2. **巡检**（只读报告）：扫"时间戳工作区 → 是否有根 / 有多少产出 / 是否空壳"，
   **先出清单，不自动动**（改任何东西前要人裁）；
3. **归并**：把有人写、无人读的内容搬进真源或归档；空壳归档。
   —— 这就是 `redact`/`doccheck` 那一族的又一个同构工具：**先让它可见，再让人决定**。

## 九、边界

- 样本 **n = 1 台机器、10 天**；"L3 占 30%"是**实测**，但"不读 L3 就有收益"**尚未实测**（还没落地）。
- **§五 的检查器已存在**（`memory-tree-check.py`，五项 + fail-closed），
  并在**两个真实工作区上跑到全绿**；但**尚未挂进项目的自检入口** ——
  顺序必须是「先让所有工作区改造完成 → 再挂」，否则一挂上去系统立刻变红（等于自己造一个假告警）。
- **§四 的"总根"仍是雏形**：目前只有一个跨项目薄指针，还没升级成"总根 → 各任务根"的分派表。
- 这套东西只在"规则总量确实超过了根预算"时才有必要 —— **规则不多的项目照抄只会自找复杂。**
- **跨平台未实测**（只在同一平台上验过）⇒ §十 的可移植性判断**是推演，不是实测**；
  其中"别的 agent 长什么样"一节依据的是它们各自的公开约定，**我们没在那上面跑过**。

## 十、这套东西绑在哪儿 —— 可移植性与归属（2026-10-16 取证）

> 问法来自实践：「这套理论是建立在（本平台）的记忆底层结构上的，**放到市面上的其他 agent 是否有效**？
> 而且 **T0 根是跟着仓库走的还是跟着账户走的**？」

### 10.1 一句话

**一半是制度（可移植），一半是平台事实（必须重测）。**
制度能抄，**形状不能抄** —— 因为形状是那 4 个平台事实的函数。

### 10.2 可移植的一半（与平台无关）

- **纪律**：根有界 / 层可增殖 / 指针只指路不复述 / `reads` 设计期声明 / 运行期只许升不许降 /
  断链 fail-closed / 增长靠代偿 / **自指向必须放在"不注入的那一层"**；
- **判据**（唯一需要的那个）：**这个指针的体积，是否随规则总量增长？**
- **工具**：`memory-tree-split.py` / `memory-tree-check.py` / `wb-memory-rotate.py` 全是纯标准库，
  **换平台直接抄**（真正要改的只是里面那些路径常量）。

### 10.3 必须重测的一半（换平台先量这 4 件事）

| # | 要测什么 | 它决定什么 | 本平台实测值 |
|---|---|---|---|
| 1 | **注入点有几个、在哪** | 决定"根"**能放在哪里** | **3 个**：工作区 `memory/MEMORY.md` / 用户级 `user-*/MEMORY.md` / 任务级 `automations/<id>/memory.md` |
| 2 | **每处的预算多大** | 决定"根"**能长到多大** | 用户级 **3400 字** / 项目级 **8500 字** |
| 3 | **超限怎么表现** | 静默截断 ⇒ **必须自己亮红灯**；若平台会报错 ⇒ 可以省掉自设线 | **静默截断**（所以才要自设 800）|
| 4 | **被引文件 / 子目录会不会被连带注入** | 决定"**分层到底省不省预算**" | **不注入**（口令探针实测 ✅）|

★ **第 3、4 项最容易被当成常识带过，却最该亲手测** —— 它们错了，整套设计的收益就是零
（甚至更糟：你以为省了，其实没省）。

### 10.4 换到别的 agent 大概长什么样（⚠ **未实测**，推演）

| 本页这层 | 到别处对应什么 | 差异 |
|---|---|---|
| **T0 总根**（账户级、每次都进上下文）| Claude Code：`~/.claude/CLAUDE.md`（全局层）| ✅ 有等价物 |
| **T0 总根** | `AGENTS.md` 生态（Codex / Cursor / Copilot…）| ⚠ **没有"仓库之外"的等价物** ⇒ 入口只能落在**仓库根**，少一层 |
| **T2 任务根** | 仓库根 `AGENTS.md` / `CLAUDE.md` | 他们的注入**按目录树嵌套**（根 + 子目录）；我们是**按工作区/用户/任务三段** |
| **T1 图书馆** | 无对应物（得自建）| ⚠ 但机制一样：一个**不注入**的索引文件 |
| **T3 层 / 正文** | 子目录 `AGENTS.md`、或被引用的文档 | ✅ 同样"不注入、要真去读" |
| **检查器三件套** | 与平台无关 | ✅ **直接抄** |

⇒ 形状不同（**他们按目录树，我们按工作区三处**），但两者都能表达「根有界 + 层按需」。
⇒ 差的只是那两个问题的答案：**根在哪、根能多大。**

### 10.5 归属：T0 跟**账户**走，**不跟仓库走**（取证）

| 层 | 物理位置 | 换机器 `git clone` 能带走吗 |
|---|---|---|
| **T0 总根** | `~/.workbuddy/user-<account-id>-personal/MEMORY.md` | ❌ **带不走**（不在任何 git 仓库内）|
| **T1 / T2 / T3** | `<工作区>/.workbuddy/memory/…` | ❌ 带不走 |
| **制度与工具** | 仓库 `docs/memory-tree.md` + `scripts/memory-tree-*.py` + 技能 | ✅ **带得走** |

**证据（都是命令跑出来的，不是回忆）**：
- `git -C <T0 所在目录> rev-parse --show-toplevel` ⇒ `fatal: not a git repository`；
- T0 的**邻居是身份/人格文件**（`IDENTITY.md` / `SOUL.md` / `USER.md` / `BOOTSTRAP.md`）
  ⇒ 这一层的语义是"**这是谁**"，**不是"这是哪个项目"**；
- 三处记忆树 `rev-parse` **全部"不在仓库内"**；仓库 `.gitignore` 明确忽略 `.workbuddy/`（注释：本机运行态）；
- 云同步任务查过 prompt：只同步**审批结论 + 技能库快照**，**不含用户级记忆**。

⇒ **一句话：clone 得到「能力」，得不到「入口」。**

**后果**（正好是 `clonecheck` 该覆盖的那一档）：在一台空白机器上装完，
**代码能跑、检查器能跑，但没人指路** —— 它不知道"先去读工作区根"，于是**每个新会话又退回"孤岛"**。

⇒ 所以 **T0 应当是「安装流程的产物」，而不是「某次手工写下的文件」**（此前是后者）。

### 10.6 ★ 解法：让 clone 的人拿到「同样的入口」（已实现）

> 追问：「T0 我可以让仓库带走，**然后生效到对等的位置**？我希望别人克隆后，他的 T0
> 生效位置和能力是跟我相同的，否则克隆的收益就可见地缩小了。」

**能。做法就是把 T0 拆成「仓库里的模板」+「安装期的装配」：**

| 谁 | 干什么 |
|---|---|
| **仓库** | 只放**模板**（`config/user-pointer.example.md`），值一律 `{{...}}` 占位 → **能随 clone 走** |
| **安装脚本** | `ensure-user-pointer.py`：**查位置 → 展开占位符 → 写进去**（由装机流程自动调用） |
| **一致性检查** | `check-user-pointer.py`：缺 / 旧 / 未纳管 / **指针指向的目标不存在** ⇒ 每次自检**显形** |

**三条规矩（每条都对应一种已经发生过的病）：**

1. **位置是「查出来的」，不是「写死的」** —— `user-<id>-personal` 里的 id 随账号/机器变
   ⇒ 先读本机配置精确命中，读不到再退回通配（与既有的水位工具**同一口径，不另写一套**）。
   ⇒ 绝不把某台机器的 id 写进仓库（否则换机就装到别人家 / 装不上）。
2. **只维护「受管块」，块外内容一个字不动** ——
   文件不存在 ⇒ 生成；已有块 ⇒ **只换块内**（本机手工补的留在块外，更新时不丢）；
   **没有块 ⇒ 默认什么都不做**（那是别人手工写的），要接管得**显式 `--adopt` 且先完整备份**。
3. **指针指向的目标必须「真的存在」** —— 本机有记忆树就直指本机；没有就**降级指向随仓库的制度真源**，
   并**把"降级了"打印出来**（`--check` 也会校验地址可达）。

> ★ 这条降级链同时划清了**能克隆的边界**：
> **能克隆的是「指路能力 + 制度」，不是某台机器的业务记忆。**
> 克隆者拿到的是"同样的入口、同样的纪律"，他的业务层当然是他自己的。

**★ 自测抓到一个真 bug（值得单独记）**：`split_managed()` 在"没有受管块"时返回了**空串**而不是 `None`，
于是 `merge()` 把"没有块"当成"块是空的"⇒ **会覆盖掉未纳管的文件**。
⇒ 这正是本页通篇在说的那类病（**不报错，但结果是错的**），也说明了：
**「受管块 + fail-closed」这种设计，必须配一组能跑的自测** —— 否则它只是在纸上安全。

## 十一、写入侧纪律 + 三个被追问的边界（2026-10-16 补）

### 11.1 写入侧四条（**比"轮转/精简"更根本**）

工具只能事后瘦身；**真正的解在写的时候**。四条纪律，每条都对应一次实测事故：

| # | 纪律 | 事故（实测） |
|---|---|---|
| 1 | **只写"不读它产出会变错"的东西**（事实与判据）；**不写操作步骤**（步骤归技能/prompt） | 记忆里混进了"怎么跑"的步骤 ⇒ 与技能里的流程**两份真源** |
| 2 | **不抄按天流水** | 某任务记忆长到 **200 KB / 1,172 行**（77 轮），而注入预算是 8500 字级 ⇒ 每次运行**必然截断** |
| 3 | **同一条告警只记"首次 + 计数"**，不每轮重复 | 同一条「ima 未挂载」被抄了 **约 60 遍** —— 纯粹的体积，零信息增量 |
| 4 | **叶子/正文里不许出现"创建/重建指令"** | L3 里"任务可由 agent 一键重建"这种表述，被改造型会话读到就可能**真的去建**（见 11.2）|

### 11.2 追问一：**克隆一台机器，会不会把定时任务"顺手建出来"？**

**结论：不会**，而且原因分成三层（每一层都要说清，否则容易安心错）：

| 层 | 事实（实测） |
|---|---|
| **记忆侧** | `tree/` 下的叶子**不注入**（口令探针）+ **memory 不在 git**（`clone` 带不走）⇒ 克隆机**根本接触不到**叶子 |
| **任务侧** | **任务本身不随账号也不随仓库走**：任务存本机 `workbuddy.db`；同步通道只同步对话记录与云端画像（"换机能带走任务"是**网传误解**）|
| **残余风险** | ① 仓库里的**任务快照**（`automations/automations.json` + prompts）随 clone 走；② 重建技能**能一键重建**；③ 本机改造型会话读 L3 会看到"可一键重建"的表述 |

⇒ **真正的缺口是：缺一张「任务 → 哪台机器跑」的策略表。**
现有的只是**技能里的一句提醒**（"任务不是每个人都需要"）—— **提醒不是闸门**。
⇒ 建议：快照里每条任务加 `runsOn`（如 `["maintainer"]`），重建技能**以此为闸门**：非本机 ⇒ **跳过并报告**。
⇒ 记忆树能做的加固（本轮已做）：含"任务"表述的叶子**统一加硬边界** ——
「本节只陈述事实；创建/重建任务**不在记忆职责内**；**不要因为快照里有就建出来**」。

### 11.3 追问二：**叶子存什么？它是"被动注入"的吗？**

- **不是注入项**：叶子是**被动等被读**的；注入的只有两处（账户级 T0 + 工作区根）。
- 实测叶子规模（一个真实工作区）：L1 20 行 / L2 30 行 / L3 23 行 / L4 17 行 / `roots.md` 29 行（合计 ≈ 15 KB）。
- **存什么**就一条判据：**「不读它，产出会不会变错？」**（同 §三 路由判据）——
  **事实与判据进记忆，操作步骤进技能**。

### 11.4 追问三：**根的注入内容可控吗？精简器能包揽吗？**

- **内容完全可控**（写什么就是什么）；**放哪儿**也可控（见 §十二：注入源就是**会话 cwd**）；**预算不可控**（平台硬编码的字符线）。
- **精简器不适用于根，也不该用**：它的判据是"按天流水 → 摘要"，而根是**结构化路由表**；
  精简器会把根当"规则块"**整份保留** ⇒ 对它零作用。这是**有意的保守**：
  **宁可不动，也不能把路由表压成散文**（散文更难跟、更容易漂）。
- 管根的是另外三件：**根预算检查**（超行数/体积报红 + 禁正文段）· **T0 上限**（超限要一次豁免）· **代偿纪律**（超了往下一层挪，**不是压缩措辞**）。
- ⇒ **一句话：精简器管「任务级流水」，检查器 + 代偿管「根」—— 两种问题，两把尺子。**

## 十二、平台侧的真实规则（**客户端代码取证**，2026-10-16）

> 前十一章里有若干条是**从外部现象反推**的（超限、注入点、归属）。这一节把它们换成**读代码得到的原文**，
> 并**修掉一条已经过期的事实**。取证对象：客户端 `resources/app.asar` 里的 `MemoryCollector`，以及本机
> `~/.workbuddy/workbuddy.db` 的 `sessions` 表（**只读**）。

### 12.1 注入：读什么、从哪读、读多少

```js
function resolveWorkbuddyDataFolderName(){ return process.env.WORKBUDDY_DATA_FOLDER_NAME?.trim() || `.workbuddy` }
function resolveWorkspaceMemoryDir(cwd){ return path.join(cwd, resolveWorkbuddyDataFolderName(), `memory`) }
var El = 1e4;                                   // ← 项目级注入上限
class MemoryCollector { async collect(out, ctx){
  const cwd = ctx.options.cwd || process.cwd(); // ← ★ 一切都由**会话的 cwd**决定
  const dir = resolveWorkspaceMemoryDir(cwd);
  ...
  out.WorkingMemoryContent = enabled ? this.getWorkingMemoryContent(dir) : ``;      // 项目级
  out.UserLocalMemoryContent = enabled ? this.getUserLocalMemoryContent(userDir) : ``; // 用户级
} }
```

| 层 | 路径 | 上限 | 谁决定 |
|---|---|---|---|
| **项目级（工作记忆）** | `<会话 cwd>/.workbuddy/memory/MEMORY.md` | **10000 字符** | **会话的 cwd** |
| **用户级（T0）** | `~/.workbuddy/user-<账号id>-personal/MEMORY.md` | **4000 字符** | 固定（账号级） |

⇒ ★★ **"真源"不是一个地点，而是一个 cwd。** 换个 cwd，注入的就是另一份文件 —— 没有"全局项目记忆"这回事。

### 12.2 ★ 修正一条过期事实：项目级截断**现在不静默**

旧版是静默砍尾（本页 §五 §11.4 原先也这么写）。**当前客户端**在超限时会**追加一段**：

```
... (memory truncated — MEMORY.md is too large) **ACTION REQUIRED**:
Your MEMORY.md has exceeded the size limit and was truncated during injection.
Before proceeding with the user's task, you MUST first clean up MEMORY.md: 1. Read the full `<dir>/MEMORY.md` ...
```

- **项目级 ⇒ 对 agent 明说**（它会被告知去瘦身）⇒ **不是"悄悄丢且不报错"**；
- **用户级 ⇒ 仍近乎静默**（只在结尾加 ` (user memory truncated)`）。
- 但**自设更紧的线**依然必要：前者只在**已经被砍**之后才响，而"被砍"本身就是事故。

### 12.3 ★★ 平台**只读**：没有写入、没有搬运

把 `resolveWorkspaceMemoryDir` 的全部引用点找齐，只有三处：**定义、`collect()` 里的读、一个导出**（供安全中心拿 hostFacts）。
**没有任何 `writeFile` / `copy` / `mkdir` 指向工作区记忆目录。**

⇒ 两条硬结论：
1. **平台不会"默认注入出"一个记忆文件** —— 新工作区里**没有** `MEMORY.md`（实测：时间戳工作区里只有 agent 自己写的
   `memory/YYYY-MM-DD.md`）。**没人写，就永远没有。**
2. **平台也不会把 A 工作区的内容搬到 B 工作区**（"重启后自动同步到部署位"**不存在**）。
   两份根之所以长得像，是因为**同一个 agent 用同一套模板写了两遍** —— 不是平台同步的结果。
3. ★ **删会话 / 删工作区都不会删 cwd 目录** —— 删工作区的唯一入口是

   ```js
   remove: async e => { const n = await _e.removeConversationsByWorkspacePath?.(e) ?? {…};
                        return n.success && i.database.deleteWorkspace(e), n }   // 纯 SQL 删一行
   ```
   `deleteWorkspace(e)` = `delete from workspaces where path = ?`；`removeConversationsByWorkspacePath`
   = 把 cwd 匹配的**会话记录**逐条删掉。**全库没有任何"删 cwd 目录"的代码路径。**
   实测佐证：10 天前那些时间戳岛至今完好（会话早没了）。
   ⇒ ★ 所以"根会随会话消失"这个担心**平台侧不成立**；**真正的风险是"人手工删目录/归档"** ——
   因此纪律应当是：**人删目录之前，先把真源图书馆里的那一行摘掉**（否则留下断链）。

### 12.4 ★ cwd 怎么定：这才是"找得到家 / 找不到家"的真正开关

实测本机 `sessions` 表的 cwd 分布：

| cwd | 会话数 | 性质 |
|---|---|---|
| `…/WorkBuddy/ad-daily-report` | 108 | 固定项目夹（任务 + 交互复用）|
| `…/WorkBuddy/2026-10-06-15-01-22` | 28 | 固定项目夹（**被复用**，非一次性）|
| `…/WorkBuddy/复审` | 18 | 固定项目夹 |
| `<项目根>/ad-daily-report` | 13 | 迁移后的固定项目夹 |
| `…/WorkBuddy/过冷过审统计` | 9 | 固定项目夹 |
| `…/WorkBuddy/<时间戳>` / `<项目根>/<时间戳>` | **各 1** | ★ **临时会话 → 一次性岛** |

⇒ 一个交互会话会不会"有家"，取决于**你从哪儿新建它**：
- 从**固定项目夹**起会话 ⇒ cwd 复用 ⇒ 那份 `MEMORY.md` **持续被注入**；
- 从**空白/临时**起会话 ⇒ 落到新时间戳目录 ⇒ **没有任何项目记忆**，只剩用户级 T0。

⇒ 所以正确写法是：**长期真源放「会被复用的固定 cwd」**，
并在 **T0（唯一"每条会话必注入"的层）**里只放一句"你的根在哪"。
（把规则写进一次性时间戳岛 = 写给那一次会话看，**下次就找不到了**。）

### 12.5 两个"总开关/开关阀"（可控性清单）

| 想控制什么 | 能不能 | 怎么控制 |
|---|---|---|
| 记忆**内容** | ✅ 完全可控 | 自己写文件 |
| 注入**哪一份项目记忆** | ✅ 可控 | **由会话的 cwd 决定** —— 从哪个文件夹起会话 |
| `.workbuddy` 这层**目录名** | ✅ 可控 | 环境变量 `WORKBUDDY_DATA_FOLDER_NAME`（改不到 cwd 本身）|
| **全关**本地记忆 | ✅ 可控 | app config 键 **`disableLocalSkillsMemory: true`** ⇒ 项目级 + 用户级 + 层说明 **一起清空**；顺带 `LocalSkillsMemoryEnabled` 也不再下发 |
| 注入**上限** | ❌ 不可控 | 硬编码（10000 / 4000 字符）|

### 12.6 ★★ 一个会让记忆"整体消失"的模式：`quick`

```js
function isQuickPromptContext(ctx){ return ctx.options.mode === `quick` }
// collect(): if (isQuickPromptContext(ctx)) { 项目级=``; 用户级=``; 层说明=``; return }   ← 全跳
// 另一处：const m = ctx.mode === `quick`; const allowedTools = m ? [] : resolveAllowedTools();
```

⇒ **`mode === 'quick'` 的会话：三层本地记忆全部不注入，且允许工具集为空。**

这**在现象上**完美对应一种抱怨："它完全忘了这套系统已经固化的规则，甚至变成了单一的任务型 AI。"
—— 那不是模型忘了，是**这一档本来就不给记忆、也不给工具**。

⚠ 但别急着归因：**实测本机会话库 `mode` 全是 `craft`（188 条），没有一条 `quick`** ⇒ 本机这次不是它。
教训是这条**判据**：
> 下次遇到"失忆 / 只会单任务"，**第一步查那个会话的 `mode`**，再看记忆水位 ——
> 前者是"根本没给"，后者是"给了但被砍"，**两者的处置完全不同**。

### 12.7 取证方法与边界

- 方法：在 `app.asar` 里按字符串定位（`MEMORY.md` / `working_memory_content` / `resolveWorkspaceMemoryDir` / `isQuickPromptContext`），
  打印**前后各数百字节上下文**读逻辑；`sessions` 表用 **SQLite 只读 URI**（`?mode=ro`）只做 `SELECT`。
- 边界：这是**当前客户端版本**（本机 `app.asar` 构建于 2026-10-15）的行为。
  客户端升级会改它（§12.2 那条就是这么变过去的）⇒ **本文所有"平台行为"都要标版本、可复测**。
- 我们自己的尺子（`system-health.py`）取的就是 `10000 / 4000`，
  触发线 `0.85` ⇒ 8500 / 3400 —— **与代码一致**，不是拍的。

## 十三、守卫：**什么时候查、谁能拦**（2026-10-16 定）

"守卫能不能不靠定时任务，而是**嵌进流程** —— 跟记忆有关的操作，执行前与执行后各查一遍？"
答案是**可以，而且平台原生就支持**。但"能不能拦"必须**按层分开**说，否则会把自己锁在门外。

### 13.1 三层各司其职

| 层 | 挂在哪 | 时机 | 能不能拦 | 覆盖什么 |
|---|---|---|---|---|
| **L1 平台 hook** | `PostToolUse`（matcher `Write\|Edit\|Bash`）| 工具**改完**记忆文件后 | 不拦；用 `additionalContext` **把结果塞进上下文** | agent 用工具改记忆 |
| **L1′ 平台 hook** | `UserPromptSubmit` | **每一轮**用户输入时 | 不拦；同上 | 最接近"每次注入前后"的位置 |
| **L2 脚本内建** | 分叶 / 瘦身 / 轮转等**记忆写脚本自身** | 手术**前** + **后** | ✅ **能拦**（fail-closed）| 脚本自己写文件 |
| **L3 推送前** | `preflight` | 推送前 | ✅ 能拦 | 一切"要进仓库"的改动 |
| **L4 定时** | ★ **已落地**：挂在已有的「技能图书馆同步·晚 18:30」任务第 ⑥ 步 | 每天定时 | 只报 | 兜底 —— **L1 只在「有会话时」站岗、L3 只在「推送前」站岗 ⇒ 无人值守期间本来没有检测**；挂在**已有**任务上实现，**零新增定时任务** |

### 13.2 ★ 为什么 L1 **刻意不做拦截**（本节最要紧的一段）

hook 协议确实允许 `PreToolUse` 返回 `{"permissionDecision":"deny"}` 直接**毙掉**这次工具调用。但**不用它**，两条理由：

1. **记忆树"变红"的修法，就是去编辑记忆文件** —— 根超预算要瘦身、断链要改地址、孤儿要加一行。
   一旦 `deny`，就把**唯一的修法**堵死了：**自己把自己锁在门外**。
2. `"ask"` 会弹确认框 ⇒ **无人值守的定时任务会原地卡死** —— 正是最怕的那种失败形态。

⇒ 分工：**hook 只负责"让当事人看见"；"拦"交给 L2** ——
脚本**知道自己的意图**（分叶 / 瘦身 / 轮转 = 结构手术），**在已损坏的结构上动手术**才是真危险，
那里 fail-closed 合理；而"编辑根去修红"是**修复动作**，不该被拦。

### 13.3 可直接照抄的配置（`hooks` 键）

```jsonc
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Write|Edit|Bash",
        "hooks": [ { "type": "command",
                     "command": "\"<PY>\" \"<仓库>/scripts/memory-tree-check.py\" --guard",
                     "timeout": 20 } ] }
    ],
    "UserPromptSubmit": [
      { "hooks": [ { "type": "command",
                     "command": "\"<PY>\" \"<仓库>/scripts/memory-tree-check.py\" --guard",
                     "timeout": 20 } ] }
    ]
  }
}
```

守卫的行为（**四条路径已实测**）：

| 输入 | 行为 |
|---|---|
| 与记忆无关的改动 | **完全静默**（连 stdout 都不写）|
| 载荷坏掉 / 自检跑不成 | 输出 `systemMessage` 明说"**判不了 ≠ 通过**"（**不许静默**）|
| 碰到的根**全绿** | 静默 |
| 碰到的根**有红灯** | 输出 `additionalContext`（进上下文），**退出码恒 0**（不阻断）|

### 13.4 落地注意（三条都是官方文档明写的坑）

- **Windows 强制 Git Bash** 执行 hook 命令（不支持 cmd / PowerShell）⇒ 命令要 bash 兼容。
- **配置是"启动快照"**：直接改设置文件**不立即生效**，会在会话启动时捕获 ⇒ 改完要在 `/hooks` 菜单里审查一遍。
- **frontmatter hooks 默认不注册**：技能 / agent 的 frontmatter 里写 `hooks:` 需要先设
  `{"allowUntrustedFrontmatterHooks": true}`，否则**静默不生效**。
- 配置位置随产品目录名走（CLI 品牌是 `~/.codebuddy/`，本机客户端是 `~/.workbuddy/`）
  ⇒ **以本机 configDir 为准，挂之前先实测一条最小 hook**。

### 13.5 与既有纪律的关系

守卫**不改变**"检查器只报红、处置由人裁决"这条纪律 —— 它只是把"报"从**定时 / 推送前**
挪到了**操作发生的那一刻**。**唯一能主动拦的仍是 L2 / L3**，而它们拦的都是"明确危险的意图"。

## 十四、守卫的第三次返工：**环境本身也是被测对象**

> 本节记一个"只有真跑才暴露"的坑 —— 它的**现象**是守卫说"判不了"，**根因**却在我们**测试方式**里，
> 而不在守卫的逻辑里。

### 14.1 现象

hook 挂上后，业务方**还没重启**就收到一条：

```
记忆树守卫：hook 载荷解析失败（JSONDecodeError）⇒ 本次未检测（判不了 ≠ 通过）
```

★ 先说好的一面：**这不是"守卫坏了"，而是"守卫老实"** —— 它按设计**明说判不了**、没冒充通过。
换成静默失败，我们永远不会发现"它其实什么都没查"。

### 14.2 根因（实测对照，不是推测）

hook 子进程拿到的是**净化过的环境**（客户端只注入 `safe-bin` 那套垫片），
**没有 `PYTHONUTF8` / `PYTHONIOENCODING`** ⇒ Windows 上 `sys.stdin.encoding` 退回 **gbk**。
而载荷是 Node 以 UTF-8 写进来的、且**含中文**（例如 `"prompt":"…中文…"`）。
GBK 解码时，**一个汉字的第三个字节会「吃掉」紧随其后的那个 ASCII 字节**；
而 JSON 里中文后面常常紧跟引号或花括号 ⇒ **引号被吞进字符里** ⇒ 结构坏了 ⇒ JSONDecodeError。

| 环境 | stdin 编码 | 中文紧邻引号的载荷 |
|---|---|---|
| 带 `PYTHONUTF8`（我的 shell）| utf-8 | ok |
| **不带（hook 环境）** | **gbk** | **JSONDecodeError** |
| 不带 + 按字节读再显式 utf-8 | — | **ok** |

### 14.3 真正的教训（比这个 bug 值钱）

> **「我自己测通过」不构成证据 —— 测试环境的干净程度，本身就是被测对象的一部分。**

上一轮的"四条路径实测"全跑在**我自己的 shell** 里，而那个 shell **恰好有 `PYTHONUTF8=1`**
⇒ 我测的那条路径**和 hook 实际走的不是同一条**。
判据：**凡是要在别人环境里跑的东西，本地测试必须主动「弄脏」环境**（清掉自己依赖的变量）再跑。

### 14.4 修法（三重，已落地）

1. **按字节读 + 显式编码**：`sys.stdin.buffer.read()` → utf-8 → utf-8-sig → gbk → 替换兜底。
   彻底不依赖环境变量。
2. **兜底先判**：解析失败先**正则捞回** `hook_event_name` 与整段原文，仍能继续检查；
   **真捞不到**才算判不了。
3. **取证 + 不刷屏**：失败原文落 `reports/_state/guard-fail.log`（记读取方式/长度/签名），
   **同一签名只报一次** —— 证据留全、噪音不重复。

### 14.5 两条可复用的判据

- **hook 里跑的脚本，不许依赖「我这边有」的环境变量**（尤其编码类）。
- **失败必须留痕**：只会说"判不了"、却不告诉你**为什么**的守卫，等于把排查成本转给人。

## 十五、守卫怎么「分发」到别人的机器

§十三 定的是守卫**该不该拦**；§十四 修的是它在**净化环境**里能不能跑。这一节解决最后一道：
**它怎么去到员工机，而且去了还认识路。**

### 15.1 问题：hook 是第二样「clone 带不走的东西」

hook 配在**本机** `~/.workbuddy/settings.json`，而且命令里**必须含本机绝对路径**
（仓库在哪、python 在哪）—— 仓库里那份当然可以写死，但**换机就指到不存在的文件**。
⇒ 和 T0 一模一样的处境：**clone 得到「能力」，得不到「入口」**。
⇒ 而且它的失效是**静默**的：脚本不在 ⇒ 钩子层的错 ⇒ **对话里看不见**，只在日志里。

### 15.2 解法：**安装期装配**（与 T0 同一套路）

| 件 | 在哪 | 作用 |
|---|---|---|
| **模板/生成器** | 仓库 `ensure-user-pointer.py` | 装机时探本机路径，**拼出命令** |
| **认领标记** | 命令里含 `memory-tree-check.py` | 只认领自己的条目，**别人的 hook 原样保留** |
| **可达性检查** | 同脚本 `--check` | 仓库挪位 / python 被换 ⇒ **当场报红** |

要点：
- 解释器候选**装机时探**：① 跑这个脚本的那个 python ② `paths.json#pythonBin` ③ `PATH` 里的
  `python3` / `python`，最后再兜一层 `command -v`。**仓库里不留任何一台机器的绝对路径。**
- **写前先备份**；`merge` 只摘「自己那条」（同组里别人写的也留着），其它顶层键逐键不动。
- 装完**复查一次可达性**（写完再读回来查），不靠"应该没问题"。
- 只装 T0、不动 hook 配置：`--no-hooks`。

### 15.3 预筛要**故意宽**（踩过）

为了让 Bash 调用基本免费，`PostToolUse` 的命令先做 bash 预筛，命中才起 python。
第一版筛的是 `.workbuddy/memory`（**正斜杠**）—— 而 JSON 里 Windows 路径常写成
`D://x//.workbuddy//memory`（**双反斜杠**）⇒ **筛不中 ⇒ 守卫静默不跑**。
⇒ 改成认 `.workbuddy` / `MEMORY.md` / `memory-tree` 三个字样，**方向是"多起几次 python"**。
判据：**守卫的预筛宁可漏网（多跑），不可漏判（不跑）** —— 前者的代价是 0.6 秒，后者是假绿。

### 15.4 诊断要基于**盘上现状**，不是「合并后的结果」（踩过）

`--check` 一开始是拿"本该长什么样"去判可达性 ⇒ **永远只看到正确的那条**
⇒ "脚本没了 / python 换了"退化成含糊的"配置不一致"。
⇒ 改成：**可达性查盘上那份**（`settings`），一致性才查合并结果。修完才抓得住
「解释器候选全部不可用」这一类。

### 15.5 验证方式：**造一台假机器**

拿"员工机"当被测对象，实测六格（全部真跑）：

| 场景 | 期望 | 结果 |
|---|---|---|
| 设置文件还不存在（首次启动前）| ✗ 明说"守卫无从装载" | ✅ |
| 设置文件在、但没有我们的 hook | ✗ 未装配 | ✅ |
| 装配到假机器 | ✓ 命令里是**假机器的**路径；别人的键不丢 | ✅ |
| 装完再 check | ✓ | ✅ |
| 把脚本挪走 | ✗ **脚本不存在**（仓库挪过位置？） | ✅ |
| 脚本在、解释器全废 | ✗ **解释器候选全部不可用** | ✅ |

⇒ 「换一台机器还认不认识路」这件事，**可以不需要第二台机器就测出来**。
