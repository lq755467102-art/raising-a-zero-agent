## 1. 分层与职责

**每一层只解决一类问题。** 跨层的"顺手"会制造隐式耦合 —— 那是后期最难拆的债。

| 层 | **只做** | **不做** |
|---|---|---|
| **调度** | 按时间 / 事件触发；记录"该跑什么" | 不知道业务细节；不做校验 |
| **编排** | 步骤顺序、幂等、续跑、重试、状态机 | 不碰具体页面的操作 |
| **执行** | 一个**原子动作**（取数 / 提交 / 下载） | 不做决策、不管并发 |
| **守卫** | 并发、质量、脱敏、审批、容量 | **不改变业务结果**，只决定"放不放行" |
| **数据** | 落库、导出、归档 | 不做校验（校验在守卫层） |

> 「守卫层**不改变结果**」这条很重要：它只能**放行或拦截**，不能"顺手修一下"。
> 一旦守卫开始改数据，你就再也说不清"到底哪一层是真相"。

## 2. 任务生命周期

```mermaid
flowchart LR
    A["触发<br/>（定时 / 事件）"] --> B["身份与权限<br/>（平台事实）"]
    B --> C["加锁<br/>reslock"]
    C --> D["编排<br/>checkpoint"]
    D --> E["执行：取数 / 操作"]
    E --> F["质量闸门<br/>checkgate"]
    F --> G["落库 / 导出"]
    G --> H["出口脱敏<br/>redact"]
    H --> I{"需要审批?"}
    I -- 是 --> J["approvalgate"]
    I -- 否 --> K["发布"]
    J --> K
    K --> L["释放锁 + 审计"]
    L --> M["写完成心跳"]

    classDef guard fill:#fff4e5,stroke:#d97706,stroke-width:2px;

```

橙色的四处都是**守卫** —— 它们不产生业务结果，只决定**这一步能不能过去**。

## 3. 失败分类学

把失败按两个维度分开，处置完全不同：

| | **可恢复**（重试有意义） | **不可恢复**（重试无用） |
|---|---|---|
| **显性失败**<br/>（会报错） | 网络抖动 / 限流 ⇒ **退避 + 上限重试** | 格式错 / 语义错 / 权限过期 ⇒ **立刻失败并报出来** |
| **静默失败**<br/>（不报错） | ★ **没有"处置"，只有"预防"** | 同上 |

**这张表最重要的一格是左下角**：

> 静默失败**不是"处理"出来的，是设计时拦掉的**。
> 因为它没有信号 —— 你没有机会"重试"或"报错"，只能在它发生之前**不让它发生**。

这就是为什么要有守卫层，也是本仓库全部工具存在的理由：
**把"没做成的"变成"显式失败"，把"看不出来的"变成"看得出来的"。**

## 4. 控制点地图

| 守卫 | 挂在 | 挡什么 | 失败时 |
|---|---|---|---|
| [`reslock`](../failclosed/reslock.py) | 执行前 | 多个任务抢同一份共享资源 | 如实报出"谁在占"并退出 |
| [`checkpoint`](../failclosed/checkpoint.py) | 编排 | 重跑导致重复副作用 / 跳过时用了过时输入 | 视为未完成，重跑该步 |
| [`checkgate`](../failclosed/checkgate.py) | 提交 / 发布前 | 内容缺陷以"能推"的形式溜过去 | 阻塞（判不了也阻塞） |
| [`contextbudget`](../failclosed/contextbudget.py) | 提交 / 发布前 | 笔记超限被静默截断 | 预警；超线即失败 |
| [`redact`](../failclosed/redact.py) | 出口 | 产物里残留真值 | 拒绝产出 |
| [`approvalgate`](../failclosed/approvalgate.py) | 有副作用的操作前 | 审批被绕过（尤其**自批**） | 拒绝执行 |

**共同底线**：**没做成的，不许冒充做成了。**

## 5. 真值边界

| 东西 | 在哪 | 进仓库吗 |
|---|---|---|
| **真值**（凭据 / ID / 人名 / 余额…） | 本机配置 | ✗ **绝不** |
| **模板**（带 `{{占位符}}`） | 仓库 | ✓ |
| **生成物**（注入后的部署副本） | 本机 | ✗ |
| **对外产物** | 脱敏之后 | ✓ |

三条纪律：

1. **配置外置**：真值只在本机；进仓库的只有模板。
2. **注入后要检查**：生成物里若还有残留占位符 ⇒ **失败**（不是"跑就是了"）。
3. **提交前自查**：占位符残留 / 绝对路径 / 私钥块，一个都不能有。

> 本仓库本身就是这条的产物：**只有与业务无关的部分被拿了出来。**

## 6. 人机边界

有些步骤**只有人能完成**：扫码、一次性界面授权、人工确认。

| 反模式 | 做法 |
|---|---|
| 整条链**同步阻塞**等人 ⇒ 人不在就全停 | **挂起 + 回读**：产出待办 → 链继续走能走的 → 人做完后触发回读补齐 |

> **瓶颈在人，所以要让机器适应人的节奏，而不是反过来。**
> 实测代价：一次"等人"就能把整条流水线堵住几十分钟。

## 7. 扩展点

**好的架构的标志：加东西时，不需要改已有的东西。**

| 想加 | 要动哪里 |
|---|---|
| **一项一致性检查** | 只往注册表加一条（运行方自动遍历） |
| **一个定时任务** | 复用既有编排 + 守卫，不新写并发/脱敏逻辑 |
| **一份可分发的能力** | 走分发链路（单一真源 → 打包 → 幂等安装 → 校验） |
| **一类新的守卫** | 按同一套「判不了即阻塞」的约定实现，接口不变 |

反过来说：**如果加一样东西要改五处，说明抽象还没做够** ——
这正是[「单一真源」](ai-collaboration.md)那条护栏的由来。

## 9. 诚实的边界

- 这套分层是**一台机器 + 一套系统**长出来的，不是从教科书抄的；
  换环境需要重新验证哪些假设还成立。
- **守卫只能保证"没跑成不冒充跑通"，不能保证"检查项选得好"** —— 后者仍靠人的判断。
- 分层不是越多越好：这里分五层，是因为**每层都真的有一类独立的问题要解**。
  为了"看起来架构"而分层，只会增加交接成本。
