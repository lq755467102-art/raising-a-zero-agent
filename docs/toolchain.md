# 这 11 个工具是怎么串起来的（编排）

> 单看每个工具的 README，容易得到一个错误印象：**"这是 9 个互不相干的检查器"**。
> 不是。它们**本来就在同一条流水线上**，只是当初是**一个接一个被真实问题逼出来的**，
> 所以落地顺序（`redact` → `checkgate` → `reslock` → …）**不等于它们的工作顺序**。
>
> 这一页补的正是这件事：**谁在什么时候该被叫起来。**

---

## 一、一句话看清全貌

**它们不是"一组库"，是一条流水线上的九个工位。**

```
        写代码时                跑任务时                要交付时              跨机器时
   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐      ┌──────────────┐
   │  redact      │      │  reslock     │      │  checkgate   │      │  clonecheck  │
   │  checkgate   │  →   │  checkpoint  │  →   │  doccheck    │  →   │  feedback    │
   │  doccheck    │      │  contextbudget│     │  approvalgate│      │  approvalgate│
   └──────────────┘      └──────────────┘      └──────────────┘      └──────────────┘
      防"改错"               防"跑错"               防"交错"               防"复刻走样"
```

**四个工位，各管一段**。每一段里都有一个共同的问题：**出错的时候不报错**。

---

## 二、四个工位分别在防什么

| 工位 | 什么时候 | 工具 | 这一段的"静默失败"长什么样 |
|---|---|---|---|
| **① 写代码** | 改完、要提交之前 | `redact` · `checkgate` · `doccheck` | 脱敏漏一处 / 自检没跑却报绿 / 文档写了死链和过期数字 —— **看着没事** |
| **② 跑任务** | 任务执行中 | `reslock` · `checkpoint` · `contextbudget` | 任务早干完锁还占着 / 重跑重复副作用 / 笔记被静默截断 —— **跑完了，结果不对** |
| **③ 要交付** | 推之前 | `checkgate` · `approvalgate` · `doccheck` | 危险操作被静默放行 / 推上去的东西本身有问题 —— **放行了不该放的** |
| **④ 跨机器** | 克隆到别的机器之后 | `clonecheck` · `feedback` · `approvalgate` | 空白机器跑不起来 / **两台机器对同一件事判断不一致却没人发现** —— **以为复刻成功了** |

> ★ **注意 `checkgate` 出现两次**：它是**闸门**，不是一个具体检查 ——
> 它把上面那堆检查**收口到一张注册表**里统一执行（加一项只改一处）。
> 所以它在①③都要出场，**不是重复**。

## 三、一条真实的主链路（推荐给新使用者的最小闭环）

**别一上来就全铺。** 按下面这条链走一遍，你会立刻明白它们的关系：

```
1. 你写了 / 改了一段自动化代码
      ↓
2. checkgate  ← 把"这次改动涉及哪些检查"跑一遍（拿不准就阻塞，绝不默认放行）
      ↓
3. redact     ← 要外发的产物先脱敏，并且**替换完再扫一遍**（有残留就拒绝产出）
      ↓
4. reslock    ← 用一个资源名把这次任务锁住（不相干的资源不排队，心跳停了自动接管）
      ↓
5. checkpoint ← 任务分步跑：中断后重跑，靠"key + 输入指纹"判断这步做过没有
      ↓
6. contextbudget ← 跑之前看一眼预算：笔记 / 记忆是不是快超线了（超线会被静默截断）
      ↓
7. doccheck   ← 这次改动如果碰了文档，扫死链 / 坏锚点 / **写死的数字**
      ↓
8. approvalgate ← 如果这步是"破坏性操作"，必须有人批，且**申请人不能自批**
      ↓
9. clonecheck ← 把这次成果拿到**空白机器**上跑一遍：只给代码、不给上下文
      ↓
10. feedback  ← 别的实例跑起来之后，**对账**：它对同一件事的判断和我一致吗
```

**⇒ 这条链的价值不在"有 9 步"，而在**：**每一步都在问同一个问题——「我现在真的知道它对吗？」**
**答不上来就停下**（fail-closed），而不是**继续往下走**。

## 四、单独拿一个也有用（别被"9 个"吓住）

**它们之间是弱耦合的 —— 没有任何一个依赖另一个才能跑。**
所以：

| 你的处境 | 只上这个就够 |
|---|---|
| 只是**怕脱敏漏了** | `redact` |
| 只是**自检结果不可信** | `checkgate` |
| 只是**并发任务互相咬** | `reslock` |
| 只是**重跑会重复副作用** | `checkpoint` |
| 只是**笔记写着写着就丢了尾** | `contextbudget` |
| 只是**只有你会批自己的操作** | `approvalgate` |
| 只是**文档老是有死链 / 过期数字** | `doccheck` |
| 只是**不知道别人机器上能不能跑** | `clonecheck` |
| 只是**不知道别的实例判断得对不对** | `feedback` |

> ★ **这不是"先学完 9 个再开始"，而是"遇到哪个病，拿哪个药"。**
> 反过来讲 —— **这一页存在的意义，是让你在"遇到病"的时候知道"这里正好有一味药"。**

---

## 五、为什么当初落地顺序是乱的

回头看，工具的落地顺序是这样的（**不是设计出来的**）：

```
redact → checkgate → reslock → contextbudget → approvalgate → checkpoint → doccheck → clonecheck → feedback
```

**它们是按"痛苦的先后"落地的，不是按"流程的顺序"。**

- 先被**泄密**咬到 → 才有 `redact`
- 然后发现**自检本身在骗人** → 才有 `checkgate`
- 然后**任务互相咬** → 才有 `reslock`
- ……
- 直到**跨了机器** → 才需要 `clonecheck` / `feedback`

⇒ 所以**如果你按这一页的顺序（①写 → ②跑 → ③交 → ④跨机）去理解它们，
会比按落地顺序理解顺得多** —— **这一页补的就是这段错位的理解成本。**
