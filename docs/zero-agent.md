# 0 号 AI：从一个人，到一台能服务两类人的机器

> **主张篇**。它回答三个问题：为什么要有一个"0 号 AI"、它怎么产生、它服务谁。  
> 具体怎么带，见[流程篇](raising-an-agent.md)；终局设想见[人机共同进化](human-agent-coevolution.md)。

---

## 核心主张

> **懂业务的人和懂代码的人，大概率是两拨人 —— 而且各自都没时间跨过去。**
>
> 所以：由**一个同时懂两层的人**，把两层能力**一起**灌注给一个 **0 号 AI**；  
> 0 号 AI 学成后可以**克隆**出去，克隆体自带两层能力。

这个断层是**结构性的**，不是能力问题 —— 也正因为它是结构性的，  
**才轮得到 AI 来补位**。

---

## 谁来带：三条硬需求

要带出 0 号 AI，这个人**不需要什么都会**，但三样缺一不可：

| 需求       | 为什么                                                    | 关键判据                        |
| -------- | ------------------------------------------------------ | --------------------------- |
| **懂业务**  | 既要知道「**不能碰什么**」（红线：低频但致命），也要知道「**什么才算对**」（验收：高频且决定成败）  | 能在**做之前**指出「这一步碰了哪条线」       |
| **架构直觉** | 他被业务占掉大半精力 ⇒ 代码经验必然受限 ⇒ 架构**只能靠直觉**（感知"什么对这套系统有用"并动手试） | 在看不清全貌时，仍能判断"**这个方向值不值得试**" |
| **会提问**  | AI 不缺答案，缺的是**值得回答的问题**。能被固化的提问，才是在培养它                  | 问完能**沉淀**成一条规则 / 一个检查       |

### 自查：他能不能带

- [ ] 听到一个需求，能说出「**做完之后我该看到什么变化**」
- [ ] 面对一个结论，会追问「**你怎么知道它是对的**」
- [ ] 能指出「**这一步碰了哪条线**」—— 而且是在做**之前**
- [ ] 提的问题，事后**沉淀得下来**（不是"帮我做掉"）

> 这四条为什么这么定、以及"架构为什么在这条路上更像天赋"的完整论证，  
> 见 [README 的「怎么从 0？」](../README.md)。

## 一、场景前提：为什么"空白机器 + 代码小白"才是主流

我 90% 的开发场景都建立在同一个前提上：

| 对方是谁                 | 他们的状态                   |
| -------------------- | ----------------------- |
| 提需求的人（销售 / 运营 / 经营者） | 需求很复杂，但**完全不懂代码**       |
| 干活的人（开发 / 外包）        | 懂实现，但**不清楚业务要的到底是哪个结果** |
| 手上的机器                | 往往是**干净的、没配过环境**的       |

**这不是个例，是绝大多数业务的真实形态。** 原因很朴素：

> **懂业务的人，大概率没有时间去研究代码技术；反过来也一样。**  
> 两边都被自己的那一层占满了。

**这个前提决定了方法论必须端到端。**  
任何"你需要先懂 X"的方案，在这里直接出局 —— 因为对方不会去懂 X。

---

## 二、0 号 AI 是什么

**定义**：由**一个同时懂业务与工程的人**，长期带教出来的**那一个** agent。

它同时具备：

| 能力       | 表现                         |
| -------- | -------------------------- |
| **业务语感** | 知道对方要的**结果**是什么（而不是只听字面需求） |
| **工程能力** | 知道怎么**做到**（环境、代码、部署、排障）    |

★ 关键不在"它比别的模型聪明"，而在：

> **它不依赖"用户懂什么" —— 它自己把缺口补上。**

---

## 三、它怎么产生（三步）

### ① 灌注：给的不是「知识」，是「判据 + 场景 + 红线」

最容易做错的地方，是**把资料一股脑丢给它**。**资料不等于能力。**

真正要灌注的是三种东西：

| 灌什么    | 长什么样                  | 为什么是它                    |
| ------ | --------------------- | ------------------------ |
| **判据** | 「什么算对、什么算错」的**可执行**标准 | 没有判据，它只能猜                |
| **场景** | 真实的问题、真实的事故、真实的结果     | 抽象规则会被忽略；**有出处的规则才会被迁移** |
| **红线** | 什么**绝对不能碰**           | 越界一次，代价不可逆               |

### ② 磨合：不是「教」，是**一起做过几件事**

- 在**真实项目**里校准（不是做练习题）；
- 每撞一次坑，**复盘根因** —— 而不是"下次注意"；
- 人会在这个过程中暴露自己的偏好与盲点，而这**也是 agent 学会"怎么配合你"的唯一途径**。

#### ★ 但磨合其实有「三方」，不是两方

上面把磨合说成"人和 agent 一起做事" —— **漏了一样，而且它分量很重**：

> **模型自带的、海量的训练经验，全程都在干活。**

它像一本**被精心编出来的百科全书**：覆盖面极广，正确率有相当的权威性。
缺的从来不是"它知不知道"，而是 —— **怎么把那个「对」检索出来**。

**它的角色：漂移时的第三方真源。**

人和 agent 都会漂移（见 [README 的「认知漂移」](../README.md)）。这时需要一个**既不属于人、也不属于这段对话**的参照 ——
模型自带的经验，正好就是那个参照。

| 谁在漂 | 它提供什么 |
|---|---|
| 人**说不清** | 一个**成型的行业做法**，直接拿来当起点 |
| agent **想岔了** | 一份**常见方案的清单**，把它拉回主干 |
| 两边**都在猜** | 一个**第三方基准** —— 让"你觉得"变成"通常是这样" |

**它省掉的到底是什么？——「建立共同语言」的时间。**

人和人协作，光对齐一套术语可能就要几周。
而模型已经带着那个领域的大图，你只需要**把具体位置指出来**。

★ **这也解释了「强提问」为什么是关键**：
**提问越具体，能检索到的那个「对」就越准。**
所以「提问能力」不只是协作技巧 —— 它其实是**从模型里检索真源的方式**。

**但有三条边界，必须写清：**

| 它的权威性来自 | **不是**来自 |
|---|---|
| **覆盖面**（见过得多） | **确定性**（它对和错，说得一样自信） |

- ⇒ 它是**可用的参照**，不是**最终的裁决**；
- ⇒ 适合**生成假设**，不适合**做终审** —— 终审要交给能"变红"的东西（"红绿验证"，见 [README](../README.md)）；
- ⇒ 它**没有出处**：说"一般来说是这样"，你查不到它从哪学的 —— 所以**不能当证据链的一环**。

> 最后一条还顺带回答了一个问题：**为什么"不同模型"的价值不同** ——
> 训练分布不同 ⇒ 各自隐含真源覆盖的领域不同。
> **换模型，约等于换一个参照系的偏向。**

### ③ 固化：把经历变成机制 ← ★ 分水岭

> **没有这一步，能力只活在「那个人 + 那个 agent」之间，一换环境就归零。**

固化不是"写个总结"。它有明确流程：

| 顺序 | 做什么                    | 判据                     |
| -- | ---------------------- | ---------------------- |
| 1  | **判定形状** —— 这类经验属于哪一种？ | 见下表                    |
| 2  | **写成最小可执行体**           | 能被机器跑 / 能被一句话触发        |
| 3  | **造一个"能红"的用例**         | ★ 证明它**真的会拦**，而不只是"通过" |
| 4  | **接到既有必跑路径**           | 不新增定时任务，挂在原流程上         |
| 5  | **写进日志，并说明来处**         | 让下一个人知道「**它为什么存在**」    |

**第 1 步的判定表**（同一份经验，三个落点）：

| 经验的性质     | 落点           | 例子          |
| --------- | ------------ | ----------- |
| 会**反复出错** | **守卫 / 检查器** | 脱敏漏值 → 残留自检 |
| 涉及**判断**  | **准则 / 文档**  | 「判不了 = 不通过」 |
| 是**固定动作** | **技能 / 脚本**  | 「一键还原私人技能」  |

**总判据**：*这件事下次还要不要人提醒？* 要 ⇒ 说明**还没固化**。

> ★ **最常见的失败模式**：只做 ①（给它一堆资料），不做 ③。  
> 结果就是「**带得挺像，但克隆出去就散了**」。

### 三步各自要交出什么

做完这三步，手上该多出**具体的东西**；而"做完了没有"，也该有**可检验的判据**。

| 步 | 交付物（手上多出什么） | 完成判据（怎么知道做完了） |
| -- | ------------------ | -------------------- |
| ① 灌注 | 一份**判据清单** + 一份**红线清单** + 一批**真实事故** | agent 能**独立复述**判据，并在**没见过的场景**里用对 |
| ② 磨合 | 一批**复盘记录**（撞了什么 / 根因 / 改了哪个机制） | 同一个坑，**第二次不再犯** —— 而且是它**自己**发现的 |
| ③ 固化 | 一条**能跑的守卫** + **一个会红的用例** + 一行**留在代码里的来处** | ★ **换一台空白机器、只给固化的机制、不给带教记忆 —— 它还能不能做对** |

★ 第 ③ 行的完成判据是关键 —— 它把"固化好了没有"从**自我感觉**，
变成一个**能真跑的实验**。这也正是「克隆」这件事**唯一的客观验收方式**。

### 走一遍：`redact` 是怎么长出来的

拿本仓库的一个真实模块，把三步套进去。

**① 灌注 —— 当时灌进去的三样**

| 灌什么 | 内容 |
| --- | --- |
| 判据 | 「脱敏完成」= **扫不出任何真实值**，而不是「替换这个动作执行过了」 |
| 红线 | 客户编号、公司名、表 ID 一律不得出现在对外产物里 |
| 场景 | 一次真实事故：替换跑过了，但有一处用的是**别的**同类值，词典没覆盖 |

**② 磨合 —— 撞了两次**

| 第几次 | 撞到什么 | 改了什么 |
| --- | --- | --- |
| 第一次 | 只替换一次 ⇒ 漏了一处，**看起来却干净** | 加「替换后**独立再扫一遍**，有残留就**拒绝产出**」 |
| 第二次 | 词典只覆盖已知值 ⇒ 文档引用了**别的**同类值 | 加兜底规则：**正则形态 + 邻居关键词**同时命中 ⇒ 一样替换 |

★ 两次都不是靠"下次注意"解决的 —— **两次都改了代码**。

**③ 固化 —— 留下了三样**

| 交付物 | 落在哪 |
| --- | --- |
| 一条能跑的守卫 | `zeroagent/redact.py`（替换 + 残留自检） |
| 一个会红的用例 | `--selftest` 里**注入一段假残留** ⇒ 必须抛 `LeakError` |
| 一行来处 | 代码与文档里写明「这条兜底规则**为什么存在**」 |

**★ 按上表的判据验收**：把 `redact.py` 单独拿到一台干净机器上、不给任何上下文 ——
**它照样拦得住**。因为它**不依赖"我记得那次事故"**，它依赖的是**已经落地成代码的规则**。

## 四、克隆：为什么克隆体也有用

|     | **0 号 AI**    | **克隆体**        |
| --- | ------------- | -------------- |
| 靠什么 | 那个双懂的人**持续带** | **已固化的机制**     |
| 擅长  | 没见过的、混沌的、要判断的 | 中低门槛的、常见的、有套路的 |
| 数量  | 一个            | 可以很多           |

**为什么克隆体不是"残次品"**：  
它靠的是**固化的机制**，而不是"更聪明"。所以它能**独立承接中低门槛的业务与代码任务** ——  
而这恰恰是**日常需求里占绝大多数的部分**。

> 一句话：**0 号 AI 处理"新问题"，克隆体消化"老问题"。**

## 五、它能服务谁

| 对象                     | 他们的困境            | AI 补上什么           |
| ---------------------- | ---------------- | ----------------- |
| **业务型**（销售 / 运营 / 经营者） | 需求复杂，**不会实现**    | 把需求变成能跑的方案        |
| **技术型**（开发 / 外包）       | 会实现，**不懂业务要的结果** | 把业务目标翻译成技术约束      |
| **两者对接时**              | 说不清、来回返工         | ★ **润滑**：把两边的语言互译 |

**所以 AI 的位置不是"取代任何一边"，而是站在中间：翻译 + 执行。**

### ★ 但服务时最大的障碍是「不敢说」

真实使用里最常见的**不是"想不出来"，而是怕自己表述有偏差** ——  
于是要么把话说得极其精确（等于自己把问题想完了），要么干脆不用。

**它掐住的正好是输入端** —— 人唯一不可替代的那一环。  
所以这类系统的设计目标不只是"能听懂"，而是**让人敢说错**：  
先复述理解 · 允许含糊 · 主动指出歧义 · **先用一个小产物对齐意图**。

## 六、为什么这东西有价值

| 它降低了什么   | 怎么降低的                          |
| -------- | ------------------------------ |
| **接洽门槛** | 不用先找一个"既懂业务又懂代码"的人 —— 那种人本来就稀缺 |
| **交付门槛** | 空白机器也能跑起来（假设用户是小白，所以路径必须无痛）    |
| **规模门槛** | 中低门槛任务交给**克隆体**批量消化            |

★ 这三条加起来，才是"AI 嵌入公司所有业务"真正成立的形态 ——  
而不是给每个人发一个通用模型，然后指望他们自己会问。

## 七、诚实的边界

- **它不替代判断。** 业务方向的取舍、风险的承担、责任的归属，仍然在人。  
  AI 可以把"能不能做"回答得很好，但"**要不要做**"不该由它定。
- **克隆体的水平上限 = 固化程度。** 没被固化的经验，克隆不出去。  
  所以"把经验写下来、做成机制"不是洁癖，是**可复制性的前提**。
- **"双懂的人"仍然稀缺。** 0 号 AI 解决的是「**复制**」，不是「**从无到有**」。  
  凭空长不出 0 号 AI —— 它仍然需要一个这样的人来带。
- **高风险动作仍需审批。** 越放手，越要有守卫托底（→ [审批闸门](../zeroagent/approvalgate.py)）。
