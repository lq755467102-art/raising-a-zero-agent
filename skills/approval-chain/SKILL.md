# 申请审批（提交 → 批复 → 回读放行）

## 〇、什么时候要申请

**规则**：**业务层面的「改 / 删」需审；系统层面一概免审。**

| 情形 | 要不要提交申请 |
|---|---|
| 要跑**会改 / 删业务数据**的技能 | ✅ **要**（首次） |
| 只读类（巡检 / 统计 / 下载表格 / 核验） | ❌ 不用 |
| 系统类（改代码 / 建任务 / 推仓库 / 装扩展…） | ❌ 不用 |
| **已经在某个技能上被批准过** | ❌ 不用（★ **资格授权永久有效**） |

**怎么判断某个技能是否需审**（择一即可）：

1. 它的说明书里带 `needs_approval: true` 或开头有 ⚠️ 提示；
2. 查一份**清单**（唯一真源，别在别处抄）。

**其他需要"请示"的情形**：

- 想做的事**拿不出凭据**（缺输入）⇒ 提交申请；
- 发现**自己越界**了（试了不该试的）⇒ 如实上报（`--type 越界尝试`）。

> ⚠ **本技能不替你放行**。它只负责"申请—批复"这条链；
> 拿到「已批准」之后，**回到原技能继续**即可。

## 一、主路径：云通道

**为什么用云通道**：旧的"共享表"方案要求员工**被邀请进空间**才能用；
云服务让员工**用自己的邮箱**就能走完，且权限由**数据库行级安全**兜底 —— **员工碰不到别人的数据**。

```bash
NODE="{{NODE}}"; WB="{{WB_ROOT}}"

# ① 身份自检（先看"我是谁 / 有没有被授权"）
"$NODE" "$WB/approval.mjs" --whoami

# ② 登录（首次 / 会话过期时）★ 必须单进程：后台启动 → 用户报验证码 → 写进文件
"$NODE" "$WB/approval.mjs" --login --email <邮箱> --code-file <临时文件> --wait-sec 300

# ③ 提交申请（以**员工自己的身份**写入）
"$NODE" "$WB/approval.mjs" --submit --item "某流程①：把 3 个新户加入业务单元" --detail "已提供：3 个账号 ID、目标单元名"

# ④ 看自己的申请与状态
"$NODE" "$WB/approval.mjs" --my

# ⑤ ★ 放行判据（按**会话身份**查批复，不依赖姓名匹配）
"$NODE" "$WB/approval.mjs" --check --item "某流程①"
#    {"approved":true}  ⇒ 放行，回原技能继续执行
#    {"approved":false} ⇒ **不要执行**；按 --submit 先申请
```

**关键点**：

- `--check` 按 **登录身份**判定，**不是按姓名** ⇒ 换电脑、改名都不会"解锁不了"。
- 服务端强制**精确来源校验**；脚本已自动注入必要的请求头。
- 会话由官方 SDK 保存在本机（**含令牌，绝不入库**）。
- **未在成员名单里 ⇒ 提交会被拒**（行级安全兜底）；先申请开通。

### ★ 免登录提交 —— 提申请不必先过邮箱验证码

**没有云会话时，`--submit` 自动走「免登录（匿名）通道」**：直接插一条到云端，
**审批台立刻可见**；管理员照样能批。

```bash
"$NODE" "$WB/approval.mjs" --submit \
  --item "某流程①：把 3 个新户加入业务单元" \
  --who <姓名> [--email <提交人邮箱>]     # 姓名是唯一硬要求
# ⇒ {"ok":true,"stage":"submitted-anon","appCode":"APP-…","loggedIn":false}
```

**机制与红线（都别忘）**：

- ★★ **为什么敢开匿名提交**：**批准的真凭据在另一张表（`decisions`），其写权限只给管理员**
  ⇒ **匿名提交伪造不出「已批准」**。
  ⇒ 这是整个设计的关键：**提交可以开放，批准不能开放。**
- ⚠ **提交人只能靠自述**（姓名 + 邮箱）⇒ **只当线索，不当证据**。
- ⚠ **批复时必须绑人**：匿名行没有身份 ⇒ 批复时**优先用管理员手选的人**；
  没手选就退回用邮箱去成员表自动配对；**两者都拿不到就拒绝批复**
  （否则批了也放行不了）。
- ⚠ **匿名插入不能带"回读"**：匿名身份对那张表通常没有读权限，
  `INSERT ... RETURNING` 会被策略判否并**把整条插入一起回滚**
  ⇒ 编号由**客户端生成**后再插。

### ★★ 免审身份 —— 有钥匙的人不用申请

`--check` 会**先看本机身份**（判据真源是一份身份判定脚本）：

| 身份 | 认定依据 | 需审技能 |
|---|---|---|
| 主维护者 | 能推主线 + 空间全 owner；或**账号后门** | **免审** |
| 系统管理员 | 能推发布分支，但推不了主线 | **免审** |
| 业务管理员 | 三个协作空间全 owner，但推不了分支 | **免审** |
| 普通成员 | 都不满足 | 首次需申请 |
| ⚠ **可疑（判据矛盾）** | **能推主线却不是空间 owner** ⇒ 冒充 / 误认 | **不放行**，人工确认 |
| 证据不足（新机未配） | —— | 按普通成员处理 |

- 命中免审 ⇒ `--check` 返回 `{"approved":true,"bypass":"identity:…"}` ——
  **不需要登录、也不需要申请**。
- ★ **fail-closed**：身份缓存缺失 / 过期 ⇒ **不放权**，落回正常申请流程
  （**绝不因"取不到身份"就放行**）。

## 二、三个动作（按角色）

### 2.1 提交申请

```bash
"{{NODE}}" "{{WB_ROOT}}/approval.mjs" --submit \
  --item "某流程①：把 3 个新户加入业务单元" --detail "已提供：3 个账号 ID、目标单元名"
# ⇒ {"ok":true,"stage":"submitted","appCode":"APP-1791866807-2065", ...}
```

- 记住返回的 **`appCode`**（= 业务编号，回读 / 核对都用它）；
- `--item` 想做什么（一句话）；`--detail` 已提供了什么资料；
- `--type`（可选）`请求授权`（默认）/ `越界尝试` / `异常上报`。

### 2.2 管理者端 · 批复

待审批 = 云库里 `status='待审批'` 的记录；点一下即写决定表。

> ★★ **批复只允许两条路**（**别开别的渠道**）：
> 1. **手动** —— 管理者在**界面**上直接改；
> 2. **agent 判权限后执行** —— 有人对 agent 说「批准 XXX」时，
>    agent **必须先确认他有审批权限**，**确认后才落笔**。
>
> ⚠️ **绝不要**在工作台页面 / 小组件上放「批准 / 拒绝」按钮 ——
> **那等于把"能不能打开页面"当成了"有没有审批权"**，两种结果都不对
> （要么人人能批、要么人人都不能批）。

### 2.3 回读结果

```bash
"{{NODE}}" "{{WB_ROOT}}/approval.mjs" --my                       # 我的申请 + 状态
"{{NODE}}" "{{WB_ROOT}}/approval.mjs" --check --item "某流程①"    # ★ 放行判据
```

> ★ **不用记申请编号**：`--check` 按**身份 + 事项关键词**判定 ⇒ **换电脑、改名都不影响**。

> ★ **为什么要能按"我是谁 + 我要做什么"查**：资格授权是**永久**的，
> 但申请编号是**一次申请**的凭据 —— **员工换了电脑就记不住编号了**，
> 总不能重新申请一遍。

> ℹ️ 若总开关关着（默认）⇒ 直接返回 `approved:true`（不拦）。

---

## 三、注意

- **申请表全员可写、状态表只有管理者可写** —— 这是本机制的根基，别去动它；
- 申请编号是**唯一凭据**，回读**只认它**（不按"提交人 + 事项"匹配，会撞重名）；
- 缺配置时报错是**对的**，不是 bug。

---

## 四、这个设计值得抄的三点

| 点 | 为什么 |
|---|---|
| ★ **提交可以开放，批准不能开放** | 匿名提交之所以敢开，是因为**真凭据在另一张只有管理员能写的表里** —— **权限边界画在"批准"上，而不是"提交"上** |
| ★ **按"我是谁 + 我要做什么"判定，不按姓名 / 编号** | 换机器、改名都不会失效；资格是**永久**的，凭据是**易失**的 |
| ★★ **绝不在"看得到的界面"上放批准按钮** | **可见 ≠ 有权** —— 把"能打开页面"当成"有审批权"，会同时制造"人人能批"和"人人不能批"两种错误 |
