# bug 修复收集区（`bugfix` 分支）

> **一句话**：修好的 bug **先落 `bugfix`**，其他分支都不动；
> 验证 OK 后再一次性并入主线并发布。**修 bug 不再打扰已经分发出去的分支。**

## 〇、为什么要这么干

```
用户机   → 读 发布分支  ┐
协作者机 → 读 协作分支  ├─ 这些分支**已经分发出去**了：
维护者   → 走 主线     ┘   动不动就会让所有人跟着同步 / 被打扰
```

**问题**：本机发现一个 bug、手快改完直推主线 ⇒ **所有用户机下次自检就被推着更新**，
而这次修复可能**还没验证**、或者只是**临时救火**。

⇒ **解法：加一个隔离区**。修复先进 `bugfix`，那儿**没人读**；
需要时再从 `bugfix` 拉下来验证，确认没问题才发布。

| 分支 | 谁在读 | 用途 |
|---|---|---|
| 主线 | 无人（维护者工作区） | 本机日常开发 |
| **发布分支** | **用户机** | 稳定发布 |
| **协作分支** | **同事 / 协作者** | 协作开发 |
| **`bugfix`** 🆕 | **无人** | ★ **bug 修复收集区**（本技能的落点） |

## 一、怎么用（三步）

```bash
# ① 看清改了什么（★ 只挑「本次 bug 相关」的文件）
git status --short

# ② 提交（★ 写具体文件路径，**绝不 `git add -A`** —— 工作区可能混着别的活）
git add path/to/a.mjs path/to/b.md
git commit -F - <<'EOF'
fix(<范围>): <一句话说清修了什么>

- 根因：<为什么坏>
- 修法：<怎么修的>
- 实测：<怎么验证的 / 实际结果>
EOF

# ③ ★ 只推 bugfix 这一个分支（其他分支都不动）
git push origin HEAD:bugfix
```

**完成后**：远端 `bugfix` 收到了这次修复；**主线、发布分支、协作分支原封不动**。

> `bugfix` 分支**不存在时会自动创建**。

### ⚠ 推不动怎么办（**先看本机角色，再选出路**）

**各人权限不同**（同一角色在不同分支上也可能被单独授权）——
所以**不要预设"我能不能推"**，先看本机实际角色，再按下面走：

| 本机角色 | 常见能推什么 | 出路 |
|---|---|---|
| 维护者 | 全部分支 | 按 ③ 推 `bugfix`；验证 OK 后按 §二发布 |
| 协作者 | **视平台授权而定**（`bugfix` 通常可推） | **优先推 `bugfix`**；若被拒 ⇒ 走**合并请求**，或把补丁交给维护者 |
| 没有推送权限 | 推什么都会被拒 | **别硬试** ⇒ ① 走**合并请求**（Fork 后提）；② **导出补丁**交给维护者：`git format-patch -1 --stdout > fix.patch` |

> ★ **判断"能不能推"的唯一可靠方式**：**以平台实际结果为准**（推送被拒 = 没权限）。
> ⚠ **不要用 `git push --dry-run` 探权限** —— 有些平台的 dry-run **不触发保护检查**，
> 会给出**假阳性**（真实项目曾因此两次误判）。
> 被拒后**别反复重试、别 `--force`**；按上表换出路即可。

## 二、发布（验证 OK 之后）

```bash
# 把收集区里的修复并入主线，再发布到用户机读的那条分支
git push origin main
git push origin main:pub
```

> ⚠ **顺序**：先主线，再发布分支。**推发布分支 = 给所有用户机发布** ——
> 确认验证过了再推。

## 三、要改的几点认知（避免踩坑）

1. **本机主分支会「领先」远端** —— 这是**设计如此**：
   修复在本机主分支上提交（工作区不变、便于边改边测），但**只推 `bugfix`**。
   ⇒ 本地 `git log origin/main..main` 看到的，就是「**已修但未发布**」的清单。
2. **别在 `bugfix` 上直接改代码** —— 本机工作面**始终在主分支**。
   `bugfix` 只是**接收端**（用 `HEAD:bugfix` 推上去）。
3. **推送被拒** ⇒ 先分清是哪种：
   - `non-fast-forward` ⇒ 远端 `bugfix` 上有别人的提交 ⇒ **先看差异，别 `--force`**；
   - **权限类拒绝** ⇒ 本机角色对该分支没写权限 ⇒ 按 §一的三条出路走（**别试探、别重试**）。
4. **这是「维护者」的操作** —— 协作者通常只能推协作分支（由钩子拦）。
   **发现 bug 的人**：把修复推自己的分支，或把问题报给维护者。
5. ⚠ 钩子是**软提示**（可绕过）；**真边界在平台**。

## 四、和别的流程怎么分工

| 场景 | 用哪个 |
|---|---|
| 改完功能 / 文档，**要正式更新** | `repo-sync`（同步 + 推送） |
| **修 bug、先收集不发布** | ★ 本技能（落 `bugfix`） |
| 已收集，要**正式发布给用户机** | 本技能 §二 |

## 五、自检（做完看一眼）

```bash
git rev-parse --short HEAD origin/main origin/bugfix   # HEAD 应等于 bugfix，主线应「没动」
git log --oneline origin/main..HEAD                    # 「已修未发布」清单
```

## 这个模式值得抄的地方

**它解决的是"多机分发之后，怎么改而不惊动所有人"**：

| 常见做法 | 问题 |
|---|---|
| 修完直推主线 | **所有下游机器被迫同步**，而修复还没验证 |
| 攒着不提交 | 修了什么**没有记录**，且工作区越堆越乱 |
| ★ **落到一个"没人读"的分支** | ✅ **修了、记了、但没惊动任何人** —— 发布是**另一个显式动作** |

⇒ 一句话：**把"修好了"和"发出去了"拆成两件事。**
