# 记忆蒸馏（长期记忆 + 日志 → 精简 + 留档）

> **一句话**：记忆**无法扩容**（阈值在客户端里）⇒ 只能**分层 + 定期蒸馏**：
> 「每次注入的那份」保持精简，「历史细节」不丢、可回溯。

---

## 何时用

- 用户说「**蒸馏一下记忆 / memory 太大了 / 记忆体检 / 日志太长了**」
- 健康检查的「**记忆**」项报 `▲`
- 换机前后想清理一下长期记忆

## 第 0 步：先看水位（**有尺子再动手**）

先跑健康检查，看最后一行「记忆」。

★ 三个容易读错的地方：

- 括号里**前一个 % 是"用量占注入阈的比例"**，后一个 % 才是触发线 ——
  别把用量误读成"阈值设成了 85%"
- **判据是「字符数」不是字节数**（中文 1 字 ≈ 3 字节，按字节比会**严重低估**）
- ★★ **一次要量两份** ——「用户级记忆」是**另一份文件、另一道上限**（见下节）

---

## ★★ 记忆有**两层**，各有**独立**的注入上限（实测）

| 层 | 文件 | 注入上限 | 触发线 |
|---|---|---|---|
| **工作区（项目）** | `<注入位>/memory/MEMORY.md` | **≈10000 字符** | 8500 字 |
| **用户级（跨项目）** | `~/.workbuddy/user-*-personal/MEMORY.md` | **≈4000 字符** | 3400 字 |

- **实证**：两份**同一会话都注入**；项目那份 11116 字符被砍在 **9990**，
  用户级那份 5248 字符**两次都被砍在 ~4000**
  ⇒ 是**每文件各自的上限**，**不是**"记忆区总预算"
  （否则用户级会被项目那份挤小）。也与系统提示 Layer 2 的 `Limit: 4,000 chars/session` 吻合。
- ⇒ **只量一层 = 同款的「假绿」**：用户级超 4000 后，**尾部整段每轮静默不进上下文**，
  而旧检查只量工作区那份 ⇒ **照样报 ✓**。
- ★ 蒸馏时**两层都要看**。用户级那份**跨项目共用** ⇒ 改前先 `cp` 备份（`MEMORY.md.bak-<日期>`），
  同样守「**只减不丢**」。

## 三文件分工（先认清，别搞混）

| 文件 | 作用 | 注入 |
|---|---|---|
| `memory/MEMORY.md` | 当下长期记忆（**铁律 + 索引**） | ✅ **会被注入** |
| `memory/YYYY-MM-DD.md` | 当天流水（append-only） | ✅ 当天 |
| `memory/archive/*.md` | **归档**：老日志 + 变更日记 | ❌ **不再注入** |

★ 判据：**跨会话仍成立、且影响行为**的（规则 / 判据 / 红线 / 约定）→ 该进长期记忆。
当天的一次性过程、已完成的工单、临时排查细节 → **不上移**。

---

## ★★ 先认清：`memory/` 有**两处**，别搞混（实测）

| 位置 | 内容 | 是否被注入 |
|---|---|---|
| **会话工作区** `…/<会话目录>/.workbuddy/memory/` | 当前会话**注入**的那份 | ✅ **就是这份** |
| **部署位** `…/<某部署目录>/.workbuddy/memory/` | 另一空间的一份 | ❌ **不注入** |

- ⚠ **先确认你测的是哪一份**：路径解析常常按脚本自身位置**就近找** ——
  在**仓库布局**下解析为 `<工作区>/.workbuddy/memory`（**注入的那份** ✓）；
  在**部署位**下可能落到 `<部署根>/.workbuddy/memory`（**不注入**）⇒ 那种情况**读数会误导**。
- 归档与日记本要建在**被注入的那一份**旁边，**否则白干**。
- ★ 实测教训：长期记忆到某个程度后**看起来像「纯铁律」密度下限**（改写三轮几乎不动）。
  - ★★ **后来修正了这一条**：那结论是**在错的尺子下**得出的（按**字节**比 32KB）。
    换成正确尺子（**10000 字符硬上限**）后，同一份文件 **11116 → 7527 字符（−32%）**，
    铁律一条没丢 —— **真降得动的原因是删的是「重复 / 过时 / 细节」**。
    ⇒ **"压不动"通常意味着你还在删规则，而不是文件已到底。**
  - ⚠ 外移前先查**脱敏约束**（空间 ID / 表 ID / 主体 ID / 账号 ID **不能进 git 仓库**，
    只能留本机或 `config/`）—— 拿不准就**留在正文压缩版**或写进本机 `archive/`。

### ★★ 下沉三准则（跨机安全）

「长期记忆只留铁律 + 指针」这个手术**不会让新机拿到空指针**，
但前提是**指针指对地方** —— 记忆文件是**本机的**，**指针指向的目标**才决定能不能跨机：

| 指针指向 | clone 到新机后 | 说明 |
|---|---|---|
| 仓库内 `docs/xxx.md` | ✅ **在** | 跟 git 走 ⇒ **下沉内容只该放这里** |
| `<注入位>/memory/archive/*.md` | ❌ **不在** | 归档是本机的、**设计上不入库** ⇒ 别当跨机载体 |
| 资料库节点 ID / 知识库名 | ⚠ **用不了** | 需账号权限，且 **ID 本身禁止入库**（脱敏红线） |

1. **只有「脱敏后能进 `docs/`」的内容才下沉成指针**；
2. **不能入库的细节**（空间 ID / 表 ID / 主体 ID / 账号 ID / 本机路径）⇒ **留在正文**，
   **绝不换成指针** —— 换了就是**永久空指针**（新机上永远取不到）；
3. **指针一律写「仓库内相对路径」**，不写 `~/.workbuddy/...` 等本机绝对路径。

▶ **新机靠什么活**：长期记忆本身不在仓库 ⇒ 新机 clone 后**连指针都没有**，
靠一份**入口文档**（文首写明「给新机器上接手的 agent：先读这一页」）当入口，按它**重建**记忆。
⇒ **记忆是在新机上重新长出来的，不是"被克隆过来的"。**

## 蒸馏流程（五步）

```
① 提炼上移：读老日志 → 抽「规则/结论/教训」→ 与长期记忆逐条比对 → 补漏（去重、压缩）
② 外移成文：成体系的知识（设计/踩坑/SOP）→ 写 docs/（进 git）或递进可检索的知识库
③ 留档记账：把「从长期记忆里删掉/压缩掉的**原文**」追加到 archive/变更日记
            （★ 原文照抄 —— 这是"万一漏了能捡回来"的保险）
④ 归档瘦身：老日志移入 archive/；长期记忆只留「铁律 + 指针」
⑤ 复核：再跑一次健康检查的「记忆」项，确认水位回落
```

## ★ 三条铁律

1. **只减不丢** —— 减下来的**原文必须进日记**，这是可回溯的前提。
2. **归档 ≠ 删除** —— 老日志移到 `archive/`（**留档、不再注入**）；日志是经验，别真删。
3. **先备份再大改** —— 大改前先复制一份到 `archive/<名字>-<日期>.md`，改坏了可回滚。

## 关于「注入阈」（★ 实测重标）

- ★★ **客户端按「字符数」截断每个记忆文件，硬上限 ≈10000 字符**
  （**内置，非配置项、改不了**）。
  - **实证**：某日长期记忆 11116 字符 / 20347 字节，注入**恰在第 9990 字符处被砍**
    （尾部整段未进入上下文）。
  - ⚠ **旧口径「约 32KB / 触发线 27.2KB」是错的**：
    ① 单位错（那是**字节**，中文 1 字 ≈ 3 字节 ⇒ 显示"占 42%"时实际已到 75%）
    ② 27.2KB(≈9300 字) 比硬上限还高 ⇒ **永远不会响**。
    后果是"**假绿**"：健康检查报 ✓ 的同时，**尾部铁律每轮都被静默截掉**。
    ⇒ 教训：**尺子的单位要对得上被量的东西**；**报绿不等于没丢东西**。
- ★★ **第二层（用户级 · 跨项目）有独立上限 ≈4000 字符**，超出的尾部**每轮静默丢失**。
- ★ 归档 / 日记**务必放在不被注入的地方**（子目录）——
  否则它们自己会越长越大，**反噬注入预算**。

## 换机提醒

`memory/` 是**本机工作区**的目录 —— **不在 git、不在资料库** ⇒ **换机就没了**。
所以成体系的经验要及时**外移**：进仓库 `docs/`（跟 git 走）或跨机可检索的知识库。
