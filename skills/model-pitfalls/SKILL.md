# 模型陷阱画像：错误带"模型烙印"

> **一句话**：**"哪个模型犯的错"要写进画像** —— 这样**切换模型后，别的模型来跑任务也能看到警示**。

---

## 一、为什么要有这个

提出者原话：

> 如果你能知道自己现在是什么模型的话，最好也把对应错误的相关注释对应到对应的模型身上，
> 这样**哪怕切换模型，有些烙印能定在上面**，然后其他模型来跑任务的时候也有警示作用。

**本质**：错误不只是"这次犯的"，而是「**这类模型容易犯的**」
⇒ 给后续模型**画像警示**。

> ★ 这条思路的反面很常见：**把错误记成"项目的问题"** ——
> 于是换模型之后，同样的坑**换个模型再踩一遍**，因为没人知道"上一个是谁踩的"。

---

## 二、怎么知道自己是什么模型

- **看系统提示**：`This conversation is powered by <模型名>`
- **或看连接器 / 配置**：`models.json` 里的 `id` / `vendor`

---

## 三、画像文件（单一真源）

**位置**：`rules/模型画像.md`（仓库内，**跨模型可读**）

**格式**（每条记录）：

```markdown
## <模型名>

### <错误名>（<日期>）
- **场景**：<在什么任务里犯的>
- **错误**：<具体犯什么错>
- **根因**：<为什么犯（认知 / 习惯 / 参数 / …）>
- **教训**：<以后该怎么做>
- **来源**：<日志 / 提交 / 对话>
```

---

## 四、一个真实案例（第一次记录长什么样）

```markdown
## <模型名>

### 没读已有实现的注释就重造轮子（2026-10-15）
- **场景**：把一批节点从一个空间移到「待删归档」空间
- **错误**：直接调平台的 `move-node` 接口，把「**空间 ID**」当成
  `--target-parent-id` 传了进去 ⇒ 报 `code=12607 permission denied`
  ⇒ **误判为"权限问题"**，建议使用者"手动删或去开权限"
- **根因**：**没读那个已有脚本的注释**（那里前一天就写明了三个坑，
  包括"跨空间时 `--target-parent-id` 必须是目标空间里的**真实节点**，不是空间 ID"）
- **教训**：**复用已有实现前，必须先读它的注释 / 实现**；
  报错信息要当"**参数问题**"来读 —— `permission denied` 不一定是"你没权限"，
  也可能是"**你传错了**"
- **来源**：当天工作日志「一次不该发生的错误」
```

> ★ 注意这条案例的结构：它**没有停在"我错了"**，而是把错误**归到"哪一类模型容易这么认为"**上 ——
> 这才是它能跨模型起作用的原因。

---

## 五、怎么用（跑任务前）

1. **读画像** —— 看**我这个模型**犯过什么错
2. **警惕** —— 如果当前任务**类似**（如"移动节点 / 调 API / 复用已有实现"）
   ⇒ **先读注释 / 实现**再动手
3. **记新错** —— 犯了新错 ⇒ **追加到画像**（**带模型名**）

---

## 七、边界

- 画像**不是追责**（不批评哪个模型差），而是**沉淀经验**（这个模型在这个场景容易犯什么）
- 画像**不替代**技能里的"坑"章节 ——
  技能的坑是"**这个技能怎么踩**"，画像是"**这个模型怎么踩**"
- 切换模型后：**新模型读画像**，看到前任的教训 ⇒ **不重蹈覆辙**
