# 多机部署 · 分级授权 · 备份还原

适用场景：要把这套系统**装到多台电脑**（同事 / 没有业务归属的成员），
且**不想所有人都能改库** —— 只给特定人修改权限，其余人**只要下载和阅读**。

**仓库**：`{{REPO}}`　**远端**：`{{REMOTE}}`（main）

---

## 〇、★ 权限矩阵速查（"给他什么权限？"一问即答）

| 角色 | 申请箱 | 审批与资料 | 技能图书馆 | 分支 | 额外 |
|---|---|---|---|---|---|
| **主维护者** | owner | owner | owner | `main` | — |
| **开发者 / 协作者** | 编辑者 | 只读 | 只读 | `dev` | `dev` 写权限 |
| **普通员工** | 编辑者 | 只读 | 只读 | `pub` | — |

**给用户的答复 = 三段**：

1. **界面要加什么**（★ 权限**只能在界面上加**，脚本做不到）—— 逐一列出「空间 + 角色」；
2. **本机要配什么** —— 填 `accounts.json`；其余**用到才问**；
3. **拿哪个分支** —— 员工 `pub` / 开发者 `dev` / 你 `main`。

**权限变更场景**：

| 场景 | 改什么 |
|---|---|
| 加新员工 | 三空间加成员（申请箱 = **编辑者**；审批与资料 / 技能图书馆 = **只读**）|
| 员工 → 开发者 | 加 `dev` 写权限；**资料库权限不变** |
| 开发者 → 员工 | 收回 `dev` 写权限 |
| 员工离职 | 三个空间移除该成员 |
| ★ 新增数据表 | 先定「落哪个空间」（**空间决定谁能看**）→ 更新矩阵文档 |

## 〇·补、员工机「远端连不上 / 推送挂起」怎么修（实测）

**症状**：员工机跑 `git pull` / `git push` 后**卡住不动**；禁用凭据助手立刻报
`could not read Username for 'https://...'` ⇒ **本机 https 凭据助手没有缓存凭据**。

**推荐修法（一劳永逸）：改用 SSH**（密钥是**员工自己的**，不用共享账号密码）

```bash
# ★ 在【员工机】上做（不是维护者机）
ssh-keygen -t ed25519 -C "<员工邮箱>"        # 一路回车
cat ~/.ssh/id_ed25519.pub                    # 复制这行公钥

# 把这行公钥贴到【他本人的代码平台账户】：头像 → 设置 → SSH 密钥 → 新增
# 然后把仓库远端从 https 换成 ssh（只改本仓库，不动全局）：
git remote set-url origin git@<平台>:<组>/<仓库>.git

ssh -T git@<平台>                             # 验证（返回欢迎语/权限提示即通）
```

> ★ **要点**：
> - **公钥绑"他本人"的账户** —— 别用维护者的密钥（那是**身份穿透**，会被身份校验脚本判成冒用）；
> - **只改本仓库的 remote** ⇒ 不影响他别的仓库；
> - **提交身份**也只设本仓库：`git config user.email "<他本人邮箱>"` / `user.name "<他的署名>"`
>   （**不碰 `--global`、不冒用维护者**）。

**关于"能推什么"**：SSH 只解决**连不上 / 挂起**，**不改变权限**。
能不能推某个分支，**以平台给他的角色 + 该分支的保护设置为准**（推被拒 = 没权限，别硬试）。

## 一、核心结论：**Git 只管网盘（代码），不管电脑（数据）**

| 资产 | 权威方 | 谁动 |
|---|---|---|
| 脚本 / 技能 / 规则 / 文档 | **远端仓库** | 有写权限的人 |
| `config/*.json`、定时任务、登录态、凭据、产物 | **各自本机** | 各自（**不进 git**） |

因为配置根本不进 git，所以「多人部署」并不会造成配置冲突 ——
**权限控制要控的是 git 写权限，不是配置文件。**

## 二、★ 权限分级（核心诉求：只给特定人修改权）

### 2.1 代码平台官方角色矩阵（记忆锚点）

| 角色 | 级别 | 能做什么 | 典型用途 |
|---|---|---|---|
| Guest | 10 | 仅访问 | — |
| Follower | 15 | 关注 | — |
| **Reporter** | 20 | **只读**：可 `clone`/`pull`/下载/浏览，**不能开分支、不能 push** | ★ **给「只需下载和阅读」的人** |
| **Developer** | 30 | 可推**非保护分支**、可发 MR；**推不了受保护分支** | 给协作方（改动走 MR） |
| **Master** | 40 | 可推**受保护分支**、可管成员 | ★ 给**你**（维护者） |
| Owner | 50 | 仓库所有权限（可删库、改成员） | 建库人 |

> 保护分支的成员权限门槛：**至少要 Reporter**。

### 2.2 三种推荐配置（对号入座）

| 你的诉求 | 配置 |
|---|---|
| **只有我能改，其他人只读**（最常见） | `main` 设**保护分支** + 只留 **Master=你**；他人一律 **Reporter** |
| 给协作方独立发布权，但要留一手 | `main` 保护 + 只留 Master=你；协作方 **Developer**（走 MR 由你点合并） |
| 信任的协作者，允许直推 | `main` 保护 + Master=你 + 协作者；或干脆不保护 main |

**⇒ 推荐第二种**：协作方 Developer，改动一律走 MR，**合并权只在你手里**。
效率不够时再升为 Master（并且**先确认备份已开**）。

### 2.3 手工动作（agent 无法代做，必须用户/管理员在网页操作）

> ⚠ **「分配角色」和「保护分支」是两个不同页面，别混**：
> - **成员管理**：给**人**定角色 —— Reporter / Developer / Master
> - **保护分支**：给**分支**定规则 —— 谁能推、谁能合并
> 带下拉框的那个页面是**后者**，它**不会**给人分配角色。

**① 成员管理页**：加人 + 选角色。

- **路径**：项目 → **设置 → 成员 → 新加成员** → 搜人 → 选角色 → 添加。
- ★ **搜什么**：搜索框支持 **用户名 或 账号 ID**（两者都行）。
  ⚠ 但**他必须已注册、且设置过用户名**，否则**搜不到** —— 这是最常见的卡点。
- **备选路径**：若你们有共同**项目组**，可把整个组邀进项目（更省事）。
- 加为成员后他会**自动关注**该项目 —— 所以「关注」是**结果**，不是授权前提。

**② 保护分支页**（以 `main` 为例）：

1. 「选择分支」→ `main` → 保存变更。
2. ★ **「允许推送代码」这个下拉最重要，它决定协作方能不能绕过 MR 直推**：

   | 选项 | 实际效果 | 什么时候选 |
   |---|---|---|
   | `仅分支成员（除了 Reporters）` | **只有白名单里的人**能推 | 最严：只有你能改 |
   | `Master 及以上 + 分支成员` | Master 及以上都能推 + 白名单也能推 | ★ **推荐**（不怕把自己漏掉） |
   | `Developer 及以上 + 分支成员` | **所有 Developer 都能直推 main**，绕过 MR | 想给协作方独立发布权时 |

3. **分支成员白名单**在同页最下方。添加时还有一个 **「访问角色」下拉** ——
   它是**分支级角色**，只对这条分支生效，与项目级角色**取较高者**。
   ⚠️ **白名单只能"提权"，不能"赋权"**：**项目级才是地基**。
   要给某人"开分支 / 发 MR"的能力，必须把**项目级**给到 Developer；
   只靠白名单会造出"能推 main、却开不了自己分支"的怪状态。
4. ⚠️ **最常见的自锁**：选「仅分支成员」却忘了把自己加进白名单 → **连你自己也推不上**。
   ⇒ 正确姿势：**先把自己加为分支成员（角色 Master），再把推送策略收紧。**
5. ★ **「分支成员」与「允许推送代码」必须配合看，只看一个会误判**：

   | 白名单 | 「允许推送代码」 | 实际结果 |
   |---|---|---|
   | 只加了你自己(Master) | `仅分支成员` | 只有你能推 ✅ |
   | 只加了你自己(Master) | `Developer 及以上 + 分支成员` | **所有 Developer 也能推** ❌ 以为挡住了、其实没挡 |
   | 加了协作方(Developer) | 任意 | 协作方能推（分支成员身份提权） |

**③（可选）代码评审**：开「必须通过 MR」「必要评审人 = 1」。

> 这三项**没有靠得住的 API 路径时就让用户手点**，**别硬编脚本假装做了**。
> 若对方机器上有浏览器自动化桥接，可提议代点 —— 但这是**生产权限变更**，先让用户确认。

### 2.4 只读成员怎么拿到代码 / 怎么提改动

- **拿代码**：`git clone {{REMOTE}}`（Reporter 足够）。
- **提改动**：Reporter 不能开分支 → 让他 **Fork 到自己空间**改，再发 MR；或直接给你 patch / 截图。
- **写不了不用慌**：他能跑全套（脚本 + 技能 + 定时任务都在本机），只是改不了源码。

### 2.5 「要不要给 agent 管理员权限？」—— **不需要**

- agent 推送用的是**你本机的 SSH 密钥**，commit 身份就是你自己 ⇒ 平台眼里只有一个账号。
- 角色是分配给**人**的；把 agent 加进成员列表**不会**改变它能做什么。
- 多一个成员账号 = 多一份凭据要管 + 多一个可被冒用的入口，**零收益**。
- 唯一需要权限的动作是「推到保护分支」，而它已经借你的密钥完成。
- （可选加固）若希望 agent 也只能走 MR：给它单独账号 + 只给 Developer。

### 2.6 分支策略与合并验证（让协作者独立开工）

| 分支 | 是否保护 | 谁能推 | 定位 |
|---|---|---|---|
| **`main`** | ✅ 保护 | **只有你**（Master） | **稳定线** —— 随时可跑、可交付 |
| **`dev`** | ❌ 不保护 | 协作者（Developer） | **协作线** —— 新功能先落这里 |

协作者也可从 `dev` 再切 `feature/xxx`（更细粒度，推荐）。

> ⚠️ **平台的合并请求只做 `diff` 比对与评审流程 —— 它不会替你跑任何测试。**
> 「能不能跑通、有没有破坏通用化」**必须自己验证**：

```bash
git fetch origin
bash scripts/pre-merge-check.sh origin/dev    # 隔离检查（临时目录），不动你当前工作区
```

它依次跑：JS/PY 语法 → 通用化自检 → 占位符检查 → 配置体检。**全绿才合并；有 ✗ 让作者修。**

**静态检查 ≠ 能跑通**：涉及业务链路的改动，再跑冒烟（有 `--list` 类只读模式的脚本先跑它）。

- 出问题回退：`git revert <merge-commit>`（**优于 `reset --hard`**）；
  整库坏了用 bundle 还原（见 §四）。
- 完整流程：见仓库内的分支与合并文档。

## 三、给新同事部署（完整步骤）

**前置：先解决「他能不能拿到代码」**

- 把他加为 **`Reporter`**（只读即可 clone）+ `main` 设保护 —— 见 §2。
- ⚠️ **「关注项目」≠ 授权**：关注只是**订阅通知**。能否 clone 取决于**他是不是项目成员**。
  私有仓库必须由你把他**加为成员**；公开仓库虽然人人可 clone，但等于**所有人都能看**。
- **SSH 公钥要加在「他自己的」账户** —— **不是加到你的账号上**。
  平台靠公钥认人，加错了会出现「他的机器推着你名下的提交」。
  （有些平台的旧算法在新版 OpenSSH 下被默认禁用 ⇒ 可能需在 `~/.ssh/config` 里显式允许。）

```bash
# ① clone（在他的机器上，用他自己的 SSH 密钥）
git clone {{REMOTE}}
cd <clone 出来的目录>
# ② 环境探测（★ 只探测本机路径，**不问任何业务配置**）
node setup.mjs
# ③ 部署脚本 / 技能 / 规则到本机（自动展开占位符）
node install-skills.mjs
# ④ 自检（应「✅ 全部通过」）
node scripts/check-generality.mjs
#   推仓库前跑一条总检（身份 + 通用化 + 配置 + 推送环境）：bash scripts/preflight.sh
# ⑤ 重建定时任务（任务不跟账号同步，必须逐条建）→ 用 `automation-rebuild`
```

> ★ **业务配置按需索取**：操作者标识 / 空间与表 ID / 账号清单**都不在部署时索取**，
> 而是他**第一次用某个功能时**只问那几项，并附「是什么 / 去哪拿 / 怎么填」。
> 首次配置引导与上手导览 → 技能 `onboard`。

> ⚠️ **clone ≠ 能跑**。除代码外还需要：运行时、平台环境与连接器、
> **浏览器桥接**（要操作后台的话），以及填好的 `config/*.json`。

**他的账号清单和你的不一样是完全正常的**：每人一份，
账号 ID 唯一决定归属 ⇒ **互相不干扰**。

### 3.1 无归属员工（这类人会存在）

- **照样能跑**：清单里没有他名下的，就填**他能看的那批账号**，
  可见范围按需设成 `group`（+ 组名前缀）或 `company`。
- **权限给 Reporter 就够**（他不需要改库）；要改就 Developer + MR。

### 3.2 新机器上「技能 / 定时任务 / 连接器」不会自动跟过来

它们**不随账号同步**，必须靠「仓库 + 一键重建」：
下发脚本技能 → 重建定时任务 → **逐条回读校验**。

## 四、★ 整库备份与还原

### 4.1 备份

```bash
cd "{{REPO}}"
bash scripts/backup-repo.sh            # 默认 → {{REPO}}/.backups/，保留 10 份
bash scripts/backup-repo.sh <目标目录> 20   # 自定义目录 + 保留 20 份
```

- 原理：`git bundle create --all` —— **打包全部历史**（含所有分支），单文件、可离线、可校验。
- 产物：`repo-<时间戳>.bundle` + `manifest-<时间戳>.txt`（记录 HEAD / 分支 / 文件数）。
- 超期自动轮转删除旧份。
- **推荐时机**：`git push` 之前跑一次；或挂成定时任务。

> ⚠ **备份要放另一个盘 / 网盘**：脚本默认放在仓库内 `.backups/`，
> **本机与备份同盘同坏 = 等于没备**。脚本末尾会提醒，**务必照做**。

### 4.2 还原（三种情况）

```bash
# 情况 A：整个库没了 → 从 bundle 克隆
git clone "{{REPO}}/.backups/repo-<时间戳>.bundle" <新目录>

# 情况 B：现有库里丢了历史 → 回灌
cd "{{REPO}}"
git fetch "<bundle 文件>" 'refs/*:refs/*'

# 情况 C：只是改错了想回退某次提交
git log --oneline -10                 # 找到目标
git revert <commit>                   # 生成反向提交（推荐，历史可追溯）
# 或 git reset --hard <commit>（★ 破坏性：会丢未提交改动，慎用）
```

**先校验再用**：`git bundle verify <bundle>` → 应输出 `records a complete history`。
**从远端恢复也可以**：`git clone <远端地址>`（前提是远端没被一起弄坏 ⇒ 所以 bundle 备份仍有意义）。

## 五、易错点

- **★ `main` 是代码分支，不是"员工合集"**（高频误解）：保护分支页里的「成员」是**这条分支的白名单**，
  **主体是分支**、员工只是被授权的**对象**；「访问角色」= 该成员**在这条分支上的权限等级**
  （与项目级角色**取较高者**），**不是标签**。
- **平台的「标签」是 git tag**（版本标记如 `v1.0.0`），与权限**毫无关系**，
  别把"给分支加白名单"理解成"给员工上标签"。
- **两层权限的关系**：`项目级（成员管理）`定基础角色 → `分支级（保护分支）`可**提权**；
  生效 = max(项目级, 分支级)。
- **平台昵称 ≠ 本机操作者标识**：本机配置里的身份标识是「业务后台的操作者名」，
  平台成员列表显示的是「平台账号昵称」。**两者本来就可以不同** ⇒
  看到对不上是**正常**的，别据此判断"加错人了"。
- **别把 `main` 保护起来却没给自己留 Master** → 谁都推不了。
- **Reporter 推不上不是故障**：那是设计如此。别为了「让他方便」直接给 Master，**先问需求**。
- **备份别只留本地同一块盘**；`.backups/` 与 `*.bundle` 应在 `.gitignore` 里。
- **换行符**：新同事首次 `clone` 后若 `git status` 报大面积改动，跑一次 `git add --renormalize .`。
- **仓库里不得出现本机绝对路径**：换机部署前先跑通用化自检（它的 F 项会抓）。
- **`{{ }}` 是占位符不是模板引擎**：只做「占位符 ↔ 本机绝对路径」的字符串替换，
  替换按**值长度降序**（`{{HOME}}` 是别的前缀）。

## 六、一句话交付口径

> **代码：远端一份真源，`main` 加保护，你 Master、协作方 Developer 走 MR、其他人 Reporter 只读。
> 数据：`config/*.json` 各自本机一份，互不干扰。
> 兜底：`bash scripts/backup-repo.sh` 打全量 bundle，放另一个盘，出事 `git clone <bundle>` 还原。**
