# 定时任务：快照刷新 · 跨机重建 · 回读校验

> 本文里的 `{{…}}` 是**占位符**写法 —— 仓库里只存占位符，**读取时才展开**成本机真实路径（见 §一·一）。

## 零、前提事实（先认清，否则会白费工夫）

**平台上的定时任务默认是「本机产物」，不跟账号走。** 别信教程，先取证：

| 观察点 | 查什么 | 结论 |
|---|---|---|
| 任务存储 | 本机客户端数据库里的任务表（`automations` 之类） | **纯本地** |
| 账号同步通道 | 同步表里**装的是什么**（本例全是"对话消息"记录，**零条**技能 / 任务） | 任务不进同步 |
| 技能文件 | 本机技能目录 + 缓存里的来源字段与**绝对**路径 | 本地 |
| 技能开关 / 覆盖 | 本机设置文件里的覆盖项 | 本地 |

⇒ **随账号漫游的只有「对话记录 + 云端画像」；技能、任务、连接器、身份文件全在本机。**
这是官方的安全设计，不是 bug。

⚠ **网上的"云端优先协同 / 加密恢复码"之类教程可能是编造的**：本机配置里那个看着像总开关的键，
实际只是**某个消息渠道的配置**（本例 `claw.channels.*`）。⇒ **别去客户端里找不存在的菜单** ——
要判定"什么会同步"，就照上表**去查存储与同步通道**（这是本项目一贯的"取证 > 推断"）。

⇒ 所以采用 **「仓库承载 + 一键重建」**：任务快照进仓库，换机后按本技能重建。

### ★★ 但先别急着建 —— 重建的阀门：技能软 · 任务硬

两类东西常被一起问，规则完全不同：

| 类型 | 判据 | 为什么 |
|---|---|---|
| **技能**（一份文本） | **软阀门 · 硬执行**：需求**模糊也算数**，判为"可能有需求"就**直接建** | 多一个技能≈0 边际负担；**漏建 = 能力永远不在，且没人发现** |
| **任务**（会定时跑） | **默认关、需求侧开**：不明确就**先不建** | 会占**独占资源**（浏览器会话 / 页面锁） |

- 先问「**你要不要开这几个定时任务**」—— **不同人职责不同，A 需要的技能未必是 B 需要的**；
  对方说不需要 / 还不确定 ⇒ **一条都别建**，回一句「想开的时候随时说，我把配置也一起带你配好」。
- 配置里的「机器角色」是**默认值，不是否决权**：需求侧明确要 ⇒ 照建，
  但先查**是否与已有任务抢同一独占资源**（抢 ⇒ 只提示冲突，交需求方裁决）。

**仓库位置**：`{{REPO}}`
**快照**：`automations/automations.json`（结构）+ `automations/prompts/*.txt`（prompt 全文）
**工具**：`scripts/localize-prompts.py`（占位符**展开** + 校验）

## 一、方向 A：刷新快照（本机真实任务 → 仓库）★ 改过任务后必做

快照是**手工产物，必然漂移**。已踩过：「rrule 记 `INTERVAL=1` 而实际是 2」
「已删除的任务仍在列表」「prompt 快照与线上**双向**漂移，两边各缺对方段落」。
⇒ **改过任何任务后立刻刷新。**

```text
① 列出本机真实任务（平台任务工具 list）
   → 拿到 id / name / status / scheduleType / rrule
   → 与 automations.json 的 automations[] 逐条比对，**只改差异字段**

② 对每条任务 view 拿真实 prompt（里面是**本机真实路径**）
   → ★ **先收敛成占位符，再覆盖快照**：
       把返回的 prompt 写到临时文件 /tmp/p.txt
       node scripts/placeholder.mjs shrink /tmp/p.txt > automations/prompts/<对应>.txt
   ★ **绝不要手工拼 prompt 快照** —— 手工拼 = 必然漂移
   ★ 也**不要直接贴真实路径** —— 那会把本机路径提交进仓库（绕过占位符体系，害协作方）
      判据：提交前 `node scripts/placeholder.mjs check` 必须输出「✓ 全部已占位符化」

③ 新建 / 删除任务 → 同步增删 prompts/ 下的文件，并更新 prompts/README.md 的文件清单表

④ 在 automations.json 的 _变更记录 追加一行（日期 + 改了什么 + 为什么）

⑤ 提交推送（见 §四）
```

**注意**：`id` 是**本机生成**的，换机器重建后必然不同 ⇒ 快照里的 id **只作对照，不要照抄**。

### 一·一 ⚠ 快照里**只有一类**占位符：路径类

| 类 | 形态 | 谁负责 | 工具 |
|---|---|---|---|
| **路径占位符** | `{{NODE}}` / `{{REPO}}` / `{{WB_ROOT}}` / `{{HOME_SCRIPTS}}` / `{{SESSION}}` | 由脚本自动展开 / 收敛 | `expand` / `shrink` / `check` |

★★ **业务值一律移出 prompt**（"方案 C"）：检索标签、使用者、空间与表 ID、主体清单
**全部由 prompt 指向 `config`**，运行时再读。带来三个好处：

1. **换人 / 换库只改 config 一处** —— 不会出现"改了配置但任务还写旧表"；
2. **快照刷新可以放心 `shrink` 覆盖** —— 不会再把真实人名 / 表 ID 带进仓库；
3. **某项未配置 = 本次不归档** —— 而不是"建不了任务"或"写错表"。

> ⚠ **历史机制已废弃**：早期快照里还有**业务 ID 占位符**（`<accountTag>` / `<DB_*_ID>` 这类角标），
> 需要 agent 重建时手工按 config 取值。**看到角标就说明它是旧版**，按新版重写。

⚠ `{{SESSION}}` 是**会话工作区路径**，**与浏览器自动化里的「会话名」（形如 `<会话名>` 的标签组名）
完全是两回事**，别混用：`--session=<会话名>` 用的是**字面量**，**不能**写成 `--session={{SESSION}}`。

### 一·二 ⚠ 快照 ↔ 线上是**双向漂移**，不是单向落后

实测：线上几条任务里，有的**缺整节**（快照有）；而另一条的快照与线上**又各缺对方段落**。
⇒ **谁都不是超集**，别假设「线上一定比快照新」或反之 —— **刷新前先逐条 diff，缺什么补什么**。

## 二、方向 B：重建任务（仓库快照 → 本机）★ 换机时做

### 第 0 步：**先问需求 → 再查配置 → 齐了才建**

**① 先问「你要不要开这几个定时任务」**（见 §零 的阀门）。

**② 对确定要开的，逐条查它需要的配置**；配置没齐的**同样先别建**。

重建任务的本质是「给这台机器装上闹钟」。**闹钟响了却跑不起来，比没有闹钟更糟** ——
无人值守的失败任务会反复报错、刷屏，还会把真实问题盖住。
⇒ 顺序永远是：**先查每个任务需要的配置，齐了才建。**

```bash
cd "{{REPO}}"
node scripts/ensure-config.mjs --tasks          # 人话：逐条「任务 → 能不能建 → 缺哪几项」
node scripts/ensure-config.mjs --tasks --json   # 给 agent 解析
```

映射写在 `automations.json` 的 `requires` 字段（字段定义在 `scripts/config-schema.mjs`）。

**对 ✗ 的任务，按这个顺序处理**：

1. **当场问用户** —— 这正是"落地时直接询问"的最佳时机：他人就在，也已经知道系统能干什么；
   用 `missing[]` 里现成的 `question` / `howto` / `set`，**别自己另编一套说法**。
2. 用户答了 → `--set` 写回 → **再跑一次确认转 ✓** → 然后才建这条任务。
3. 用户**答不上来 / 不想现在配** → **跳过，不要建**，并记入「**本次未建任务清单**」，
   汇报里写清「缺什么 → 去哪拿 / 找谁要」。
4. ⚠ **绝不要为了"把快照里几条都建满"而建一个必然失败的任务**。宁可少建一条，把原因说清楚。

> ⓘ 与「跑起来才发现配置没填怎么办」的关系：那一段是**任务已在跑**时的兜底（无人值守场景）；
> 本步是**建之前**的前置闸门。两道闸方向不同，别混。

### 第 1 步：确认 prompt 已占位符化 → **展开读取**（★ 别跳过）

```bash
cd "{{REPO}}"
"{{PY}}" scripts/localize-prompts.py --verify-only                                  # ① 仓库 prompt 是否已占位符化
"{{PY}}" scripts/localize-prompts.py --expand "automations/prompts/<任务>.txt"      # ② 展开成本机真实路径版
```

**机制**：仓库 `prompts/*.txt` 里存的是**占位符**，真实路径只存在于本机部署位置；
展开值来自本机 `config/paths.json`（解释器路径 / 程序根 / 会话工作区自动探测）。

> ⚠ **创建任务时，用的一定是 `--expand` 的输出**，**不能直接把 `prompts/*.txt` 贴进去** ——
> 那样会把 `{{NODE}}` 原样写进任务，任务必失败。
>
> ⚠ 老做法是「`--apply` 就地替换成本机路径」，那会把真实路径写进**仓库工作区**
> （多人协作时表现为 diff 全是路径噪声）—— **已废弃**。现在仓库永远保持占位符，只在读取时展开。

### 第 2 步：逐条重建（走平台的**任务工具**，**不要碰数据库**）

```text
create(
  name         = <任务名，照抄>,
  prompt       = <prompts/<文件>.txt 经 --expand 展开后的**全文**>,   ← ★ 不是直接复制文件
  scheduleType = <"recurring" | "once">,
  rrule        = <recurring 时必填，见下方速查>,
  status       = "ACTIVE",                        ← 先建，验证通过再确认启用
  cwds         = <该任务的 cwd，换成本机实际工作空间目录>
)
```

**rrule 速查 · ★ 与 `automations.json` 逐字对齐**（下表是通用规则，具体值照抄快照）：

| 任务 | rrule |
|---|---|
| 每 N 小时 | `FREQ=HOURLY;INTERVAL=<N>` ← **核对 N**，别照抄记忆 |
| 每天某时刻 | `FREQ=DAILY;BYHOUR=<H>;BYMINUTE=<M>` |
| 每天一条、但要跑两次 | **拆成两条任务**（见下方限制） |

⚠ **平台限制（实测）**：`DAILY` **不支持逗号分隔的 `BYHOUR`**（`BYHOUR=4,16` 直接报错）
⇒ 「上午 4 点 + 下午 4 点」**必须拆成两条独立任务**（本项目复审任务有两条就是这个原因）。
⚠ `HOURLY` **不要加** `BYHOUR` / `BYMINUTE`（加了反而不对）；要限定只在工作日跑，用 `BYDAY`。

### 第 3 步：回读校验（**必做，否则等于没建**）

```text
① list → 逐条核对：name / status / scheduleType / rrule **全部**与快照一致
        → **条数一致**（少一条就是创建失败了）
② 抽查（至少 1 条，建议全查）view → 把返回的 prompt 与 `--expand` 展开后的文本**整段比对**
        → 若不等，说明粘贴出了问题，**删掉重建**
③ 核对 cwds 指向的目录在本机真实存在（不存在 ⇒ 任务必失败）
```

**校验清单**（逐项打勾）：

- [ ] **建之前**跑过 `ensure-config.mjs --tasks`；配置没齐的任务**没有被建**（已记入「本次未建任务清单」并说明缺什么、去哪拿）
- [ ] 每条任务 rrule 与快照逐条一致（**小时级任务核对 INTERVAL**）
- [ ] 每条 `cwds` 指向本机真实存在的目录
- [ ] `localize-prompts.py --verify-only` 输出「✓ 全部已占位符化」（仓库 prompt 干净）
- [ ] 每条任务的 prompt 是 **`--expand` 展开后**的内容（里面**没有** `{{…}}` 残留）
- [ ] 每条任务都含「前置保障」段（如浏览器桥接就绪），且与业务脚本**串在同一条命令**里
- [ ] 每条任务都含「**配置没填怎么办**」段（无人值守下的正确处置 —— 别停在原地等回答）
- [ ] 先逐个「立即运行」手动验证，全绿后再放心启用定时

### 第 4 步：单任务试跑（强烈建议）

定时任务开跑前，先用**对应技能手动跑一轮**验证链路 —— 手动能跑通，定时才值得开。

## 三、易错点清单

- **不要用 shell / 数据库客户端直接读写平台的任务库来"同步任务"** —— 违反平台约束，
  且两机同时开机有 **SQLite 双写损坏**风险。**一律走平台的任务工具**。
- **不要在"任务同步"上期待自动化** —— 官方不支持；「仓库承载 + 一键重建」就是当前最优解。
- **`BYHOUR` 不支持逗号**（见上），一天两个时刻必须两条任务。
- **`id` 不跨机**：照抄旧 id 没有任何意义，重建后回读拿新 id。
- **快照必须用 view 拉真实 prompt 覆盖**，手工拼一定漂移。
- ★ **改线上任务之前，也先 view** —— **别拿快照当线上**。快照可能「落后」，也可能「**过度悲观**」：
  实测快照记某任务「字段映射过时、待更新」，view 一拉却发现在**另一条任务里早已改好**（还多了新职责）。
  ⇒ **若照快照去改，会把别人的成果倒退**。铁律：**先取线上真值，再决定改不改**。
- ★ **从 view 拉到的 prompt 含本机真实路径，必须先 `shrink` 再写进快照**，
  否则真实路径会被提交进仓库、破坏占位符体系；提交前用 `placeholder.mjs check` 自查。
- ★ **重建任务时 prompt 必须用 `--expand` 的结果**，建完在 view 里确认**没有 `{{` 残留**。
- **「前置保障」与业务脚本必须串在同一条命令**里（`A && B`）：分两次跑，中间守护进程会被回收。
- **先建后验再启用**：不要建完就宣布完成，必须过 §二·第 3 步 的回读校验。
