# 自动化脚本性能：先量 → 再改 → 后验

> **一句话**：**没有阶段计时的脚本，改等待就是盲改。**
> 实测教训 —— 盲改某个脚本只省 10%；而装了埋点后，一眼看出瓶颈在**导航占 73%**。

适用对象：所有走**本地桥接**操作已登录浏览器的脚本。

---

## 一、埋点先行（不许跳）

**工具**：一个 `lib/timing.mjs`（随脚本下发）。

**用法**（三行接入）：

```js
const _T = await import("./lib/timing.mjs").catch(() => null);   // ★ 容错：缺了就降级为空操作
const markWait = _T?.markWait ?? (() => {});
const markNav  = _T?.markNav  ?? (() => {});
const markEv   = _T?.markEv   ?? (() => {});
const installExitReport = _T?.installExitReport ?? (() => {});
const sleep = (ms) => { markWait(ms); return new Promise((r) => setTimeout(r, ms)); };
installExitReport((line) => { try { appendFileSync(LOG_FILE, line + "\n", "utf8"); } catch {} });
```

**打点位置 = 底层封装，不是业务步骤**（自动覆盖所有调用点）：

| 封装的函数 | 打什么 | 为什么 |
|---|---|---|
| `sleep` | `markWait(ms)` | ★ **必须动态累加** —— 静态数 `sleep` 出现的次数会**漏算循环内的重复执行**（实测：静态数出 7 秒，实际 **108 秒**） |
| `navigate` | `markNav(ms)` | 页面加载的物理时间 |
| `ev` / `evaluate` | `markEv(ms)` | 桥接调用（实测仅 **27ms/次**，通常不是瓶颈） |

**输出**（收尾自动打，挂在 `process.on('exit')` 上 ⇒ 正常/异常/中途退出都留）：

```
[计时] 总计 237.3s ＝ 导航 61.3s(18 次) ＋ 桥接调用 9.7s(164 次) ＋ 固定等待 164.1s(119 次) ＋ 其它 2.3s
  └ 等待 <脚本>:549 ⇒ 108.0s × 72 次（均 1.50s）
  └ 导航 <脚本>:103 ⇒  58.9s × 18 次（均 3.27s）
```

⚠ **两个必须知道的坑**：

1. **调用点聚合对 `async` 函数失效**：`navigate` / `evaluate` 内部的 `await` 会**截断调用栈**，
   聚合结果会显示成框架内部模块。⇒ **只对同步包装（`sleep`）可靠**；
   要定位 async 路径的调用点，得**手动传标签**。
2. **`installExitReport(...)` 必须在 `const` 定义之后调用** —— 否则撞 TDZ
   （`Cannot access '…' before initialization`，脚本 2 秒即崩）。
   ⚠ **`node --check` 查不出这个**（语法合法，是**运行时**错误）。

## 二、铁律：**先检查、后等待**

★ 这是**最高频、收益最大**的一类改动 —— 实测里四个脚本有三个都栽在这。

```js
// ❌ 错：先等再查 —— 页面早就绪也要白等满
for (let i = 0; i < N; i++) { await sleep(1500); const b = await read(); if (b) break; }

// ✅ 对：先查、没就绪才小步等 —— 就绪快时几乎零等待，上限不变
for (let i = 0; i < N; i++) { const b = await read(); if (b) break; await sleep(300); }
```

**实测收益**：某一处 **108.0s → 21.6s（−80%）**，全脚本 **237s → 124s（−47.7%）**。

**推论**：`navigate` **之后**的固定等待，**几乎总是多余的** ——
`navigate` 本身就会等页面加载；若不放心，后面通常已有轮询兜底。

## 三、自适应冗余（**别给网络留冗余**）

**实测**：目标站点直连（建连 + 首 2KB）= **42ms**，而一次 `navigate` = **7270ms**
⇒ **纯网络仅占 0.6%**；即便把 SPA 几十个资源请求都算上（HTTP/2 并行 2~3 个 RTT）也就 **1~2%**。
⇒ **98% 是 JS 解析执行 + 渲染 + 等后端接口返回。**

**⇒ 结论**：**不要为"网络传输"留固定冗余**（它太便宜），而要把冗余做成「**轮询 + 上限**」：

- 页面快 ⇒ 轮询立刻返回（省时间）
- 页面慢 ⇒ 轮询继续等（不失败），上限（`maxMs`，通常 40~60s）兜底

即**固定 `sleep` 只留"首帧"量级（200~300ms），其余交给轮询**。

⚠ 唯一边界：**轮询间隔别太密** —— **300~350ms 是平衡点**
（桥接调用 27ms/次，但太密会白增次数）。

**已知不可优化项**：**页面渲染本身**（实测某类表格就绪需 ~25s）。
到这一步就**别再压等待**了，那是页面 / 后端的物理时间。

## 四、并行四原则

> 来源：一位同事投递的设计 —— **设计正确，但注意：它在仓库脚本里尚未实现**，
> 别照着文档就以为能并行。

1. **会话隔离** —— 每个并行任务用**独立 session 名** ⇒ 标签组互不干扰、互不误关；
2. **分锁** —— 并发锁**按任务维度分文件** ⇒ 不同模式不互斥、**同模式仍互斥**（防自己踩自己）；
3. **共享资源归属校验** —— 下载中心这类共享资源，按「**时间戳 + 状态 + 特征名**」三重过滤，各拿各的；
4. **渐进式改造** —— 暂不并行的角色**保持原全局锁**，行为不变。

★ 关键判断：**并行的真正障碍不是锁，而是「共享资源（标签页 / 下载中心）能不能各拿各的」**。

## 五、验证纪律（否则数字会骗人）

1. **`node --check` 只查语法**：TDZ、初始化顺序、运行时错误它都查不出
   ⇒ **改完必须实际加载一次**（如 `timeout 4 node <脚本>`，看头几行日志是否正常）。
   ⚠ **写文档时举例的路径要用真实存在的文件** —— 有些检查器会把「docs/」「scripts/」样式的字符串
   **当真引用**扫描，用占位名举例会被报成「失效引用 / 幽灵引用」。**要举就用真实文件。**
2. **必须有**可比基线**：同一台机、同一模式、**同一工作量**。
   ★ 反面教材（真实踩到）：某脚本改前 341s、改后 31s ⇒ 看着"提速 90%"，
   实际是**改后那次的任务量完全不同**（9 个账号全部无新增）⇒ **数字骗人**。
3. **先备份、先提交**：多路会话同时改时 ⇒ **写具体文件路径 add，绝不 `git add -A`**
   （否则你的未提交改动会被别人的提交裹走）。
4. **改完跑自检**：要求 **0 ✗ / 0 ⚠**。

## 六、实测基线（用来说明"必须逐脚本量"）

**四个脚本的瓶颈结构完全不同 ⇒ 必须逐脚本量，不能套用结论**：

| 脚本 | 观测时 | 总耗时 | 其中最大头 | 优化收益 |
|---|---|---|---|---|
| 巡检类 | 101 行数据 | 58 → **44s** | **导航 73%** | −24% |
| 统计类 | 9 个主体 | 333 → **276s** | **导航 66%** | −17% |
| 复审类 | 9 个账号 | 341s | **固定等待 97.6%** | 待复核 |
| 下载类 | 5 个主体 | 237 → **124s** | **固定等待 69%**（单点 108s）| **−47.7%** |
| 桥接调用（通用） | — | — | **仅 27ms/次** ⇒ 几乎从不是瓶颈 | — |

⚠ 上述数字均为**单机单次**观测，**导航耗时波动可达一倍**（同一脚本两次跑 3.98s/次 vs 7.37s/次）
⇒ 报数时**注明观测条件**，**别拿单次当承诺**。

## 七、一个可复制的排查动作（照做即可）

```bash
# 1) 跑一遍，拿计时行（脚本收尾自动输出到它自己的运行日志）
timeout 4 node <脚本>            # 先只确认能加载（防 TDZ）
node <脚本>                       # 正式跑一次（注意是否有写副作用）

# 2) 看 Top 等待点 → 逐个读代码，判断属于哪类：
#    · 「先等后查」        ⇒ 改成先查后等（第二章）
#    · 「导航后的固定等」   ⇒ 缩到 200~300ms，交给后面的轮询
#    · 「循环末尾纯白等」   ⇒ 直接删
#    · 「轮询间隔」        ⇒ 300~350ms（按时间判超时的循环可放心加密）

# 3) 改完：`node --check` + 实际加载 + 跑一次 A/B（**同条件**！）
```
