# 技能投递与分发（投递 → 归纳 → 取用）

**一句话**：技能**打包成本体（zip）+ 说明文档**投到「**投递区**」；
管理者**归纳**成「**注册表**」（只读）；别人**按注册表取用**（下载 → 校验哈希 → 安装）。

> 本文里的 `{{…}}` 是**占位符**写法 —— 仓库里只存占位符，**读取时才展开**成本机真实路径。

## 〇、三个空间，别搞混

| 空间 | 谁写 | 放什么 |
|---|---|---|
| **投递区** | 成员**可写** | 申请单 + **技能投递箱** |
| **注册表区** | 管理者写、成员**只读** | 审批簿 + **技能注册表**（技能清单 = 白名单） |
| **橱窗区** | 管理者写、成员**只读** | ★ **稳定版技能归档**（给新机器 / 新同事一眼看全，见 §六） |

> ⚠ **真源永远是版本库（git）**；这三个空间是"协作与橱窗"，**不是版本库**。
> 安装 / 更新仍走同步脚本（那是"我 ↔ 仓库"的事，见下）。

### 〇·一 与「环境同步」的分工 —— 别混

| | **环境同步** | **本技能**（投递 / 分发） |
|---|---|---|
| 收件人 | **你自己的机器**（我 ↔ 仓库） | **别人**（我 → 别人） |
| 动作 | 下发 / 回收整个环境 | 投递 / 归纳 / 取用 / 归档橱窗 |
| 审批 | 无（自助） | 有（投递区 → 注册表白名单） |
| 粒度 | **整个环境**（脚本 + 技能 + 规则） | **技能这种独立单元** |

> **关系**：环境同步会**捎带技能**（技能本就是环境的一部分）——这种包含是**有意的**，不是重复。
> **给自己的机器同步 → 环境同步；把技能分享给别人 → 本技能。**

## 一、为什么要"打包"（别踩这个坑）

- 技能本体是一份 `.md`，而 **`.md` 不能直接上传**（资料库会拒）；
- ⇒ **必须打包成 zip**（zip 里装 `.md` 没问题）；
- 同时要**配一份「说明」文档** —— 因为 **zip 在云端读不了内容**，
  agent 靠**说明文档**才知道这个技能是干什么的（它也是注册表"功能"字段的来源）。

### 一·一 ★ 技能分类（橱窗的目录结构）

**单一真源**：`scripts/skill-categories.json` —— **改分类只改它**
（投递 / 归档 / 归纳**三处都读这一份**，否则三套分类必然漂移）。

| 分类（= 橱窗里的文件夹） | 装什么 |
|---|---|
| `01·取数与巡检` | 日常取数、投入产出巡检、异常下钻 |
| `02·业务流程` | 某条端到端业务流程的各环节 |
| `03·环境与部署` | 装机引导、仓库同步、多机部署、任务重建 |
| `04·协作与治理` | 申请审批、技能投递分发、通用化守护 |
| `05·系统运维与自检` | 健康体检、台账、清理、记忆蒸馏、告警 |

**三个环节都吃这份分类**：

| 环节 | 怎么用分类 |
|---|---|
| **投递**（成员） | 自动按表判定；也可 `--category "03·环境与部署"` 手动指定（写进说明文档） |
| **归档**（管理者） | 自动放进对应分类夹（**夹不存在会自动建**）；分类改了会**自动归位** |
| **归纳**（管理者） | 注册表新增「**分类**」列（投递时写的优先，否则按表判定） |

⇒ 使用者能**按分类浏览**、**按分类筛选**，不必逐个点开看。
未在表里的新技能 ⇒ 自动落 `99·未分类`（**提醒维护者补登记**，不自作主张归类）。

### 一·二 ★ 分发方式标签

技能有两种来源，必须能**一眼区分**：

| 标签 | 含义 | 装 / 更新方式 |
|---|---|---|
| **仓库同步** | 随版本库走（技能在仓库 `skills/<名>/`） | clone / 同步脚本 |
| **技能库分发** | 只在本机技能目录（**不入仓库**） | 按名字取用脚本 `--name <名>` |

**判定规则一句话**：**技能在仓库里 → 仓库同步；不在仓库 → 技能库分发。**

**三个载体 —— 要同时打，别只打一处**：

| 载体 | 位置 | 谁写 |
|---|---|---|
| **注册表** | `分发方式` 列（枚举：仓库同步 / 技能库分发） | 归档时建字段；**值由管理者补写一次**（生成器是增量更新，不覆盖它） |
| **说明文档** | 首行 `分发方式：…` | 投递 / 归档脚本自动生成 |
| **对外可见的清单**（如云应用） | 字段 + 页面标签 | 同步步骤写入（见 §六·三） |

> **为什么要三处**：① 注册表给管理者和脚本读；② 说明文档给**其他 agent** 读
> （一眼知道该怎么装、要不要走枢纽取用，省一次试错）；③ 云应用给**外部成员**读
> （他们可能没有资料库权限，这是唯一入口）。

## 二、投递区长什么样

```
技能投递/                      ← 可写空间
  └── <技能名>/                ← 一个技能一个文件夹
        ├── <技能名>.zip       ← 技能本体
        └── 说明               ← 说明文档（在线文档，agent 可读）
```

### 二·一 ★「看投递箱」：一条命令

**为什么**：投递**只落在投递文件夹里** —— 没表、没通知，**对外快照里也看不到**。
在界面里逐个点开翻"哪个是新技能"很费劲 ⇒ 用一条命令一眼看完：

```bash
"{{PY}}" "{{REPO}}/scripts/skill-inbox.py"           # 人话表格
"{{PY}}" "{{REPO}}/scripts/skill-inbox.py" --json    # 机读
```

输出每个包：**技能名 / 作者 / 投递时间 / 分类 / 是否已入库 / 节点 ID**，并给出**清理判定**：

| 判定 | 含义 | 该怎么做 |
|---|---|---|
| ✅ 已入库（同内容） | 注册表里有同名且**哈希一致** | 可安全清出投递箱 |
| ⚠ 同名但内容不同 | 注册表里的同名行是**另一份**（常见：仓库版） | **别清**，先看清是不是新版 |
| ✗ 未入库 / 待处理 | 还没进注册表 | 先走归纳（§三·二） |

> ★★ **别只按名字判"已入库"** —— 注册表里可能有**同名但不同内容**的行。
> 实测：投递箱里某技能与注册表里的同名技能**哈希不一致**（后者是仓库版），
> **只看名字会误判成"已入库"从而误删**。

### 二·二 ★ 对外快照（可选）：投递即登记

投递脚本可以在**第 ④ 步**往一张云表补一条记录 ⇒ 管理者在**任何设备**上打开都**立刻可见**，
不必再翻文件夹。两条通道分工：**对外快照 = 一眼可见**（跨设备、不用开仓库）；
**`skill-inbox.py` = 本机细看**（带"能不能清出投递箱"的四档判定）。**两者数据源不同，互为校验。**

| 该云表 | 说明 |
|---|---|
| 身份 | ★ **`技能名 + 内容哈希` 联合唯一键** ⇒ 同名不同版本**各占一行** |
| 状态 | 待处理 / 已入库 / 已拒绝 / 已替代（**改状态仅管理员**） |
| 写入 | 成员写自己的；agent 可**免登录**写（限死"匿名作者 + 待处理"） |

## 三、三个动作（按角色）

### 三·〇 ★ 投递前自检（必跑；有命中**先问一轮**再投）

**为什么**：技能投递最怕把**本机路径 / 身份 / 配置值**一起带出去（本项目多次间断踩到：
本机路径、账号昵称、空间 / 表 ID 混进技能）。**投递前先扫一遍，有命中就先问用户，别默默上传。**

```bash
node scripts/skill-precheck.mjs <你的技能目录>
node scripts/skill-precheck.mjs <技能名>          # 也可只给技能名
```

- 退出码 **0** → 干净，直接进入 §三·一 投递；
- 退出码 **1** → **先别投**！把命中项（文件:行 + 类型 + 值）列给用户，让其三选一：
  - **(a)** 改成占位符 / 去掉本机值 → 改完**重跑本自检**；
  - **(b)** 用户确认必须保留 → 该行加豁免注释 → 重跑通过后再投；
  - **(c)** 取消本次投递。

  **只有拿到用户明确选择后才继续**（这就是"额外询问一轮"，与 `leakcheck` 同一条铁律：
  **发布前的扫描器一旦命中就停，不替用户决定**）。
- 检查项 = 本机配置里的**独有值**（本机路径 / 邮箱 / 远端地址 / 账号标签 / 空间与表 ID /
  业务名与 ID）+ 结构型模式（真实远端地址、疑似密钥）。

### 三·一 成员端 · 投递技能

```bash
"{{PY}}" "{{WB_ROOT}}/skill-submit.py" \
  --skill-dir "<你的技能目录>" \
  --note "这个技能是干什么的、怎么用（可选，但强烈建议写）"
```

返回 `{"ok":true, "skill":"<名>", "sha256":..., "cloudRegistered":true}`。

脚本自动四步：读 `SKILL.md` 提取名称与描述 → 打包 zip → 建技能文件夹 → 传本体 → 建说明文档 →
**④ 登记到对外快照**（管理者立即可见）。**你不用管命名、格式、目录结构**（脚本统一处理）。

- ★ 第 ④ 步**非致命**：没配云配置 / 没登录 / 不在成员名单 ⇒ **只告警**，
  投递本体照样成功（云登记只是"可见性"增强）。要跳过：加 `--no-cloud`。
- ★ 身份＝**技能名 + 内容哈希** ⇒ 同一份重复投递会被**幂等跳过**；改了内容再投 = **新版本另占一行**。

### 三·二 管理者端 · 归纳（生成注册表）

```bash
"{{PY}}" "{{WB_ROOT}}/skill-registry-sync.py" --dry-run   # 先看要同步几条
"{{PY}}" "{{WB_ROOT}}/skill-registry-sync.py"             # 正式写注册表
```

- 扫投递区 → 读每个技能文件夹的**说明文档** → 归纳 → 写**注册表**（在只读空间）；
- ★★ **身份＝技能名 + 内容哈希**：
  - 同名 **同**哈希 ⇒ 同一份 ⇒ 只刷元信息，**不动**审批状态（不会把"已通过"打回"待审"）；
  - 同名 **不同**哈希 ⇒ **新版本 ⇒ 新增一行**，旧行原样保留（**谁都不被覆盖**）；
  - ⚠ **旧实现只按名字索引** ⇒ 同名新版本会被当成"同名技能的更新"并**保留旧状态**
    ⇒ **一份从没审过的新版本静默继承了「已入库」**。这就是"重名不同版本"当初的漏洞。
- ★ 这一步**必须由管理者本机跑** —— 注册表在只读空间，成员写不进去（**这正是设计**）。

### 三·三 成员端 · 取用技能

```bash
"{{PY}}" "{{WB_ROOT}}/skill-fetch.py" --list                     # 看有哪些
"{{PY}}" "{{WB_ROOT}}/skill-fetch.py" --name "<技能名>"           # 取用（默认装到本机技能目录）
"{{PY}}" "{{WB_ROOT}}/skill-fetch.py" --name "<技能名>" --out "<目录>"
```

- **注册表 = 白名单**：**只在注册表里的技能才会被取用**；没登记的一律拒绝；
- 取用会**校验 sha256**（与注册表比对）—— 对不上就**中止安装**；
- 解压带**防路径穿越**保护。

## 四、注意

- ❗ **别直接往投递区手工塞文件** —— **没登记 = 不存在**；投递请走投递脚本；
- ❗ 注册表里没有的技能，取用脚本会**明确拒绝**（这是**保护**，不是 bug）；
- "说明"文档就是给 agent 看的**唯一可读入口** —— 投递时**把 note 写清楚**，别人才能判断要不要用；
- 缺配置时报错是**对的**（先跑 `ensure-config.mjs --for <技能名>` 看缺哪几项）。

## 五、★ 两条踩出来的工程判据

| 判据 | 来历 |
|---|---|
| ★★ **"扫到 0 条 / 列不出来"永远要当成疑似故障** | 排障 §六·一时发现：`list` 调了**不存在的 API 名**（复数 vs 单数）⇒ 恒返回空。**静默的 0 与真实的 0 长得一模一样** ⇒ 凡"读不到东西"的脚本，都要有一条**能区分二者**的探针 |
| ★★ **"报错"比"静默"好，别把报错改成静默** | 同族第二处：给不接受分页参数的接口**无条件带** `--limit` ⇒ 从"报错"变成"恒返回空"。★ 修法应是**先带参数试、失败就去掉重试**，而不是把失败吞掉 |

> ★ 一般化：**跨平台的/第三方的接口名与参数，不能靠猜**（复数 / 单数、要不要 `--limit`）——
> 一律**用"真跑一次"确认**，并把"判不了"与"没有"**在输出上分开**。

## 六、技能橱窗（稳定版归档）

**用途**：把**仓库里现有的稳定技能**归档成一个**只读橱窗**，
让**新电脑 / 新同事的 agent 一眼看到"我们有哪些技能、各自什么功能"** —— 不必先读遍仓库。

```bash
# ★ 只有管理者跑（在仓库根目录；这个脚本不下发给成员）
"{{PY}}" "{{REPO}}/scripts/skill-library-sync.py" --dry-run   # 看要归档哪些
"{{PY}}" "{{REPO}}/scripts/skill-library-sync.py"             # 归档（缺的建、有的更新）
```

- 归档内容：每个技能一个文件夹（`<技能名>.zip` + `说明`）；
- **默认全归档**（技能本来就在仓库里，clone 就有 ⇒ 橱窗放不放**不改变可见性**）；
  确实不该进馆的用 `--exclude a,b` 单独排除；
- **幂等**：已存在的走"更新"（**替换**本体与说明，**不堆积旧版本**）；
- ★ **归档"不在仓库里"的技能**（走技能库分发的那种）—— 加 `--skill-dir`：

  ```bash
  "{{PY}}" scripts/skill-library-sync.py \
    --skill-dir "<本机技能目录>"            # 可逗号分隔多个；不填则归档仓库全部技能
    --category "03·环境与部署"              # 本机技能不在分类表里，需显式给
  ```

- ★★ **这一步会同时把注册表状态写成「已入库」** —— 即 **「入库 + 挪进橱窗」是一次动作**，
  不必"先在表里点入库、再手工搬"；
- ⚠ **橱窗不是真源** —— 它由仓库镜像而来，安装 / 更新仍走同步脚本或取用脚本。

### 六·一 排障：橱窗里出现「同一技能多套」

**症状**：某个技能文件夹里出现 2 个本体 + 2 份"说明"。

**根因（幂等失效，两个 bug 叠加）**：

1. 归档脚本调了**不存在的 API 名**（复数形式，正确是**单数**）⇒ 恒返回空
   ⇒ 永远"查不到已有节点" ⇒ **每次同步都新建**；
2. 判断"已有 zip"时用了一个**节点上并不存在的字段** ⇒ 恒为假。

**验证是否已修**：`skill-library-sync.py --dry-run` 输出里 `created` 应为 **0**、各 `action=update`。
★ **这就是"幂等"最容易被骗的地方：脚本"以为自己在更新"，其实在新建。**

**清理存量**（资料库通常**没有删除节点 API**，只能移动 + 人工删）：

1. 在橱窗空间建一个文件夹（如「🗄 待删归档（旧版本）」）；
2. 对每个重复技能：列它的子节点，按类型分组、**按 `updatedAt` 保留最新**，其余**移进归档夹**；
3. 在归档夹里建一份「归档清单」文档（列出技能 / 类型 / 时间 / 节点 ID + 删除步骤）；
4. 让使用者**在界面手动删**该文件夹。

> ★ 与"清理个人文件"同一套纪律：**移走，不删；清单 + 人工确认**。

### 六·二 ★ 定位策略：ID 为主，**别靠名字**

- 配置里存的是**节点 ID** ⇒ **位置移动、被页面包含，都不影响**（ID 不随位置改变）；
- 需要"重新找"时：按 ID 直接访问 ✅｜按 ID 反查位置（`node-info`）✅｜逐层遍历 ✅；
- ❌ **别按名字搜** —— 内容搜索是**搜正文**的，**搜不到标题**（实测搜 5 个标题词，只有正文命中）；
- ★ **健康检查**：一条脚本反查配置里**所有链接类 ID**，表被删 / 移走时**当场发现**，
  并接进发布前自检（`preflight`）—— **ID 型依赖必须有人定期反查，否则失效是静默的**。

### 六·三 对外可见的那份清单，**不会自动跟随**

对外快照（如云应用里的技能清单）**是只读快照，不会自动跟随注册表** ——
新增技能 / 改分类 / 改标签后**必须显式同步一次**，
否则别人看到还是旧的那一批（实测踩过：注册表 31 条、对外快照还停在 23 条）。

| 项 | 说明 |
|---|---|
| 字段 | `slug / title / description / category / distribution / source_updated_at` |
| 来源 | 注册表里**状态 = 已入库**的行 |
| 唯一键 | `slug` ⇒ 用 **upsert** 保证幂等 |
| 现状 | 由 **agent 在管理者机上执行**（读注册表 → 经云库管理通道写入） |

> ★ **"多端可见"与"自动同步"是两件事**：可见性是给人看的，同步必须显式做一次，
> 并且**做完要核对条数**（否则"我同步过了"只是一句话）。
