# 系统健康度一屏

> **一句话**：跑一条命令，看全"系统现在健不健康"。

## 何时用

- 用户问「**系统健康吗 / 状态怎么样 / 体检一下 / 自检一下**」
- 准备跑业务前，想**先确认环境就绪**（避免跑到一半才发现桥接断了 / 配置缺了）
- 换机、更新之后的自检
- 想快速知道"我在哪台机器、什么身份、代码新不新"

## 怎么跑

```bash
"{{PY}}" "{{WB_ROOT}}/system-health.py"           # 一屏（默认）
"{{PY}}" "{{WB_ROOT}}/system-health.py" --fast     # 跳过桥接探测（最慢的一项）
"{{PY}}" "{{WB_ROOT}}/system-health.py" --json     # JSON（供告警 / 看板消费）
"{{PY}}" "{{WB_ROOT}}/system-health.py" --selftest # 只跑内置自测（不联网）
```

> 退出码：**0 = 没有 ▲/✗；1 = 有 ▲ 或 ✗**（可直接接告警）。
> ★ **「未启用 ·」与「判不了 ?」不计分**。

## 六档状态（先看这个再看表格）

| 符号 | 状态 | 意思 | 要不要管 |
|---|---|---|---|
| ✓ | 正常 | 查过、没问题 | 不用 |
| ▲ | 要你过目 | 有问题（**含「待配置」**：该配却没配） | **要**，驱动退出码 1 |
| ✗ | 真错 | 阻塞级 | 立刻 |
| **·** | **未启用** | **这台机不需要这一项**（不是"跳过"、更不是"错"） | 不用；**它会自己转态** |
| ? | **判不了** | 探测失败 / 证据不足 | 想查清就得先修探测条件 |
| ○ / - | 信息 / 本次没跑 | 纯提示；`-` 是 `--fast` 之类主动跳过 | 不用 |

### ★★ 为什么要有「未启用 ·」这一档

**「部署完成」不等于「权限获取完毕」** —— 新机部署那一刻配置是空的，但**那时不该吵**；
等对方**拉完权限**，这台机就**该配**了。两种偷懒做法都不行：

- **缺了就报警** ⇒ 新机一进来满屏红黄（**狼来了**，真问题被淹）
- **缺了就静默** ⇒ 权限到位后**永远不提醒**（把该报的问题藏起来 —— 这是头号忌讳）

⇒ 所以"该不该配"**必须是实时探测**（系统里**没有**部署时间 / 宽限期这种东西）：

```
该配 + 没配   ⇒ ▲ 待配置（会提醒，不静默）
不该配 + 没配 ⇒ · 未启用（不吵）
探不了        ⇒ ? 判不了（**不许当成"不用配"**）
```

**它是怎么知道"该配"的**：**不读本机配置**，而是问服务端「**我被拉进过别人的团队空间吗**」——
这件事在服务端直接可见。★ 这绕开了一个循环依赖：
「判你是不是空间 owner」要空间 ID，而空间 ID 就在新机那份**空配置**里。

⇒ 对方**拉完权限那一刻，这台机的下次自检会自动从「·」变「▲ 待配置」**，**不靠人记着催**。

## 七项怎么看

| 项 | 看什么 | 异常怎么办 |
|---|---|---|
| **配置** | 身份（你是谁 / 看哪些账号）+ 清单 + 审批表 | 四态：齐 ⇒ ✓；缺 + **该配** ⇒ ▲ **待配置**（跑配置引导，缺什么问什么）；缺 + 不该配 ⇒ · 未启用；探不了 ⇒ ? |
| **身份** | 身份判定的分级结论 | 判不出 ⇒ **? 判不了**（新机 / 未配 / 网络不通，**不是错**），拉完权限再确认即可；判成"冒用" ⇒ ▲ 要人工确认，**别直接放权** |
| **更新** | 落后几个提交 | 有更新 ⇒ **问用户**要不要更新（别自作主张） |
| **桥接** | 后台进程 / 扩展 / 窗口 | **`○` 是按需启动，不是错**（用时会自动拉起） |
| **部署** | 技能下发数 + **一致性检查**（十几项：权限矩阵 / 下发副本 / 技能依赖 / 文档索引 / 文档镜像 / 配置副本 / 链路一致性 / 技能元数据 / 文档路径 / 仓库根定位 / 用户级总根 + 身份层块 + 守卫 / 平台事实 / 记忆树结构）+ **未下发检测** | 报「未下发」⇒ 重新下发；报「一致性异常」⇒ 看对应脚本提示；报「找不到仓库 ⇒ 一致性全部跳过」⇒ **这是失明不是通过**。★ 哪几项 + 红/黄都看**唯一真源**（那张分级表）；★ **「未跑」（缺检查脚本）也算告警，绝不报 ✓**；★ 注册表本身读不出来 ⇒ **不许报「0/0 ✓」** |
| **任务** | 任务快照条数 | 发布布局下"无快照目录"属正常（任务存平台侧） |
| **记忆** | **两层**：① 工作区长期记忆体量 ② **用户级**（跨项目）那份的体量；再加日志份数与最大者 / 归档 / 日记本 | 超阈 ⇒ 跑 `memory-distill`。★ **两层各有独立上限**：工作区 **10000 字符**（超 **8500 字**报警）/ 用户级 **4000 字符**（超 **3400 字**报警）—— **只量一层 = 同款「假绿」**。★ 判据按**字符数**（客户端按字符截断，不是字节） |

★ 记法：**`·` 与 `?` 都不计分** —— 把"不用查"混进"有问题"会让真问题被淹，两者必须分开说。
★ 但**都不许静默**：总评里会把它们各自几项点名（如 `· 未启用 2 项`）。

## 设计原则（这几条是它值得抄的地方）

- **复用已有探针，不重复造轮子**：每一维都指向**已有的那个检查**，
  不另写一套（两边口径要一致）。`--fast` 会跳过最慢的一致性检查。
- **按需启动的项不算异常**：桥接没跑 ≠ 出问题（它本来就是用时才拉）。
- ★ **「不用查」与「查不了」都不是"没问题"**：前者记 `·`、后者记 `?`，
  **都在总评里点名，只是不计分** —— **既不当狼来了，也不静默失明**（两种失败模式都踩过）。
- ★ **「该不该配」实时探，不用部署时间 / 宽限期猜**：判据是**服务端看得见的事实**，
  **不依赖本机配置**（否则新机探不动）。
- ★ **字段清单读真源，本文件不硬编码** —— 免得造出**第二份真源再漂移**。
- **纯读、无副作用**：只探测、不改任何东西。

---

## 这套六档设计的要点

**它把"状态"从两档（好/坏）拆成了六档**，而拆的理由很实在：

| 混淆 | 后果 |
|---|---|
| "不用查" 混进 "有问题" | **真问题被淹**（狼来了） |
| "查不了" 混进 "没问题" | **静默失明**（把不知道说成知道） |

⇒ **拆开之后**，"没吵"和"没查"就是两件不同的事 —— **这正是它比普通健康检查值钱的地方**。
