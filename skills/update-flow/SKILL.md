# 老机器更新（**一次只给一步**）

## 〇、这份流程解决什么

「更新」在这套系统里**不是一条 `git pull`**。它至少是**六件互相独立的事**，而且**顺序有讲究**：

| # | 要更新的东西 | 为什么不能漏 |
|---|---|---|
| 0 | **本地有没有未提交的改动** | 有 ⇒ 拉更新会**撞车**（轻则冲突、重则把别人的改动盖掉）⇒ 这是**闸门**，先过它 |
| 1 | 代码（`git`） | 专门的检查脚本管这段 |
| 2 | ★ **`clone` 带不走的两样**：账号级总根 + 记忆守卫 | 都不在仓库里、且命令里**必须写本机路径** ⇒ 换机 / 更新后要**重新装配**，否则「代码能跑但没人指路」，且守卫会**静默失效** |
| 3 | 技能 / 脚本的**运行位置** | 仓库改了、运行位置没改 ⇒ 跑起来用的**还是上一版**，而且**不报错** |
| 4 | 配置的**多个副本** | 副本落后 ⇒ 各处读到**不同的值**，也不报错 |
| 5 | **收尾自检** | 前面每步都动了本机；这一步统一回答「现在自洽吗」。**不做，前面等于没做** |
| 6 | **定时任务对账** | 任务存本机、**不跟仓库同步** ⇒ 最容易漂 |

> ⇒ 缺的从来不是能力，是**编排**。所以第一步永远是同一条命令：
> **让机器自己说「我这台该做哪几步」。**

---

## 一、★ 唯一硬规矩：**一次只给一步**

提出者原话：**"尽量不用我去教他怎么跑，他跑一步你教一步。"**

| 要 | 不要 |
|---|---|
| **一条**命令，**等回执** | 一次贴完 0~6 步（他会直接懵，然后乱跑） |
| 一句**人话**说"为什么做这步" | 说 `git rebase` / `origin/pub` / "快进合并"这类词 |
| 明确「**你会看到什么**」 | 让他自己猜"跑对了没有" |
| 明确「**不对怎么办**」（含"停下来问谁"） | 出错后让他自己想办法 |
| 出错 ⇒ **先停下**，把原文贴给维护者 | 让他连着试几条命令"碰碰看" |

**每一步给完就停。** 收尾那条也一样：给完等他说"好了"。

**步骤是机器算出来的，不是你背的** —— 每台机器缺的步骤不一样
（有人的机器可能只有 2 步，有人的可能 5 步）。**永远以 `update-plan.py` 的输出为准。**

## 二、开跑前：先拿「这台机器该做哪几步」

```bash
cd "{{REPO}}"
python scripts/update-plan.py
```

它是**只读**的（不改任何东西），输出形如：

```
⛔ 【第 0 步】先处置本机未提交的改动（**闸门**）
      为什么：……      怎么做：git status --short      看什么：……
【第 3 步】把技能 / 脚本下发到本机运行位置
      为什么：……      怎么做：node install-skills.mjs   看什么：……
⇒ 共 N 步。**一次只做一步**，做完看「看什么」那一行再往下。
```

- `--json` 给你自己解析用（**给用户看的永远是人话版**）。
- 结尾若是 `✅ 无事可做` ⇒ **如实告诉他"已经是最新的，不用动"** ——
  **别为了显得干了活而编步骤。**
- 有 `⚠ 判不了` 的行 ⇒ **明说"这一项没查成，不等于没事"**，别当成通过。

## 三、逐步的话术骨架（照这个口径说，别加术语）

每一步都按四件套讲：**为什么 / 怎么做 / 你会看到什么 / 不对怎么办**。

### 第 0 步 · 闸门（有未提交改动时**才**出现）

> 「你机器上有 N 个文件改过还没存档。**先更新会和它们撞车**，所以我们先处理这个。
> 跑一下 `git status --short`，把结果贴给我 —— 我看一眼是不是你自己的改动。」

★ **判据在这儿**：是**他自己的**改动 ⇒ 让他决定"存下来还是丢掉"；
**说不清来源 / 是别人的** ⇒ **停，别继续**，把原文贴给维护者。
**这一步不许替他"顺手清掉"**（可能是别人未提交的在制品）。

### 第 1 步 · 拉更新

> 「服务器上有你手上没有的更新，跑这条它自己拉：`python scripts/self-update-check.py --apply`。
> 看到 `"applied": true` 就是成功了。」

### 第 2 步 · 入口（总根 + 守卫）

> 「有两样东西**不在代码里**，每次更新都要重新装一次（就像换了门牌要重新贴指路牌）。
> 跑：`python scripts/ensure-user-pointer.py`。看到两行 ✓ 就对了。」

### 第 3 步 · 下发技能与脚本

> 「代码更新了，但**你这边实际跑的是另一份拷贝**，得把它也换新。跑：`node install-skills.mjs`。」

### 第 4 步 · 配置副本

> 「配置在你机器上存了好几份，得让它们一致。还是那条：`node install-skills.mjs`。」

### 第 5 步 · 收尾自检（**永远都有**）

> 「最后验一下整台机器是不是自洽。跑 `bash scripts/preflight.sh`，大概半分钟。
> 结尾看到 `✅ 可以推送（0 ✗ / 0 ⚠）` 就算更新完成。」

★ 有 ✗ ⇒ 把**那一行原文**贴出来给他，并按提示修；改完**再跑一次这一步**。
**不许跳过自检说"应该好了"。**

### 第 6 步 · 定时任务对账（**agent 做，不让他做**）

> 「还有一件事是我来做：定时任务存在你本机、不跟着代码走，我核对一下是不是还齐。」

读出**线上任务**，与**仓库里的任务快照**逐条比 **条数 / 触发规则 / 状态**；
不一致就按快照文件头的「如何刷新」改。**任务的新建与删除先问过他。**

## 四、术语替换表（左边这些词**不许对他说**）

| 不说 | 改成说 |
|---|---|
| `git pull` / `rebase` / `fast-forward` / 分支 | 「拉更新」 |
| `origin` / 远端 | 「服务器上那份」 |
| 未提交 / dirty / working tree | 「改过还没存档的文件」 |
| `install-skills` / 下发 / 部署位 | 「把你这边实际在跑的那份也换成新的」 |
| 配置副本 / 漂移 | 「配置存了好几份，让它们一致」 |
| `preflight` / 自检 / CI | 「最后验一下整台机器」 |
| 总根 / hook / 守卫 | 「不写在代码里、每次更新要重装的那两样」 |
| 任务快照 / `automation_update` | 「我核对一下定时任务还齐不齐」 |

## 五、出错时的三条退路（★ 别让他自己想办法）

1. **能看懂 ⇒** 按「看什么」那一行对照，把差在哪告诉他；
2. **看不懂 / 报错带路径或英文 ⇒** 让他**把原文贴过来**，**别让他改**；
3. **涉及删文件、覆盖别人改动、改云端数据 ⇒ 一律停下问维护者**
   （这三类**不许自己动手**）。

> ⚠ 更新**永远不该删他自己的东西**。如果他发现"更新把我某个文件弄没了" ⇒
> **立刻停**，这属于上面第 3 类，**先把现场留住**（别让他再跑别的命令）。

---

## 六、别做的事（都踩过）

- ❌ **一次贴完所有步骤** —— 违反本技能的第一条规矩。
- ❌ **跳过自检**说"应该好了" —— 前五步都改了本机，**自检是唯一的总验**。
- ❌ **把"判不了"说成"没事"** —— 探针跑不成时必须明说。
- ❌ **替他处置本地改动** —— 那可能是别人未提交的在制品。
- ❌ **"更新"时顺手重建定时任务** —— 任务通常是**默认关**的；
  他只说"更新"，你就只更新。
- ❌ **本机没有的步骤也照念一遍** —— 步骤以 `update-plan.py` 的输出为准。

## 七、与其它流程的分工（别混）

| 场景 | 看哪个 |
|---|---|
| **已经装好，要更新** | **本技能**（`update-plan.py` + 一步一教） |
| **全新电脑，从零装** | 换机恢复 SOP + `onboard`（配置引导） |
| 只关心**代码分支怎么合**（维护者视角） | `repo-sync`（双向同步） |
| 多机权限 / 只读成员怎么拿代码 | `multi-user-deploy` |
| 配置缺项怎么问、怎么填 | `onboard` |
| 定时任务怎么建 | `automation-rebuild` |
